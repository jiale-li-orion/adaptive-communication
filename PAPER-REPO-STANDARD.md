# Paper Repository Standard

**A reusable convention for repositories whose primary product is a paper, distilled from artifact-evaluated systems repositories.**

A paper repository exists so that a reviewer who has never seen the project can go from `git clone` to a verdict on every claim in the paper without asking the authors anything. That purpose turns the repository from a place where code is stored into an evidence system, and an evidence system needs four properties: the clone is verifiable, numbers have one source, claims have one current status, and history is immutable. Each property is paired below with a mechanical check. A rule without a check survives until the first deadline.

## 1. Scope and normative sources

This standard applies to repositories whose primary product is a paper with an experimental claim. It does not apply to standalone method libraries, and it does not prescribe research practice.

The normative sources for artifact expectations are the ACM SIGSOFT artifact-evaluation guidance and the csartifacts resource collection [9][10]. Both require an artifact README that states how to install, how to run, how to compare against the paper, and which paper claims the artifact supports. Section 11 lists ten repositories used as implementation models, each cited for the specific practice it demonstrates.

## 2. Four invariants

**I1 Clone-verifiable.** After `git clone` plus the documented acquisition steps (`make deps`, `make data`), the repository's check entry point passes. Checks may depend on published files and on out-of-repository artifacts whose acquisition is documented and automated; they may not depend on anything else. Consequence of violation: the failure appears in the reviewer's hands, not the authors'. Check: run the entry point in a clean clone.

Two dependency classes must be distinguished, and both appear in this standard's own first case study. *Publishable dependencies* — specifications, reference results, small samples — belong in the repository; excluding them is an error. *Acquired dependencies* — large datasets and third-party packages — stay out, but each must be reachable through a documented, idempotent command, and a check that finds one missing must print that command rather than raise a traceback. In this repository's own gate, that distinction reduced a clone failure count from 3 of 18 to 2 of 18 without touching the code path under test: one failure was the excluded specification, the remaining two were the undocumented package dependency.

**I2 Numbers have one source.** Every number in the paper that depends on an experiment is generated by a script from a result file. Authors write prose and LaTeX skeleton only. Hand-copied numbers have no mechanism keeping them consistent with the results, and inconsistency of this kind does not raise an error. Check: regenerate the tables and assert equality against the result files; assert that table bodies enter the manuscript only through `\input`.

**I3 One current status per claim.** Each claim carries a status drawn from a fixed set, recorded in one table. Superseded claims leave the table body for an immutable snapshot and leave a pointer behind. Narrative documents, including the README, do not carry research history. Check: every row names an existing script and reference result, every status is in the set, every retraction pointer resolves.

**I4 History is immutable and locatable.** Superseded conclusions are not rewritten in place. They move to a date-bucketed archive carrying `superseded_by`, `reason` and `source_commit`. Archiving does not re-endorse the old reading.

## 3. Directory skeleton

```text
repo/
├── README.md  README.zh.md        entry page: claims, model, abstract; never a log
├── CITATION.cff  LICENSE
├── PAPER-REPO-STANDARD.md  PAPER-REPO-STANDARD.zh.md
├── Makefile                       check / paper / tables / data
├── paper/                         manuscripts; prose and \input only
│   ├── generated/                 generated tables, committed, never hand-edited
│   ├── figures/  refs.bib  build.sh
├── spec/                          normative numbers and contracts
├── src/ or code/                  implementation
├── experiments/                   one directory per paper experiment
├── configs/                       episode/scenario parameters, normative
├── results/
│   ├── README.md                  registry: script, command, convention, denominator
│   ├── CLAIMS.md                  claim table
│   ├── reference/                 frozen results used as verdict baselines
│   └── _withdrawn/
├── artifact/                      AE.md, reproduce_all.sh, get_data.sh
└── tests/                         only if the check entry point is not already one
```

Why each part earns its place. `spec/` exists because specifications are publishable dependencies and reviewers need them. `paper/generated/` exists so that the manuscript cannot contain a number a script did not produce. `results/reference/` exists so a verdict compares against a frozen value instead of whatever the current run happens to output. `artifact/` exists so that the reviewer's entry path is separate from the author's working path.

Three deviations are deliberate. SquirrelFS separates implementation, formal model, evaluation and environment [4]; this standard keeps that separation at the top level rather than nesting it inside one experiment tree. CalibrationPaper keeps `paper/`, `experiments/` and `src/` side by side with independent build instructions [5]; that is the layout above. A `tests/` directory is listed but optional: if the check entry point already collects the checks, a second tree creates a second entry point.

## 4. The claim table

`results/CLAIMS.md` carries one row per claim, with columns `Claim ID`, paper location, evidence, script, reference result, status, last-verified commit. Status is drawn from six values: `supported`, `scoped-negative`, `formative`, `open`, `reproduced-externally`, `retracted`.

TPack's artifact entry maps each paper finding to a specific command and expected verdict [1]; the claim table is where those commands get their identifiers. The ACM SIGSOFT guidance requires the artifact to list the paper claims it supports [9]; a claim table is that list in machine-checkable form.

A retracted claim moves to the history archive with:

```text
superseded_by: <claim id>
reason: <what corrected it>
source_commit: <commit that recorded the correction>
```

The claim table keeps a one-line pointer. One claim has one current status at any time; two statuses for one claim means the table has stopped being a source of truth.

## 5. Result registry and frozen reference results

`results/README.md` registers every result file with the script that produces it, the reproducible command, the seeds or trajectories, and what the file may be cited to show. Registration is a precondition for citation, and a file present on disk but absent from the registry is a failure, not a warning.

Two practices from the reference implementations carry over. SIGCOMM21-5G's artifact splits by experiment type, has each directory declare which figures and results it reproduces, keeps large data out of git and small samples in for validating the flow [2]; that is the model for `experiments/` and for the boundary between publishable and acquired dependencies. The ann-benchmarks reproducibility repository goes further: the paper PDF sits at the end of the reproduction pipeline, the LaTeX build reports which runs are missing, and archived raw results allow rebuilding the paper without rerunning every experiment [7]. The last capability is worth designing for early, because it is what makes a re-analysis cheap.

Frozen reference results in `results/reference/` are what a verdict compares against. Without them, "reproduced" means "produced a number", and drift between a run and a past claim stays invisible.

## 6. The number generation chain

A result file feeds a generator, the generator writes LaTeX table bodies into `paper/generated/`, and the manuscripts include them. The generated files are committed, so a reviewer sees the exact numbers used, and any change to a result requires regenerating them in the same commit.

robust-pll demonstrates the full pipeline — data creation, a single run-all driver, raw result files, a results database, table and plot generation, and only then paper figures [6]. A database is not required; the property that matters is that the paper's numbers are computed from a canonical store rather than transcribed. With two manuscripts in two languages, that property is not optional: the same table exists twice, so a hand-copied number has four places to drift.

Two checks make the chain hold. Regeneration is idempotent when results are unchanged, and generated numbers are asserted equal to the result files. A third check asserts that the manuscripts' table bodies arrive through `\input`, which prevents a number from being written back into prose.

## 7. Artifact entry point

`artifact/AE.md` is the reviewer's only entry. It states, in this order: the machine and dependency requirements; how to obtain the code and any acquired data; a Getting Started path that reaches one verdict in minutes; the full reproduction, per claim, as command plus expected verdict plus expected time; and what the artifact does not do.

FlexLLM's artifact opens with the hardware, toolkit versions, container, disk, cloud instance type and clone command [8]; a reviewer should never have to guess the environment. Not every field applies to a simulation repository, but the discipline does: state the environment, the dependencies, and which claims need credentials, and separate the claims that run without any.

TPack separates Getting Started from full reproduction and freezes an artifact tag [1]. The separation matters because a reviewer under time pressure runs the first path only, and a first path that takes hours is a first path that does not run. `artifact/reproduce_all.sh` calls each claim's script, compares against `results/reference/`, and prints PASS or FAIL with the deviation.

## 8. The check layer

One entry point collects the checks and reports exit codes. The runner does not parse the checks' prose output, because a check that fails while printing confident lines is the failure mode the checks exist to prevent.

Checks are deterministic, run without network and without model calls, and finish in seconds; a slow check gets skipped by the person who needs it most. Checks run on a clone, which is I1 restated at the level of individual files.

One trap deserves naming, from this repository's own audit code: a check tool's limitation masquerades as a data defect. A registry scan whose filename pattern excluded hyphens reported every hyphenated result file as unregistered, and following the report could not clear it. When a check fails, the first question is whether the check or the data is wrong.

## 9. Coupling between paper and repository

The paper section, the implementation component and the experiment form a three-way mapping, which smartnic's artifact makes explicit by telling the reviewer where each paper section lives in the code and where the reproduction experiments live [3]. Two rules keep the mapping from rotting: the manuscript cites stable identifiers, and a change of section numbering updates the claim table in the same commit.

The manuscript holds prose, `\input` of generated tables, and references to stable script names. Numbers, seeds and denominators live in the result files and the registry.

## 10. Bootstrap checklist for a new repository

1. Create the skeleton of section 3, with `spec/`, `results/reference/` and `artifact/` present from the first commit.
2. Write `results/CLAIMS.md` with the claims the paper currently makes, even while the list is short and volatile.
3. Add a check entry point with three checks: registry and disk agree, claim rows are complete, generated tables match results.
4. Add `make check`, `make paper`, `make tables`, `make data`.
5. Record the environment in `artifact/AE.md` before the first experiment runs, not before submission.
6. Run the clone gate: clone the repository, run the documented acquisition step, run the entry point. Fix what fails.
7. Register every result file at the moment it is produced; a registry maintained afterwards is maintained never.
8. Put acquired dependencies behind idempotent commands, and make their absence print those commands.
9. Freeze reference results the first time a number enters the paper.
10. Tag the state before any standardization pass, so later changes stay diffable.

## 12. Anti-patterns and case studies

Four incidents from the repository this standard was distilled from. Each rule above traces to one of them.

**A specification excluded from the repository.** The check entry point read a deployment manifest that lived under a directory excluded from version control. On the author's machine the check passed; in a fresh clone it could not open the file. Cause: the manifest was treated as process documentation, while it was a normative dependency. Rule: I1, and the publishable-versus-acquired distinction in section 2.

**An attribution reversal.** A failure-accounting rule counted a sample as heard at any later time rather than by the deadline, which charged 830 late-access failures to backhaul capacity. The corrected accounting moved those 830 to the access segment. The delivered total was identical under both accountings, so nothing looked wrong. Cause: the convention lived in one script and its consequences in prose. Rule: I2.

**A metric that measured its own prompt.** An agent honesty count ran only on decisions that issued a dense command, never on the control group, and matched keywords the prompt itself taught; the arm with the highest score was the arm whose instructions contained the vocabulary being counted. Rule: I3, and the requirement that a retracted claim leaves a pointer.

**A number that stopped tracking the code.** A sample-energy figure in the manifest stayed at a superseded value while the implementation had moved, and the mismatch surfaced only when someone recomputed from it. Cause: two sources for one quantity, neither checked against the other. Rule: I2, plus the numeric-comparison rule in this repository's own check, which compares values rather than strings so that `4.7e-4` and `0.00047` are not reported as a disagreement.

Two anti-patterns recur independently of incidents. A README that accumulates round-by-round progress notes stops being an entry page and becomes a log nobody reads to the end. A second entry point for checks, tests or builds creates two answers to one question, and the answer that is wrong is the one that gets run.
