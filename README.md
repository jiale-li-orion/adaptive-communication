# Reliable Execution of Agentic Monitoring Workflows under Intermittent Connectivity and Energy Constraints

灾前山区滑坡与泥石流监测。状态：执行语义与机制隔离实验已冻结（`e2c3e39`），业务闭环仿真尚未开工；场景、任务、接口与成文契约见 `docs/s6-model/pre-disaster-paper-contract-v0.1.md`。

## 命题

现有应急通信研究在给定的网络角色与通信基础设施之间做组合与恢复。本文将 agent runtime 置于这些通信实体之上，研究对象是它在实体动态上线、掉线、退化、恢复时维持任务执行的能力。

场景为**灾前**山区滑坡与泥石流监测，供电受限且链路频繁中断。第一轮的通信实体固定为三类：LoRaWAN Class A 监测节点、带缓存与预置自治规则的现场网关、间歇可用的蜂窝回传；可选中继与可选备用回传只作为第二轮的单一增量资源。UAV / HAPS / 卫星 / NB-IoT / CPE / 微波不进第一轮，通信约束来自接入与回传的共因失效、可接收机会、空口与能量，与实体种类数量无关。依据与重开条件见决策记录 D2、D3。

**研究问题。** 在灾前低功耗监测网络中，控制命令与执行证据共同竞争有限的通信机会。在相同设备与预算下，利用任务时效、动作语义与跨断连记录来管理这些机会，能否改善关键监测数据的按期可用性，并缩短错误配置的持续时间？

**关键结构假设：agent 的观测通道与它的控制通道是同一条。** 它没有带外信道，没有独立的健康监测接口，没有预示实体将要掉线的先知信息。它判断某实体是否可用，只能向该实体发一次调用并观察结果，而这次调用本身穿过它试图评估的那条链路。因此"实体已静默"与"我的查询在回程丢了"在观测上不可区分，只能靠后续调用的时序模式逐步排除。既有工作多在"状态可观测"或"故障发生可被检出"的前提下讨论恢复策略，本文的自变量正是这道观测投影带来的不确定性。

## 一、定位

现有工作多在给定的网络角色与通信基础设施之间做组合与恢复：选哪条链路、何时切换、走哪条恢复路径。本文把 agent runtime 放在这些实体之上，研究对象是**任务执行在通信与供电间歇可用时的存续**。被解释变量落在关键监测数据是否按期可用、错误配置持续了多久，链路状态只是中间量。

|  | 现有工作 | 本文 |
|---|---|---|
| 优化对象 | 通信资源与路径选择 | 任务的执行语义与证据 |
| 时间尺度 | 链路级、会话级 | 任务级，分钟到小时的期限 |
| agent 角色 | 选择器 | 运行时 |
| 失败位置 | 选错了实体 | 不知道自己面对的是哪一种失效 |
| 收益度量 | 吞吐、时延、覆盖 | 按期有效监测覆盖率、配置错配时长 |

"持续稳定通信"在本文中转译为可考核的**监测服务连续性**，不承诺链路永不中断。通信技术提供物理路径，runtime 管理路径上的任务；永久无路径或无电的站点仍需工程补盲、储能或维护，这部分不计入机制收益。

**与最接近的已发表工作的边界。** TopoLLM（DCN 2026）研究语言驱动的拓扑规划，其公式与实验把问题参数交给本地算法工具并评价产出的拓扑方案，未把下发请求、远端副作用、丢失回执与重启恢复纳入实验模型。本文研究其后续的执行问题：命令与证据必须穿过间歇可用、能量受限的路径。这是问题边界的区分，不单独构成本文方法新颖性的证明；后者仍需与设备影子、幂等执行、版本控制及验证式恢复比较（见 D9）。

### 支撑命题的证据

**政策层面。** 工信部联信管〔2024〕256号（14 部门，2024-12-31）点名断路、断电、断网，把北斗短报文与天通列为基层兜底手段，要求设备适应严寒与密林，目标年为 2027。十五五方案（自然资办函〔2026〕1198号）不含任何传输连续性、功耗或覆盖要求，因此通信侧的论证只能引 256 号文。

**灾害中的实体退服记录。** 本项目调研整理了四起事件，其中的实体损失为：2026 年西藏吉隆口岸泥石流造成 5 个基站退服，同期投入卫星电话 36 部、便携卫星设备 10 套、发电油机 18 台；2024 年四川康定姑咱泥石流造成 22 km 光缆受损与 7 个基站退服，投入 1 架大型无人机基站、6 辆应急通信车、9 台高通量卫星便携基站；2024 年日本奥能登土砂灾害一度中断 88 个基站，靠移动基站车与可搬型基站恢复；2023 年新西兰 Gabrielle 滑坡破坏主干光纤，峰值约 20% 基站离线，Gisborne 一度有 90% 基站在两天内离线，临时回传改走卫星与微波，容量低于原光纤。

**物理约束。** 以下结果由公开测量数据与标准及拟合模型共同驱动，不含本项目现场实测：地形取自 SRTM1 公开高程数据，链路损耗由 Longley-Rice ITM 计算，断链的时间结构由 ChirpBox 公开轨迹拟合，供电行为由 LiFePO4 器件的公开电化学参数与气温模型推导。西藏波密与易贡的 SRTM 地形海拔跨度为 2025 至 6690 m。单网关在 121×121 网格上的可达点仅 1689 个，占 11.5%；连不通的点 12952 个，占 88.5%，这些点在 SF12 下仍不闭合。决定连通性的是遮挡而非距离。按一条固定规则取值（见下），**4.06 km** 处地形高出视线 1029 m 的点位损耗 **198.8 dB**，而 **14.40 km** 处只高出 74 m 的点位损耗 **190.2 dB**：距离远 3.54 倍的点反而好 8.6 dB。地形遮挡造成的超额损耗在 71 至 107 dB 量级，而 SF 从 7 提到 12 只增加 14 dB 灵敏度，因此链路自适应无法救回被地形挡住的节点。ChirpBox 真实轨迹（20,913 个逐小时快照、21 节点、420 条有向链路）拟合出的链路可用率为 68.75%，中断时长中位 2 h、p99 42 h，平均中断突发 6.38 h，而同丢失率下 i.i.d. 模型只预测 1.45 h，相差 4.4 倍。供电侧，LiFePO4 在 −20 °C 下容量约为标称值的 50%，且低于 +5 °C 无法充电，高海拔站点因此在冬季长时间静默。

## 二、第一轮架构与备选实体

### 2.1 架构 A（第一轮固定）

中心运行 planner 与 runtime；现场网关带缓存与预置自治规则；节点以 LoRaWAN Class A 接入；网关经间歇蜂窝回传。取 **16 个节点、2 个坡面组、1 个网关**，延续已有规模。测点坐标与选择理由固定，节点区分形变、雨量等角色；不把任意 DEM 网格点当作真实部署节点。风险窗口内的关键测点集合由任务给出。

Class A 是本文选定的配置，依据是它的接收窗口语义（一次上行之后只有 RX1 / RX2 两个窗口，节点回到休眠即无接收窗口），而非上述案例共同采用的协议。

| 实体 | 第一轮职责 | 移除后的后果 |
|---|---|---|
| LoRaWAN Class A 节点 | 采样、本地触发保护下限、按 profile 上传 | 无被测对象 |
| 现场网关 | 缓存、预置自治规则、回传复用 | 节点无回传路径 |
| 间歇蜂窝回传 | 网关到中心的路径 | 中心无法下发，退化为纯本地规则 |

接入与回传可以共因失效——同一次天气或供电事件同时打断两条路径。这是第一轮要测的结构，也是"观测通道与它的控制通道是同一条"在部署上的来源。

### 2.2 第二轮：只增加一种资源

第二轮仅增加一种资源（固定中继或备用回传），做"硬件有 / 无 × runtime 有 / 无"的 2×2 对照，不给 agent 一个无条件成功的信号增强按钮。备用回传可能仍共享网关、电源与最后一跳，路径数增加不自动消除带外管理的质疑。

另设**独立可靠管理路径**组：中心始终拥有一条与监测链路无关的管理通道。这一组用于检验本文机制何时不再必要——结构假设不成立时，收益应随之消失。它的用途是给结论划边界，不作为主结果臂。

#### 方法对照

主表比较的是**执行运行时**，在固定决策轨迹上运行，不复现任何一篇的 planner。因此这一列用的是语义名，而不是论文名：把一个论文名贴到一行只实现了其骨架的策略上，等于借用该论文的权威。那些系统本身放到 LLM supplement 里实现，那里才是 agent 级的对照。

| 方法 | 语义 | 出处 |
|---|---|---|
| One-shot execution | 假定工具执行可靠：每个决策只发一次，失败即上报并丢弃。这是 WirelessAgent 的**假设**，不是 WirelessAgent 系统 | Tong et al., *WirelessAgent: Large Language Model Agents for Intelligent Wireless Networks*, China Communications 23(3):265–285, 2026, DOI [`10.23919/jcc.fa.2025-0163.202603`](https://doi.org/10.23919/jcc.fa.2025-0163.202603)，亦见 [arXiv:2409.07964](https://arxiv.org/abs/2409.07964) |
| Retry-on-uncertainty | 结果不确定时以**新的请求身份**重发，带重试预算 | 工程惯例，见 AWS Builders' Library 与 Google SRE Book |
| Verified Tool Calls | 超时后验证后置条件，再决定是否重发 | Mansoor, Phadke, Rana, arXiv `2608.02645` |
| **Ours** | 稳定操作身份 + 持久生命周期 + 远端 epoch fencing + 限定范围调和 + first-wins 结算 | 本文 |

逻辑链是干净的：one-shot 假定执行可靠；retry-on-uncertainty 承认不确定但用新身份重发；verified tool calls 承认不确定且先验证再重发；本文把一次远端操作当成跨断连持续存在的 durable operation，直到调和完成才结算。四条各自停在前一层。

两条实现口径需要声明。其一，`retry-on-uncertainty` **不等同于** WirelessOpsAgent（[arXiv:2608.08277](https://arxiv.org/abs/2608.08277)）的方法。该文的 RETRY 是动作保证阶段的一个决策，分发后的盲目重试只是其骨架。把它当论文名使用会被正确地质疑；作为语义对照则没有问题。其二，`verified tool calls` 按原文实现：原文规定每次尝试携带同一个确定性幂等键（`k = hash(agent_id, action_type, payload, timestamp_bucket)`），验证器返回 True / False / **Unknown** 三值，Unknown 表示状态不确定，算法此时退避等待而不重发。第一版实现漏了稳定键、并把 Unknown 压成 False，因此比其命名的方法更弱，调高后的恰好一次率从 29.2% 变为 32.8%。

CRITIC 与 AgentSpec 不进主实验。前者处理验证器本身的质量，后者处理动作允不允许执行，与本文所在的层不同，混入会把坐标轴搞散。

**LLM supplement。** 主表固定决策轨迹，因为本文的自变量是执行语义，模型采样噪声会毁掉这条因果。补充实验再让**同一个 LLM** 接四种执行层，检验闭环情形下结论是否保持；[WirelessAgent](https://arxiv.org/abs/2409.07964) 与 [WirelessOpsAgent](https://arxiv.org/abs/2608.08277) 按各自论文的方法在那一层实现，与本文的对照挂在 agent 级而非 runtime 级。

该实验有一条硬约束：**所有 arm 必须共享同一套 action 与 tool surface**——相同的 observation 格式、相同的动作集合、相同的工具 schema、相同的预算、相同的副作用语义。若让本文的 arm 拥有 wait / reconcile / relay 而对照只有 retry / hold，得到的差异衡量的是谁被给了更多动作，与决策质量无关。执行层的差异应当体现在**同一动作集合下的处置语义**，而不是动作集合本身。

这条约束与 `2608.02645` 的实验设计一致：该文用同一个模型驱动所有方法，理由正是让差异反映工具交互层而非模型能力。接口留在这里，实现待做。

**必引但不跑。** Yao et al., *ReAct: Synergizing Reasoning and Acting in Language Models*, ICLR 2023, [arXiv:2210.03629](https://arxiv.org/abs/2210.03629)（agent-loop 源头，通用背景）；Tong et al., *WirelessAgent++: Automated Agentic Workflow Design and Benchmarking for Wireless Networks*, [arXiv:2603.00501](https://arxiv.org/abs/2603.00501)（通信 agent 已在做 workflow search，但优化的是 workflow 而非执行语义）；Ma et al., *TopoLLM: LLM-driven adaptive tool learning for real-time emergency network topology planning*, Digital Communications and Networks 12(2):273–282, 2026, DOI [`10.1016/j.dcan.2025.10.002`](https://doi.org/10.1016/j.dcan.2025.10.002)（与"应急通信 + LLM + tool use"最贴的正式发表工作，负责把本文场景接进应急通信 agent 文献；其全文尚未核实，工具目录与失败语义未验证）；Wang, Poskitt et al., *AgentSpec: Customizable Runtime Enforcement for Safe and Reliable LLM Agents*, [arXiv:2503.18666](https://arxiv.org/abs/2503.18666), 2025（界定邻近的 runtime enforcement 方向，即动作允不允许执行）。

另保留最小工程惯例参照：blind retry 与指数退避，以及默认工具超时语义（MCP 规范 2026-07-28 的 Cancellation 章）。

### 实验范式

在本次检索覆盖的通信领域文献中未见使用 benchmark 作为评测基底的做法。通读的 9 篇同类论文中用外部 benchmark 作评测基底的仅 2 篇，且无一采用"公共 benchmark 加统一协议"的形式；其余全部为作者自建仿真或自建解析模型。领域惯例是**从数学描述重实现对照、用标准信道模型、报 Monte Carlo 次数**，把可复现性寄托在方法与参数表的完整，而非一个可执行的任务套件。JSAC / TCOM / TWC 的作者指南不含代码共享条款，只鼓励补充材料。

本文因此不寻找 benchmark，而是选定仿真基底并公开场景定义与全部参数。

| 层 | 选择 | 理由 |
|---|---|---|
| 地形传播 | Longley-Rice ITM v1.2.2，真实 SRTM1 | 不规则地形的标准模型；9 篇同类论文中无一使用真实地形，这一层是本文的差异化位置 |
| 链路时间相关性 | ChirpBox 实测拟合的 Gilbert-Elliott | 20,913 个逐小时快照、420 条有向链路；i.i.d. 假设会把突发性低估 4.4 倍 |
| 供电与静默 | LiFePO4 加充电闸门的温度模型 | 高海拔站点的失效由供电决定而非无线；面板从 30 W 增到 200 W，停电率恒为 93.7% |
| 几何视线 | 第一菲涅尔区净空，60% 判据 | 与 ITM 互为独立验证；该判据在 12 个山区场景与实测连通性 100% 一致 |
| 协议与能耗层（备选） | ns-3.48 加 FLoRa v0.3.7 | LoRaWAN 的标准平台，自带能耗模型、干扰模型与 ADR 组件。已在 `../ns3/` 建好 |
| 可微射线追踪（备选） | Sionna RT | 课题组既有平台。RT 接受 Mitsuba 场景，可把 OSM 楼房替换为 DEM 地形网格 |

传播模型按三档递增真实度组织并逐档量化增益：自由空间 → 加 DEM 视线遮挡 → 加刃峰绕射。该叙事结构取自同类文献的既有做法，本文沿用并把"只按距离"作为最低档对照。

FresSim 作为**外部定性一致性参照**引用，不承担复现义务。它提供的外部实测证据支持两点现象：地形与菲涅尔遮挡能在近距离造成失联（其山区场景 2200 与 3200 m 两点不通），而 LoRa 在开阔或超长距条件下可行（实测有 8.355、21.153、23.501、28.374 km 四条成功链路）。其山区与平坦场景分别位于西班牙 Aliaga 与 Aguilar del Alfambra，公开文本未给出足够的精确坐标，部署数据也未释放，因此不做同场景复现。本文传播模型的内部验证由两件独立的事承担：自由空间损耗的平地回归（必须复现两径地面反射模型），以及几何视线判定与 ITM 的交叉核对。

### Related work

**最接近的既有工作。** INFOCOM 2026 的 *Rollback Is Not Undo: Path-Dependent Failures in LLM-Arbitrated Network Control*（Weici Pan, Zhenhua Liu，DOI `10.1109/INFOCOM59046.2026.11571400`）在同类会议与同类问题空间证明，LLM 仲裁的网络控制回路中回滚无法恢复行为，且恢复效果路径相关。该文提出 `recovery gap` 指标，故障模式含 observation corruption、delay-reordering 与 agent dropout。它闭源且无公开 artifact。未覆盖的是灾害与应急场景、真实轨迹驱动与实体生命周期。本文需引用并显式对比。

**动作保证这一层。** Lu et al., *WirelessOpsAgent: A Benchmark and Agent Design for Action Assurance in Wireless Networks*（[arXiv:2608.08277](https://arxiv.org/abs/2608.08277)，CC BY 4.0）把研究层次定为 **Action Assurance**，判据是动作在下发前是否被正确授权，其表述为 *repairs recoverable support failures before execution*，问题被限定在可修复范围内。本文场景中 88.5% 的点位永久不可达、断电可持续数周，大量失败不可修复。该文中心是分发前的 repair，本文中心是分发后任务在实体变动下的存续。其发布物是数据与工具契约，不含运行时与评分谓词。

**已被占据的机制。**

## 四、系统模型

> **本节描述的是已冻结的机制隔离层（共享环境轨迹），不是契约要求的业务层模型。** 它缺三项：控制面机会与上行节奏的耦合、动作驱动的电量演化、采样与缓存调度。业务层的模型要求见契约 §6，其中"共享错误发电轨迹不保证差值不变：断电阈值、重试与期限具有非线性"与"固定 alive 轨迹只能隔离执行机制，不能支持策略节能"两条限定了本节的适用边界——本节结果不得用于续航或节能主张。

每条参数标注证据层：**M** 实测、**S** 标准模型、**F** 拟合、**A** 假定。A 层须做敏感性扫描，不得当作实测值报告。

### 部署与几何

研究区域为西藏波密与易贡一带，已记录的最大规模滑坡发生地之一。地形取真实 SRTM1（1 角秒，约 30 m），瓦片 N30E094 及相邻三片，原始海拔跨度 2025 至 6690 m。**M**

网关单点架设在 (30.330°N, 94.780°E)，海拔 2317 m，处于谷地，四周山脊高出 3300 m 以上。这一选择是场景的一部分：山区监测的现实形态就是谷地汇聚点加坡面节点。**M** 节点布点在网关周围 121×121 格点上，点距约 204 m。**A**

### 信道模型

**空间维：地形损耗。** Longley-Rice ITM v1.2.2 点对点模式，沿大圆路径按 DEM 原生分辨率采样，4/3 等效地球半径。参数为 868 MHz、发射 14 dBm、两端天线增益 2 dBi、馈线 1 dB、带宽 125 kHz、天线高 2 m、地面 ε=15 与 σ=0.005 S/m、大陆温带气候、可靠度 90%。**S** 公里与兆赫口径下自由空间损耗为 `20log10(d_km) + 20log10(f_MHz) + 32.44`，总损耗为 `FSPL + avar`，平坦地形回归必须复现两径地面反射模型。**S**

**时间维：链路好坏的时间相关结构。** Gilbert-Elliott 两态模型，参数由 ChirpBox 拟合：`p(g→b)=0.0712`、`p(b→g)=0.1567`，链路可用率 68.75%。平均下行突发 6.38 h，上行 14.04 h，而 i.i.d. 只预测 1.45 h。中断时长不是指数分布，42.99 万个未删失中断段的经验分位数为中位 2 h、p90 5 h、p95 10 h、p99 42 h，1.8% 超过 24 h；对数正态（μ=0.919、σ=0.807）在 AIC 与 KS 距离上最优。样本量 43 万时 KS 检验对所有参数化模型都给零 p 值，故建模以经验分位数为准，对数正态仅作平滑内插。**F**

ChirpBox 采自上海城区。借用的是时间相关结构，不是绝对水平。**效力威胁**

**地形建模的差异。** 同类论文中无一使用 DEM 或实测 trace。真实地形给出的结果与距离主导的直觉相反：距离近 4.2 km 的点位反而差 15.8 dB；遮挡造成的超额损耗在 71 至 107 dB 量级，而 SF 从 7 提到 12 只增加 14 dB 灵敏度。单网关可达点占 11.5%，不可达点占 88.5%。独立做的几何视线判定给出同量级结果，原生分辨率下仅 6.6% 的格点与网关有清晰视线。**M**

### 能量模型

高海拔站点的失效由供电而非无线决定。储能取 LiFePO4：−20 °C 下可用容量约为标称值的 50%，低于 +5 °C 无法充电。**S/M** 发电取光伏，气温基线由海拔推导：3925 m 处 1 月均温约 −19.5 °C、7 月约 −7.5 °C，日间温度全年低于充电下限。

三条反直觉结论。面板从 30 W 增到 200 W，停电率恒为 93.7%，发电被温度闸门掐死而非被能量禀赋限制。积雪掩埋的概率从 0 扫到 0.20 每天，停电率不动。杠杆只有电池化学、加热电池箱，或降低站点海拔。**M（模型输出）**

器件级能耗账本取实测剖面：活跃平均 35.7 mA、待机 16 µA，单周期活跃窗口约 15 s、休眠 3585 s，日均 3.56 mAh、全年约 1300 mAh，无光照条件下约 2.8 年（INA229 实测）。对照区间：ESP32 深睡 10 µA、SX1276 发射 120 mA，配 2600 mAh Li-ion 时最坏全开约 16.3 h、深睡约 13.5 年。两个区间相差两个数量级，说明寿命对占空比的敏感性远高于对器件的敏感性。**M**

气候基线整体平移 ±6 °C，停电天数在 342 天附近不变，只有夏季均温升到 0 °C 以上才改善至 217 至 260 天。基线可能偏冷约 10 °C。**效力威胁**

真实部署里加热与不加热两类站点并存，本文据此设 0.5 的加热比例。这不是调参：充电闸门决定站点能否越冬，而节点全死时任何 runtime 都送不进去，会把零次率拉到约 90% 从而淹没执行语义的对比。

### 业务与队列

上行为周期性遥测，监测对象含降雨、孔压、水位、地表位移与裂缝开度。实体部署给出的间隔为：贵州水城 **1 h** 定时、触发时 **5 min×3 包**（阈值雨量 0.2 mm、位移 20 mm）；Pantelleria **60 min**、载荷 **38 B**；Hochvogel **10 min**。本文取 10 min 与 1 h 两档并扫描，单包载荷取 38 B。**M** 下行为配置与命令，量小但必须送达：采样率调整、门限下发、休眠调度、告警确认、网关切换、中继启用。**A**

### 失效与中断模型

本节是本文的第一处分野：9 篇同域论文中无一设立失效与中断模型小节，中断在多数工作中是参数扫描的一个维度而非被建模的过程。

单个实体经历上线、可用、退化、掉线、恢复。对节点而言，掉线有两个独立来源，且**观测端不可区分、处置方式完全不同**。

**持续遮挡。** 由地形与传播决定，任何自适应与重传都无法挽回，占比 88.5% 的格点属此类。处置只能改架构：换位置、加中继、走中继回传。单网关加一个最优中继后覆盖升至 33.2%，中继有效但远不足以闭合。

**季节性静默。** 由能量与温度决定，冬季长静默、夏季恢复，处置是等待或加热。

现有工作普遍把两者当作同一件事，后果是：把永久失效算作可恢复故障会高估恢复策略的价值，把季节性静默算作随机丢包会低估所需的缓冲深度。

变动的时间尺度由三处决定，彼此相差三个数量级：空间维给出 11.5% 随时可通与 88.5% 永久不可通；时间维给出 6.38 h 的平均中断突发与 42 h 的 p99 尾部；能量维给出以月计的冬季静默。任何单一尺度的评测都会漏掉另两个。

**agent 的观测模型。** 上述过程是物理真值。agent 看到的是它的调用结果，而调用穿过同一条链路，因此观测是物理过程经一次有损、有延迟、可能重复的投影。agent 对实体 $e$ 的动作 $a$ 得到的观测取值于 {完成并回执, 未完成, 结果不可知}，其中"结果不可知"混合了三种物理原因：请求未达、实体已失效、回执丢失。**agent 无法在单次观测内区分这三者**，只能通过后续调用的时序模式逐步排除。这一投影是本文与"假设状态可观测"的既有工作的根本差别。

### 指标

| 指标 | 定义 | 说明 |
|---|---|---|
| 到报率 | 周期内应到达的采样包中最终到达的比例 | 按传感器与按时间分别统计，单一全局值会掩盖局部失效 |
| 到达时延分布 | 每包从生成到到达的时间，报分位数 | 均值被少数快包主导，监测关心尾部 |
| 能量预算余量 | 剩余能量相对越冬所需的比例 | 决定下一冬季是否存活 |
| 重复执行次数 | 同一逻辑命令被实际应用超过一次的次数 | 与任务正确性正交的执行正确性 |
| 零执行周期 | 应下发但最终未落地的命令数 | 与上一行方向相反，必须同时报 |

最后两行构成一对。只报其一会奖励错误行为：放弃执行可以压低重复率，重发可以压低零执行数。本文实测到 `verified_wrapper` 把重复减半的代价是 562 个周期完全未执行。

报告口径按三档时间分辨率分别给出，取自 Hochvogel 的实测做法：日均（当日至少 1 个测值即算有效）、时均、以及全部原始采样。该实测显示三档差异极大——日均可靠率 97.3–100%，时均裂缝计 96.7–99.4%，而激光测距仪只有 56–65%（每年被雪覆盖数月）。只报日均会把一个半数时间失效的传感器呈现为近乎满分。**M**

同域文献中不存在任务级可靠性的公认指标名。可靠性普遍写作链路级的 coverage / outage probability，或服务级的 availability / feasibility rate。本文的到报率与零执行周期属任务级指标，需在首次出现处给出定义式并论证其必要性。

## 五、方法：面向中断通信的远端操作运行时

### 执行歧义

系统里有一个 agent runtime，它通过无线链路调用远端通信实体。控制请求与执行结果穿过同一条可能中断的路径，没有可靠的带外确认通道。对一次有副作用的操作 $o$，agent 发出请求后等到超时，能确定的只有 $\text{response was not observed}$，推不出 $\text{effect was not executed}$。远端可能根本没收到请求，可能收到但执行失败，也可能已经执行而回执丢失。节点此后还可能掉线、恢复、重启，于是旧操作与新操作跨越多个连通期。

这把无线链路中断变成了一个**远端执行歧义**问题：通信故障开始影响控制操作的语义，而不只是影响分组投递概率。关键的新对象是

$$\text{physical execution state} \;\neq\; \text{runtime knowledge state}$$

### 三个正交维度

早先的实现把所有东西塞进一个 11 状态枚举，其中有明确的自相矛盾：`outcome_unknown` 同时出现在终态集合里和"未决"查询的返回里。四个不同维度的量被混为一谈——runtime 自己的生命周期、远端物理效果、agent 掌握的证据、实体的可达性。现在拆开。

```text
lifecycle    registered -> running -> stopping -> settled      （runtime 拥有）
outcome      unknown | applied | rejected | failed | superseded （远端效果）
observation  fresh | unknown | stale | unavailable             （agent 的证据）
```

旧状态各归其位：`timeout` 成为一个 wait event；`outcome_unknown` 表达为 `outcome=unknown`；`stale_result` 是 observation；`unavailable` 是实体观测；`recovering` 是恢复过程；`compensating` 是另一个 operation。与种类相关的具体事实进 `detail`，不构成新状态。

### 生命周期

agent 只产生一个逻辑动作，例如 `set_sampling_rate(node_17, 5min)`。从这一刻起可靠性不再由 agent 的推理负责，而由 runtime 接管。

**登记。** runtime 生成稳定的 `operation_id` 与单调递增的 `epoch`，写入 registry，然后才允许发送。顺序不能反：先发包后记账会留下一个窗口，协调者恰在此刻崩溃就会产生一个远端可能已执行、而本地完全不知道存在过的幽灵操作。

**发送。** 请求携带 `operation_id`、`entity_id`、`epoch`、`capability`、`arguments`。重试不产生新的逻辑操作，始终重发同一个 `operation_id + epoch`。

**远端接受。** 实体维护最小的持久元数据：`last_accepted_epoch` 与可选的 `operation_id → outcome` 回执。epoch 小于已接受值则拒绝，等于则返回此前记录的结果，大于则原子地应用效果、推进 epoch、记录回执。第三步的原子性是必需的：若应用效果与推进 epoch 不在同一个接受边界内，两者之间崩溃就会重新打开 epoch 本来要关闭的重复窗口。

### Timeout 语义

通用 agent 框架把 timeout 暴露成一个 tool error，由模型下一轮自己决定要不要重试。这个语义把"我方停止等待"和"远端没有执行"混为一谈。本文规定

$$\text{wait timeout} \;\neq\; \text{execution failure}$$

回执没回来时 `lifecycle = running`、`outcome = unknown`，操作继续留在 registry。timeout 只是协调者的一个本地观测事件，之后策略才能决定继续等、查询、重试、调和、放弃或补偿。

这条语义的物理依据是中断的时长。ChirpBox 实测的 p99 中断是 42 h，所以 `outcome_unknown` 可能横跨整个夜间。一个把超时当失败处理的运行时，会在每个夜里把大量实际已执行的操作当成未执行来处理。

### 调和与结算

实体恢复连接后，runtime 检查所有属于该实体、`outcome=unknown` 的操作，逐一做**限定范围的调和**：优先查 operation 级回执，退化到 epoch 比较。远端记录了该 `operation_id` 则 `applied`；远端 epoch 大于该操作的 epoch 则 `superseded`；远端 epoch 小于该操作的 epoch 则说明该写入从未成为当前值，同 epoch 重试是安全的；远端不可达则保持 unknown。

范围限定不是细节。问"这个实体上是否曾经出现过这个效果"会被更早的操作回答成"是"，于是策略停止重试一次根本没发生的写入。正确的问法是"操作 $o$ / epoch $e$ 是否生效"。

结算 first-wins：终态证据一旦按规则结算，迟到的分组只能成为 `late_evidence` 记录，不能改写操作真值。否则延迟到达的确认本身又会造成状态回滚。

### 边界与不变量

agent 只负责选择 capability 与逻辑动作，runtime 在动作之外包住登记、身份分配、epoch 分配、发送、等待、调和、重试许可与结算。这条边界让实验的因果变干净：固定相同的 LLM 轨迹与相同的动作序列，只替换 runtime。

协议正确性的论证强度受限于运行时的强制力度。若 runtime 静默接受一次乱序转换，关于正确性的论证前提就不成立。因此 runtime 自己维护每次操作的转换阶段并在非法时立即抛错：未登记即结算、未发送即调和、效果已确定后重发、未注册操作、重试改变身份，五条均抛 `Violation`。注意第四条与"结果未知时允许重发"不矛盾——`outcome=unknown` 的操作可以重发，这正是 fencing 起作用的前提；被禁止的是在效果已经确定之后再发。五条均已实测会抛出。

**三条由本轮复查补入的不变量。** 前五条管的是操作自己的状态转换，这三条管的是运行时与外部世界之间的顺序与许可。

*宣告排在证据之后。* 前五条的第一条要求"登记在派发之前"。它的对偶是：**在证据落盘之前，不得向平台或运维宣告某个效果已经生效。** 宣告带有外部后果——它写进工单、可能触发人工排查、改变运维决策。若宣告先于持久记录，进程在两者之间崩溃就留下一条对外的"已生效"陈述与一具空记录，此后无从判断该陈述真假；顺序反过来时，最坏结果是记录说已生效而无人被告知，可以由重放补上。形式化为 `announce(op) ⇒ durable(evidence(op))`，与前一条合起来给出完整规则：一切对外可观察的动作都排在持久记录之后。第六节"误报成功"这项业务指标测的是症状，这条规则是产生症状与否的原因。

*恢复重建的是知识，不是权限。* 从持久日志恢复出的操作处于**已知但不可派发**的状态，只有在重建到该实体的调和通道之后才重新获得派发权。理由是持久日志保存"我做过什么"，不保存"现在做还合不合适"：重启后的协调者对对端是否换过 epoch、本地记录的保留期窗口是否还有意义、上级任务是否已被取消都一无所知。把这两件事混进同一个状态，恢复就会自动产生一次未经授权的动作。由此可得一条可测差别——恢复后立即重发，与恢复后先重建授权再重发。两者的重复数预期都为零（由 C1/C2 兜住），差别应出现在调和读次数以及在节点断电、任务取消等场景下的越权副作用上。

*不派发无人能回收的工作。* 若运行时无法指出一条到该实体的调和通道，就不派发这条操作。这与第七节 7.1 的机会约束是同一件事的两面：下行机会是调和通道的物理前提，没有上行机会就没有下行窗口，也就没有调和通道。在永久遮挡的站点上（地形结果 88.5%），这条规则把操作从"永远重试"改为"一开始就拒绝并上报"。收益有两层：代价层面消掉一条随运行时长无界增长的调和负担，账目层面使平台的陈述变诚实——运维看到的是"该点位当前不可达、操作未执行"，而一条永远停留在在途状态的操作恰好是本项目要解决的那种执行歧义，只是方向反了过来。

### 远端契约的两个等级

协议对远端提出的要求分两级，二者对重复指标的贡献相同，但保护的性质不同。

**C1 持久 operation 回执。** 远端按 `operation_id` 记住已接受过的操作及其结果。它保证**同一 operation 的重复接受至多一次**。

**C2 单调 epoch fencing。** 远端维护 `last_accepted_epoch`，拒绝任何不大于它的 epoch。它除提供 C1 的效果外，还保证**旧 epoch 不能覆盖新 epoch**。

**契约要求部署方提供的是授权的身份空间，不是不可猜的身份。** 本文的 `fresh_id` 用可预测的世代前缀构造身份。远端按操作身份去重的同时校验该身份是否属于调用方，因此身份可猜与身份可冒用是两件事：边界在授权，不在不可猜测性。这一条决定了契约的部署门槛——它要求的是一个有归属的操作身份空间，而不是一个密码学随机源。

消融显示只留 C1 或只留 C2 都能把重复降为 0，但这一等价只在"重复执行"这一个指标上成立。C2 多保护的是过期重放：分区恢复、延迟到达或重连之后，一条旧命令重新出现时不能覆盖当前值。该性质在本文的故障注入下未产生可观测差异，因为它要求延迟重放的到达时间晚于一次更新，而当前模型中这类事件稀少。因此两个等级的差别由性质陈述给出，不由本轮数字给出。

协调者侧另有一项与远端等级无关的要求：**持久登记**。它不改变远端的能力，但决定重启后协调者是否还认得自己的操作。没有它时远端契约再强也无效，因为重发会带上新身份与新 epoch。

### 三条性质

三条性质建立在不同的假设上，逐条写明。

**P1 At-most-once re-acceptance。** 假设远端满足 C1 或 C2 任一。则对任意逻辑操作 $o$，其 epoch 被远端接受的次数至多一次。只能声称 at-most-once，不能声称 exactly-once：第一次请求从未到达时，效果可能根本不发生。

**P2 No stale overwrite。** 假设远端满足 C2，且协调者侧的 epoch 跨重启持久。则对 $e_j > e_i$，一旦 $o_j$ 被接受，任何迟到的 $o_i$ 都不能覆盖它。协调者侧的持久性是这条性质的必需条件：一个重启后叫不出原 epoch 的协调者只能发新 epoch，而新 epoch 必然更高，fencing 无从施加。

**P3 Eventual resolution under eventual reachability。** 假设实体最终保持可达、远端执行元数据未丢失、且协调者侧的登记跨重启持久。则未决操作经调和最终能落到 `applied | rejected | superseded | failed`。若远端元数据随其重启丢失，则不能保证解决。这条限制必须显式写出，因为它说明协议保证依赖远端持久化。

三条性质在 `code/runtime/operations.py` 中可执行验证，连同一条负面结果：客户端只复用幂等键而远端不认该键时，5 次重试全部生效；epoch fencing 下 5 次重试只被接受 1 次。远端配合是幂等性的前提，这一点属于方法陈述的一部分。

**范围限定的调和谓词**不计入贡献，降为实现细节。消融显示在有远端契约时它不承重（38.7% 对 38.7%），因为 fencing 已使重试幂等。它的价值取决于远端契约是否存在，这一条件性结论记在消融一节。

### 实验口径

主实验固定同一条决策轨迹，只替换执行 runtime。**所有协议消息都走同一条链路**：数据写入、验证读、调和读，以及每个请求的回复，都受同一链路状态约束、同样会丢失、同样计入空口。这一条是方法的前提，因此在这里由代码强制——没有任何一条读路径可以绕过链路直接取远端真值。

两种 workload 分别打分，因为它们对方法的偏好不同：

- **operation**：每条命令独立有意义（带版本的门限更新、告警确认、触发测量、看门狗刷新），其逻辑身份就是交付物。"这一条命令是否恰好执行一次"在这个 workload 下是正当要求。
- **state_setting**：目标配置循环变化（1 h → 10 min → 5 min → 1 h），一轮成功意味着目标状态在位。已经正确的配置无需再执行一次，因此在这个 workload 下按"目标状态是否在位"评分。
- **mutable_state**：单一连续的门限设定命令，写入字段是普通赋值。没有累加、没有集合，晚到的旧命令会真的把旧值放回去。它只用于陈旧覆盖实验，主表不使用。

只报第二种会偏向操作级协议，只报第一种会偏向状态验证，两个都报。

**两个 workload 的切分来自执行语义在真实系统里的两种固有形态，与实验是否方便无关。** 同一条交付通道上可以同时存在两类输出：一类是每次读取消费一段游标、每个字节只交付一次；另一类是幂等的、可重复读取、不消费游标。前者对应本文的 `operation`，后者对应 `state_setting`。这也解释了为什么 state-setting 上三种契约配置给出一致的 46.4%——在幂等语义下，执行层的区分能力天然退化，这是该语义的性质而非本文方法的失败。第三种的存在是因为前两种的命令负载里没有可被覆盖回退的字段：门限用 `max()` 累加、告警用集合添加，旧写入迟到不会改变状态。只统计"乱序生效"会把定序违规当成领域损害，因此覆盖实验单独用一个真实的普通赋值字段，并把两者分开计数。

环境口径：每个种子在跑任何 runtime 之前先建一次节点集与环境轨迹，轨迹给出每个 `(节点, 小时)` 的信道好/坏状态与供电状态，全部 runtime 索引同一张表。报文级抽样按 `(种子, 节点, 小时, 报文类型, 尝试序号, 逻辑操作身份)` 寻址，不从一条连续流里取。逻辑操作身份进入键是必需的：缺少它时同一节点、同一小时、同一报文类型、同一尝试序号下的不同操作会共用一枚抽样，把各自独立的任务绑成同生共死；带上它之后不同操作互不相关，而同一操作在不同 runtime 之间仍是配对抽样。`Link` 在缺少逻辑操作身份时直接抛错，这条约束由代码强制。这一条是必需的：各 runtime 发的报文数量相差数倍，共用连续流时多问两次就消费掉两个抽样、之后每一小时的天气都换了，比较会静默地变成三个不同信道的比较。

链路口径：上行在节点发射时计费，下行只在远端确实收到请求并应答时计费。请求没到、或被网络扣留时，远端没有收到任何东西，因此没有回复也没有下行空口。

延迟网络的注入口径：写入跨过链路后有概率被网络扣留若干小时后释放，扣留期间远端状态无变化、也没有回复可回。该注入作用于传输层，对全部被比较的配置同样生效，参数与结果见"时间乱序与陈旧覆盖"一节。

读写成本口径：报文长度统一为 38 B，不引入新的报文格式。`--read-cost-ratio` 只给读消息一个相对写入的**权重**，用于回答"如果远端要把状态放进回复里、读因此变贵，比较会怎样"。它作用于加权通信代价，不作用于物理空口：物理空口是实际发出的报文在信道上的占用时间，由跳数与扩频因子决定，不随这个权重变化。两个量在结果里分列，见"读写通信成本敏感性"一节。

统计口径：全部主结果使用 20 个种子。所有 runtime 在同一种子上共用节点集、环境轨迹与决策轨迹，因此它们之间是配对的，比较量取逐种子的差值而不是两个独立均值——在这条链路条件下，种子间方差占了总方差的大部分。置信区间用配对差值的 t 区间。计数型指标（重复、乱序、覆盖）除均值外逐种子检查，因为均值为 0 与"每个种子都是 0"不是同一个陈述。

### 协调者重启

协议的第一条规则是登记在发送之前，而这条规则只有在登记活得比进程久时才有意义。180 天，20 seed，每 72 h 重启一次协调者，全部配置跑在同一个支持 C1 + C2 的远端与同一条信道上，唯一差别是 runtime 如何对待身份。

身份能否由任务重算，决定了失效的形态。周期测量这类命令的身份完全由任务决定，任何一次重启都能重新算出同一个；临时处置这类命令的目标是在决策当时选定的，不落盘就不可复现。

| 命令类型 | 身份来源 | 恰好一次 | 重复应用 | 非请求副作用 |
|---|---|---:|---:|---:|
| 周期测量（可重算） | 每次重发新身份 | 22.5% | **595.2** | 0 |
| 周期测量（可重算） | 重算同一身份 | 32.8% | 0 | 0 |
| 周期测量（可重算） | 持久日志 | 32.8% | 0 | 0 |
| 临时处置（不可重算） | 每次重发新身份 | 26.3% | 0 | **968** |
| 临时处置（不可重算） | 重算同一身份 | 26.3% | 0 | **968** |
| 临时处置（不可重算） | 持久日志 | 32.7% | 0 | 0 |

**两种失效互补，只有日志同时避开它们。** 身份可重算时，忘了自己在途的协调者会重算出同一个名字并再发一次，第二次效果照样落地，重复 595.2 次；fencing 在这里拦不住，因为两次携带的是同一个身份、语义上也确实是同一次操作的两次尝试。身份不可重算时，重发的新身份是一条**不同的**命令，原命令永远交不出去，同时落地 968 次任务没要求的动作——在按任务意图记分的表上，它既不显示为重复，也不必然显示为失败，只有单独统计越权副作用才看得见。

**"重算同一身份"只在前一类命令上有效。** 它能复现任务已经确定的身份，复现不了决策当时抽出的那个选择；在后一类命令上它与"每次新身份"给出完全相同的数字，并同样产生 968 次越权副作用。

**在这三个机制里，持久日志是唯一同时覆盖两类的**，两类都是 32.7%–32.8%、零重复零越权。更一般的说法是：身份不可重算的动作需要某个持久来源保存它的身份与决策上下文，外部持久队列、上游事件日志、持久任务 ID 都能承担这个角色，日志与配套的决策存储是本文实现这条连续性的机制。

身份连续性与决策上下文是两件事。一个失忆的协调者即使能重建出身份字符串，也重建不出那一刻选定的告警对象，而 payload 里装着那个对象。因此 adhoc 分支的恢复同时读回身份与选择，两者都由同一份追加日志保存：`DurableDecisionStore` 把 `(地址 → 选择)` 写进注册表用的同一个 `Journal`，重启后由日志重放，实验脚本里不再有任何跨重启存活的局部映射。

**日志臂的代价形状是"少写多问"，且总量可控。** 写入 8,890 次，低于两臂的 9,536 次；调和读 3,130 次，空口 1.41 h 对 1.05 h。记得哪些已经完成，就不必把它们再写一遍，代价转移到重启后的一次确认上。

这条成本只有在两处计量正确时才成立。恢复出的操作在回执确认后必须结算回登记表，否则它会保持未决、在之后每一次重启被重新调和一次，代价随运行时长无界增长——修正前这一项是 157,071 次调和读与 42 h 空口。重启时的调和同样以任务的未决窗口为界，否则永久遮挡节点产生的每一个历史操作都会在每个重启周期被重试一次。

### 时间乱序与陈旧覆盖

写入跨过链路不等于立即生效。本组使用 mutable_state workload：单一连续的门限设定命令，字段是普通赋值，没有累加也没有集合。180 天，20 seed，命令间隔 12 h，30% 的写入被网络扣留 1–36 h 后释放。扣留时长必须能跨过命令间隔，乱序才可能存在，因此扣留上界取到命令间隔的两到三倍；扣留是传输层属性，对全部配置一视同仁。

"乱序"统计一次写入的 epoch 低于该远端已经生效过的最高 epoch 却仍然生效；"陈旧覆盖"要求一个真正会被覆盖回退的字段，即该字段当前值来自更新的写入，而这条旧命令把它改了回去。两者分开计数：乱序是协议层的定序违规，覆盖是领域层的实际损害。审计脚本用一个最小序列直接验证这一点——先让 epoch 11 生效，再放行 epoch 10，状态确实被改回去且覆盖计一；换成 fencing 则被拒、状态不变。

| 配置 | 远端契约 | 恰好一次 | 重复 | 乱序 | **陈旧覆盖** |
|---|---|---:|---:|---:|---:|
| 本文 | C1 + C2 | 32.6% | 0 | **0** | **0** |
| 只留 C1（回执） | 回执 | 34.1% | 0 | 89 | **88** |
| 只留 C2（fencing） | fencing | 32.6% | 0 | **0** | **0** |
| 去掉稳定写入身份 | 两者 | 32.6% | 0 | 0 | 0 |
| Verified Tool Calls，幂等 sink | 回执 | 28.5% | **0** | 140 | **138** |
| Verified Tool Calls | 无 | 25.0% | **200.4** | 249 | 229 |
| Retry-on-uncertainty | 无 | 19.5% | 1154.2 | 508 | 444 |
| 无契约的本文 runtime | 无 | 19.5% | 1154.2 | 508 | 444 |
| One-shot execution | 无 | 26.4% | 0 | 181 | 176 |

**这是 C2 单独承担的一条，P1 上看不到。** 在重复指标上 C1 与 C2 冗余（见协议消融一节），但陈旧覆盖只有 C2 能压到 0：只留 C1 时旧操作覆盖新值 88 次，配对差值相对本文 −87.75，区间 [−103.0, −72.5]，20 个种子全部同向；两个 arm 发出的报文逐条相同，空口差为零，所以这不是消息量差异造成的。回执去重按操作身份判别，而这里晚到的两条写入分属**两个不同的操作**，去重对它们本就无从下手——新旧之分只存在于 epoch。零值逐种子检查：本文的重复、乱序、覆盖三项在全部 20 个种子上都是 0；只留 C1 的覆盖在 20 个种子上全部非零，最大 145。

**给 Verified 配上幂等 sink，重复归零，陈旧覆盖留下来。** 第五行是同一个已发表方法，只是远端真的认它按论文生成的那个确定性幂等键。重复从 200.4 降到 0，陈旧覆盖仍有 138 次，配对差值相对本文 −137.5，区间 [−155.0, −120.0]，20 个种子全部同向。于是对照成为两行：`Verified + C1` 是零重复、138 次覆盖；`本文 + C2` 是零重复、零覆盖。C2 的增量因此不再能被归因于"没给对照它自己要求的支持"。

**代价在这一节是反向的。** 本文的恰好一次率比 `Verified + 幂等 sink` 高 4.1 个百分点（区间 [3.2, 5.0]，20 个种子全部同向），空口也更高，差值 +2178 秒，区间 [1997, 2359]。契约不是免费的，它买的是覆盖为零。

**Verified Tool Calls 在没有幂等 sink 时还失去它的零重复。** 无延迟时它与本文同为 0 重复；写入一旦会被扣留，出现 200.4 次重复。它的验证步骤读的是当前状态，而一个仍在链路上、尚未生效的写入在当前状态里不存在，验证据此判定"未生效"并重发，被扣住的那份随后落地。这与调和谓词的范围问题同源：**读当前状态得到的答案，对在途写入不构成证据。**

**去掉稳定写入身份在这组里不承重**，fencing 已经按 epoch 拒绝了迟到的旧写入。稳定的写入身份承重的位置是没有 fencing 时，即协议消融一节里的情形。

### 读写通信成本敏感性

报文长度不变，仍是 38 B。这一节只给读消息一个相对写入的**权重**，回答"如果远端要把状态放进回复里、读因此变贵，这个比较会怎样"。mutable_state workload，不注入延迟，20 seed，只比较 Verified Tool Calls 与本文。

两个量在这里必须分开，否则会读成对无线电的断言：

- **物理空口**：实际发出的报文在信道上的占用时间，只由报文跳数与扩频因子决定。它与权重无关——固定 38 B 的帧在固定 SF 下占用的时间，不因为实验者认为读"值多少"而改变。
- **加权通信代价**：按写等价计数的通信量，读的每一跳乘上该权重。这是权重唯一作用的量。

预算 20 下物理空口是 Verified 20.2 h、本文 20.3 h，在三个权重下**逐位不变**；预算 8 是 8.0 h 与 8.7 h，预算 3 是 2.5 h 与 3.6 h，同样不随权重变化。随权重变化的只有加权代价。

| 读/写权重 | 预算 | Verified 恰好一次 | Verified 覆盖 | 本文恰好一次 | 本文覆盖 | Verified 加权代价 | 本文加权代价 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 0.25 | 3 | 28.4% | 0 | 34.0% | 0 | 16,615 | 32,146 |
| 0.25 | 8 | 36.2% | 0 | 40.7% | 0 | 28,988 | 69,829 |
| 0.25 | 20 | 40.6% | **556** | 44.2% | **0** | 52,747 | 149,012 |
| 0.50 | 3 | 28.4% | 0 | 34.0% | 0 | 19,238 | 32,743 |
| 0.50 | 8 | 36.2% | 0 | 40.7% | 0 | 42,183 | 70,572 |
| 0.50 | 20 | 40.6% | **556** | 44.2% | **0** | 87,322 | 149,849 |
| 1.00 | 3 | 28.4% | 0 | 34.0% | 0 | 24,484 | 33,938 |
| 1.00 | 8 | 36.2% | 0 | 40.7% | 0 | 68,575 | 72,058 |
| 1.00 | 20 | 40.6% | **556** | 44.2% | **0** | 156,471 | 151,522 |

**加权代价的结论完全取决于读值多少。** 读只值四分之一次写时，Verified 在预算 20 下是本文的 0.35 倍，本文贵近三倍；读与写等价时两者持平，156,471 对 151,522，本文略低。本文的加权代价几乎不随权重移动（149,012 到 151,522），因为它几乎不发读；Verified 的加权代价随权重近线性上升。

**交付率与覆盖数完全不随权重变化。** 权重只进入计费，不进入决策也不进入信道，因此同一预算下三档权重的交付率与覆盖数逐位相同。这条是可以用来做自检的：如果某张表里交付率随权重动了，说明权重被误用到了别处。

**覆盖数与权重无关，与预算有关。** Verified 在预算 20 下无论读多便宜都是 556 次覆盖，本文在任何一格里都是 0。调低读的价格能让 Verified 变便宜，不能让它的覆盖消失。

这里的覆盖来自**重试重叠**，不来自延迟注入：本组 `--stale-p` 为 0，写入不会被网络扣留。预算一大，一个够不着的旧操作会被持续重试到保留期结束，期间同一节点的新操作已经落地，旧写入后到就落在它后面。mutable_state 的字段是普通赋值，因此这个乱序会真实改回领域状态，被计为覆盖。operation workload 没有可被覆盖回退的字段，同一现象在那里的表现只是定序违规，见"等预算对照"一节的两层区分。

### 架构与协议的 2×2

|  | 无中继 | 有中继 |
|---|---|---|
| Retry-on-uncertainty | 24.8% / 1316.3 | 26.6% / 1558.5 |
| 本文 runtime | 34.0% / 0 | 37.3% / 0 |

格式为恰好一次率与重复次数，180 天，20 seed，operation workload。中继覆盖 24.4% 的遮挡点，该比例取自贪心中继选址的结果。

**中继抬高了双方的交付率，但只抬高了一方的重复。** 恰好一次率各自上升约 2 个百分点，代价是中继给 retry-on-uncertainty 增加了 242 次重复。store-and-forward 把歧义搬走而没有消除：命令进了中继缓冲后协调者不知道它有没有投出去，多出一个投递状态观测不到的参与方，而中继到节点那一跳同样会丢回执。对本文 runtime 而言这个参与方由契约覆盖，重复仍是 0。

**中继可用度越高，retry 的重复越多。** 可用度 0.25 到 1.0 之间，retry 的重复从 1342.3 升到 1558.5，恰好一次率基本不动（26.5% 到 26.6%）；本文 runtime 从 35.9% 升到 37.3%，重复恒为 0。中继是架构参数、不是协议替代品。

中继不是 38 B 周期上报的终端节点，其面板、电池、占空比与加热条件属另一设备等级，用节点能量模型跑它会编造没有的数字。因此中继可用度是架构参数，本组结果是"中继可用上界"研究。

中继的两跳都不走被遮挡节点自己到网关那条被阻挡的路径，否则整组比较会退化成同一个数字的两次拷贝。审计脚本对此单独设了一条检查：永久遮挡节点的直连从不成功，同一节点经中继可以到达，而中继跳仍然要求节点有电。

### 7.1 下行机会约束缺失

**现状**：`Link.request()` 只查询节点当前的信道状态（`node["good"]` 与 `node["alive"]`），下行成功率与节点是否上行无关。`disruption_env.py::call` 与 `mission_sim.py` 的命令路径同样是独立的逐轮伯努利。

**标准规定它们相关**：

- LoRaWAN Class A 的下行只能发生在一次上行之后的 RX1 / RX2 窗口内，节点回到休眠后没有接收窗口，因此**下行机会数 ≤ 上行次数**。
- 3GPP TS 23.682 V19.3.0 cl 4.5.4：PSM 终端 "is not immediately reachable for mobile terminating services"，只有在 connected mode 与随后的 Active Time（T3324）内可达。对野外设备下发只有三条路：等下一个 periodic TAU（T3412 最长可达数百天）、等它因自身上行醒来、或用网络侧缓存（MT NIDD / device trigger / reachability monitoring）在终端变可达的瞬间投递。
- OMA LwM2M 的 Queue Mode 正是为这一约束设计的：服务器排队，等设备再次可达时投递。

**实测后果**。机会率取「节点存活且信道良好」的比例，这是当前模型能给出的最宽松上界：

| 量 | 每节点每小时 |
|---|---:|
| 节点存活 | 0.681 |
| 存活且信道良好 = 机会上界 | **0.362** |
| 等预算对照 budget 3 实际需要 | 0.44（超 1.2 倍） |
| budget 8 实际需要 | 0.97（超 2.7 倍） |
| budget 20 实际需要 | 2.12（超 5.9 倍） |

若节点上报周期是 6 h 而非 1 h，机会上界降到 0.060，三档分别超 7.3、16.2、35.3 倍。

**结论**：等预算对照的三档全部超出机会上界，其中 budget 20 超近六倍。**"预算 20 下 Verified Tool Calls 追平、本文只剩 0.58 个百分点"这条核心负结果，测在一个 MAC 供不起的运行点上。** budget 3 与 budget 8 的超额倍数较小，但同样越界，不能直接引用。

**修复方式**：把控制面机会显式建模为「上行事件率 × 下行成功率」，节点的上行节奏给出机会窗口，协调者的下行请求受该上限约束。这不只是补一个上限：它引入一个此前不存在的资源轴——**每次机会推进了多少**。当前预算 20 下 Verified 花 133,227 次机会在询问，本文花 2,151 次在询问、其余用于写入，两者的机会总数几乎相同（147,505 对 146,266），区别在用途。

**待定参数**：一次上行给出几个下行机会。Class A 约 1，PSM 的 T3324 窗口内可承载多个。这个比值直接决定结果形状，需先定口径再跑。

### 7.1b 两处能量结论必须重述（P0.1 修正后新增）

P0.1 修正 `energy.py` 时暴露出两件事，都会改变现有表述。

**93.7% 与运行时用的模型不是同一个测量。** `code/physics/energy_model.py` 自包含，有自己的按天积分循环，不导入 `energy.py`。README 引用的 93.7% 出自它；而运行时（`disruption_env.py` 与 `method_comparison.py`）用的是 `energy.py`，修正前在同一站点同一电池同一负载下实测 **92.9%**，修正后 **96.4%**。两个数字此前被当作同一件事并列，需要分开表述：`energy_model.py` 的 93.7% 是其日模型的输出，`energy.py` 的 96.4% 是逐小时模型的输出。

**修正引入了一个无出处的假定，而结论对它敏感。** 加热要生效必须有昼夜温差，因此新增了 `DIURNAL_AMPLITUDE_C = 6.0`（最冷约 03:00、最暖约 15:00）。仓库内没有这个量的来源，它是 A 层假设。敏感性：0/3/6 K 均得 96.4%，9 K 得 92.4%，12 K 得 71.4%；温度基线偏移 +9 ℃ 时 100 W 的停电率降到 60.9%，+12 ℃ 时降到 50.8%。因此"充电门限而非能量禀赋是约束"这一结论在幅度 0–9 K 区间内稳定，超出该区间需重新论证。

**同站点上加热是决定性的杠杆。** 该站点年均温 −19.5 ℃，加上 ±6 K 昼夜项后最暖的夏季小时约 +3 ℃，仍低于 LiFePO4 的 +5 ℃ 门限，因此未加热节点全年发电为零，面板从 30 W 到 200 W 一律无效。同一个 100 W 节点加上 8 W 加热盒后可产 280,907 Wh/年，停电率降到 0。这条比"加大太阳能板无效"更可用，因为它同时给出了替代方案。

### 7.2 `energy.py` 的发电量计算（已修正）

```

hourly_gen = self._generation_wh(...) / max(self._daylight_h(...), 1e-6)   # 又除回去 → 日照时段功率
```

### 7.3 多实体集合未实例化

§一 声明的底层资源是"通感算一体化的多实体集合，包含 LoRa、NB-IoT、CPE、UAV、HAPS、卫星与微波"，§二 用三张表定义该集合。**实测核查：`disruption_env.py` 与 `mission_sim.py` 中上述实体关键词命中数为 0。** `Node` 数据类只有 14 个字段，是一个 LoRa 传感节点加可选中继与网关。§二 的三张表目前是装饰。

**比声明与实现不符更要紧的一点：核心结构假设目前还是一条公理。** 本项目的命题是"agent 的观测通道与它的控制通道是同一条，'实体已静默'与'我的查询在回程丢了'在观测上不可区分"。而真实部署里备用蜂窝链路、小数据卫星回传是常规手段，它们就是带外通道。审稿人只要问一句"部署里既然有备用链路，带外通道不就在那儿吗"，这条假设就守不住。

**修复方式**：把多实体集合真正实例化，让 agent 必须在 N 条候选链路之间自己发现哪条可用。此时歧义不再是假设——agent 分不清某条链路是断了、没电了、还是自己的查询在回程丢了。**§五 的三维观测语义（fresh / unknown / stale / unavailable）正好是描述这件事的词汇表。** 一旦补上，"带外通道"这个攻击面自动闭合，§二 的三张表也从装饰变成被测对象。

### 7.4 主实验没有 agent

§六 实验口径自述"主实验固定同一条决策轨迹，只替换执行 runtime"。`agent_react.py` 是 scaffold（`MockBackend` 与待接的 backend），其结果读数为随机占位。一篇研究 agent runtime 的论文主实验里没有 agent，是审稿人最容易动手的一处。

补接成本很低（两个 backend 已就绪），但**顺序上应当排在昂贵的实证工作之前**：若接上之后结论不保持，叙事要变，那时更贵的工作可能已经白做。最便宜的证伪实验应当排在最贵的工作前面。

### 7.5 必读文献缺口（已补齐三项，一项待订阅）

**α³-Bench（[arXiv 2601.03281](https://arxiv.org/abs/2601.03281)）——阻塞 Gap 1 的那一问有答案了，答案对我们有利。** 该基准的 6G 网络状态是 `n_t = (slice_t, lat_t, jit_t, loss_t, thr_t, edge_t)`，其中 `loss_t` 是"以百分比表示的丢包率"，**它是 agent 观测状态里的一个分量**，不是作用在工具调用执行上的注入故障。工具层做的是 MCP 工具调用与 A2A 协调，量的是"工具使用一致性"；丢包进入的是推理上下文与评分维度（Network Robustness，退化条件下该项下降 30–40%），而它的重试机制针对的是**生成**失败（schema 校验不过），不是网络失败。

**因此 Gap 1 可以落笔**：现有 agent 基准把网络退化建模成**agent 需要观测并据以得分的条件**，而不是**agent 必须消解的执行结果**。"实体已静默"与"我的查询在回程丢了"在观测上不可区分，这件事没有覆盖。这一条此前挂着不能写，现在能写了。

**Atomix（[arXiv 2602.14849](https://arxiv.org/abs/2602.14849)）A.2 是与本文最接近的既有工作，必须正面引用。** 原文：故障按伯努利概率逐 tool call 注入，在工具边界抛异常；Tx-Full 与 CR 中止事务并**用新 epoch 重试**；而 **No-Tx"建模丢失的响应：动作可能已经生效，但调用方看到的是错误，对应现实的超时或丢失的确认"**。这正是本文命题的那条歧义。

差别在消解方式：Atomix 走事务中止与回滚，重试换新 epoch；本文保持**同一个逻辑身份**不变，靠**单调 epoch 的远端 fencing** 让陈旧重发被拒绝而不是覆盖。§7.23 的公平 CAS 基线在同一张表里给出了这两条路线的可比读数。与之配套的反面论据是 *Rollback Is Not Undo*（INFOCOM 2026，DOI `10.1109/INFOCOM59046.2026.11571400`），**需机构订阅，尚未取得全文**，这是本节仍缺的一项。

**AgentChaos（[arXiv 2608.06790](https://arxiv.org/abs/2608.06790)）给出了本文一条实现规则的先例。** 它在 LLM API 层拦截并改写响应，定义 crash / omission / value 三类故障，作用于 content 与 tool call 字段；**并且逐条验证故障是否真的被触发，把未触发的任务过滤掉，以免低估故障影响**。这与 §7.18 第四节独立得到的结论是同一条：*故障事件非空不等于故障影响了待测动作*。本轮为此把按动作的故障改为按真实动作武装，此处有可引的先例。

**AgentDisruptBench（[HuggingFace `kavirubc/AgentDisruptBench`](https://huggingface.co/datasets/kavirubc/AgentDisruptBench)，MIT，100 任务 / 4 领域）的 20 类干扰分类法加强了 Gap 1，而不是削弱它。** 它的四类干扰是：

| 类别 | 类型 |
|---|---|
| Timing | `timeout`、`latency` |
| HTTP Status | `http_429`、`http_401`、`http_403`、`http_500`、`http_502`、`http_503` |
| Response Content | `malformed_json`、`truncated`、`null_response`、`missing_fields`、`type_mismatch`、`schema_drift`、`wrong_data` |
| Behavioral | `intermittent`、`flapping`、`quota_exhausted`、`auth_expiry`、`cascading` |

**二十类全部是"工具调用接口收到了什么坏响应"**，其主指标 `R(k, ε, λ)` 是在重复种子 k、任务措辞变体 ε、故障配置 λ 三个方向上的**通过率曲面**。它衡量的是 agent 对坏响应的**鲁棒性**，而不是**执行结果的不确定性**：没有一类对应"调用可能已经生效，但调用方看到的是失败"。这与 α³-Bench 的结论一致，Gap 1 在它身上同样成立。它的 20 类对照表可用于 §9 第⑥项的故障类型讨论——那是一张**工具调用接口**的分类法，与本文的**链路与生命周期**分类法（请求未达 / 确认丢失 / 旧命令迟到 / 协调者重启 / 端侧重启 / 仅回传中断）互为补充而非重复。

**剩余缺口只有一项。** *Rollback Is Not Undo*（INFOCOM 2026，DOI `10.1109/INFOCOM59046.2026.11571400`）需机构订阅，尚未取得全文。

**引用纪律。** 上述四项的取用只建立在**已读到的原文段落**上；未取得全文的条目（*Rollback Is Not Undo*、AgentDisruptBench）不得据传闻转述。α³-Bench 的结论来自其网络状态定义与指标描述，不是对其代码的复核。

### 7.6 待补的强基线与业务指标

**强基线。** 设备离线管理不是 agent 出现之后才有的问题，以下三条必须进入对照：

- **版本化 desired / reported 状态调和**（AWS Device Shadow 一类）。它按版本丢弃乱序旧更新，语义上就是本文的 C2，**在配置类负载上与本文是同一个方法的不同命名**。它诚实地界定了本文的适用范围：状态对能表达配置，表达不了一次性动作（触发采集、告警确认、补传）。§六 state-setting 一节三个契约配置给出逐位相同的 46.4%，正是这条边界在配置侧的测量值，应当按这个身份引用，而不是当作弱点。
- **队列化接触窗口交付**（LwM2M Queue Mode 思路）。若未运行真实协议栈，应称"语义实现"，不得命名为完整 LwM2M 复现。
- **本地规则 + 缓存补传**，用于回答 agent 编排本身是否必要。

**精确版本 fencing** 是第四条，但它与前三条的定位不同——它是一个**比本文更严的契约**（拒绝更旧的写入之外，还拒绝版本未知的写入者），代价是每次写之前先读一次版本。因此单列在 7.9.2，与游标恢复臂一起跑。

**业务指标。** 现有计数（重复、乱序、覆盖）需要换算成业务损害，其中四项可由已有状态导出，不需要新负载：

| 指标 | 算法 | 回答 |
|---|---|---|
| 配置错配时长 | 对配置时间线积分"实际 ≠ 期望"的小时数，取代当前的轮末采样 | 错误配置持续多久 |
| 关键观测空窗 | 由实际速率与期望速率算漏采量 | 风险时段漏掉多少观测 |
| 误报成功 | 协调者结算为已生效、而结算时该值并未生效或被随后覆盖的次数 | 平台告诉运维"已更新"而实际没有 |
| 平台知晓 vs 实际生效时延 | 由 §五 的 observation 维度直接给出 | 平台以为的与真实发生的差多少 |

第三项落在本文三维语义的 `observation` 维度上，是现有对照都不具备的一栏。它的机制是 7.7.1 的宣告顺序规则：把"宣告"排在"证据落盘"之后，误报成功在结构上就无法产生。

### 7.7 待补的方法表述（已完成）

以下五条是复查方法本身时发现的表述缺口。它们不改变任何数字，但改变方法在审稿人眼里的分量。**五条均已写入 §五 与 §六：** 7.7.1–7.7.3 作为三条新不变量补在"边界与不变量"之后，7.7.5 补在"远端契约的两个等级"，7.7.4 补在 §六 实验口径。以下保留原设计说明以备复查。

#### 7.7.1 宣告顺序：先落盘，再宣告

现有第一条不变量是"登记在派发之前"。它缺一条对偶：

> **在证据落盘之前，不得向平台或运维宣告某个效果已经生效。**

宣告是有外部后果的动作：它写进工单、可能触发人工排查、改变运维决策。若宣告发生在持久记录之前，进程在两者之间崩溃，就会留下一条对外的"已生效"陈述与一具空记录，而此后没有任何办法判断该陈述真假。顺序反过来时，崩溃的最坏结果是记录说已生效、但没有人被告知，这可以通过重放补上。

形式化为 `announce(op) ⇒ durable(evidence(op))`，与现有的 `dispatch(op) ⇒ durable(register(op))` 合起来给出完整规则：**一切对外可观察的动作都排在持久记录之后。**

这条同时是 7.6 表里"误报成功"指标的机制。那项指标测的是症状，这条规则是产生症状与否的原因。

#### 7.7.2 恢复恢复的是知识，不是权限

现有 `reconcile-before-dispatch` 已经蕴含这层意思，但没有说出来。准确表述是：从持久日志恢复出的操作处于**已知但不可派发**的状态；只有在重建到该实体的调和通道之后，它才重新获得派发权。

理由是持久日志保存的是"我做过什么"，它不保存"现在做还合不合适"。重启后协调者对下列事实一无所知：对端是否已经换过 epoch、本地记录的保留期窗口是否还有意义、上级任务是否在此期间被取消。把这些混进同一个状态里，恢复就会自动产生一次未经授权的动作。

由此可得一条可测差别：**恢复后立即重发，与恢复后先重建授权再重发。** 前一者是当前 journal arm 的行为。两者的重复数预期都为零（由 C1/C2 兜住），差别应出现在调和读次数，以及在节点断电、任务取消等场景下的越权副作用上。若该差别确实存在，它是一条独立于"记得 vs 不记得"的机制结论。

#### 7.7.3 准入控制：不派发无人能回收的工作

当前实现里，日志臂会对永久遮挡的节点无限调和（修正前 157,071 次调和读、42 h 空口），当时的处理是加保留期窗口。更根本的规则是：

> **若运行时无法指出一条到该实体的调和通道，就不派发这条操作。**

这条与 7.1 是同一件事的两面：下行机会是调和通道的物理前提，没有上行机会就没有下行窗口，也就没有调和通道。把 7.1 的资源上限与这里的准入判据合起来，永久遮挡点位（88.5%）产生的操作从"永远重试"变成"一开始就拒绝并上报"。

收益有两层。代价层面，它消掉一条随运行时长无界增长的调和负担。账目层面，它使平台的陈述变诚实——运维看到的是"该点位当前不可达、操作未执行"，而不是一条永远停留在在途状态的操作。后者正是本项目要解决的执行歧义的一个镜像：歧义的方向反了过来——从「无法确知效果是否发生」变成「明知无法执行却仍登记为在执行中」。

实现上，准入判据需要输入一个"到该实体是否存在调和通道"的判定。在 7.1 的机会模型下，这个判定可以显式定义为"该实体在保留期内是否存在过至少一次上行机会"。

#### 7.7.4 两种消费语义是系统固有的类别

作业输出存在两类语义：流式输出每次读取消费一段游标、每个字节只交付一次；终结输出是幂等的、可重复读取、不消费游标。这与本文的 `operation` 与 `state_setting` 两个 workload 切在同一条线上。

这一点应当写进 §六 实验口径：**两个 workload 的设立来自执行语义在真实系统里的两种固有形态，与实验是否方便无关。** 它同时解释了为什么 state-setting 上三种契约配置给出一致的 46.4%——幂等语义下执行层的区分能力天然退化，这不是本文方法的失败，是该语义的性质。

#### 7.7.5 身份的可猜测性与安全性无关

`fresh_id` 使用可预测的世代前缀构造身份。若被质疑身份可被伪造，回答是：**边界是授权，不是不可猜测性。** 远端按操作身份去重的同时校验该身份是否属于调用方；身份可猜与身份可冒用是两件事。这一条应与 §五 的远端契约一节合并说明，因为它决定了契约要求部署方提供的是"授权的身份空间"而非"随机不可猜的身份"。

### 7.8 持久日志的健壮性（已完成）

复查 `Journal` 与 `recover()` 时发现三处缺口。它们不影响任何现有数字，但如果日志要承担"跨进程生命周期保存执行连续性"这个角色，三处都必须补。**三条均已实现，回归测试 `code/experiments/test_journal_schema.py`（18 项）通过。**

#### 7.8.1 条目缺 schema 版本号

`Journal.record()` 写入的是 `{"kind": kind, **fields}`，`recover()` 对不认识的 `kind` **静默跳过**。这意味着一处载荷 schema 改动会静默地错放旧日志：不报错，只给出错误的恢复结果。

待补：每条持久变更携带 schema 版本，未知版本**显式失败**。宁可拒绝恢复并要求人工介入，也不要静默产出一个看似正常的状态。这是持久执行系统里的一条通则——**恢复失败必须是响亮的，因为它之后的所有判断都建立在它之上。**

#### 7.8.2 字段集未校验

恢复时应按 `kind` 做精确字段集校验，字段多于或少于预期即判为不可信。这条挡的是最常见的一类改动：写入端加了一个字段、读取端不知道它存在，于是新写旧读产生一个语义上错误的操作。精确校验把这类改动从静默错误变成启动失败。

#### 7.8.3 两类条目共用一条日志

决策存储与操作日志写在同一个 `Journal` 里，条目交织。两类条目的 schema 版本分别管理：`register` / `dispatched` / `observe` / `settle` 属注册表族，`decision` 属决策族，各自带版本号。决策条目的演化节奏与操作条目无关，共用一个版本号会迫使两者同步升级。

#### 7.8.4 实现后的行为

写入侧在追加时即校验 kind 与字段集，不合法的条目根本进不了日志。重放侧在校验整条日志之后才构造状态，任何一条不符即拒绝恢复。两者都抛 `JournalError`。

测试覆盖四类拒收：未知 kind、版本不符、多字段（写入侧新增而读取侧不认识）、缺字段。第四类是实践中最要紧的一类——写入侧加一个字段会产生一个看起来完全正常的操作，事后无从察觉。

### 7.9 待补的对照臂（需要跑）

#### 7.9.1 游标恢复臂 `journal_cursor`

当前日志臂的恢复方式是**全量重放加幂等去重**：不丢任何在途操作，代价是对每个未决操作重新调和一次（本轮 3,130 次调和读，空口 1.41 h 对无日志臂的 1.05 h）。

另一条路是**从最后一条持久确认的游标开始重放**，并接受"崩溃时刻在途的操作可能丢失"。代价有界，代价是可能漏。

这两条落在同一条轴上：**持久化的粒度**。预期游标恢复的调和读大幅下降、重复仍为零，而少数在途操作会从"尚未完成"变为"从未发生"，表现为零次率上升。

实现要点：**游标只标记"已提交给远端"，不标记"远端已确认"。** 这两个必须分开，否则游标会退化成第二条不可靠的回执通道，而它恰恰是为了不依赖回执才被引入的。游标状态本身也要持久，且它的丢失必须退化到安全方向——重放得更多，而不是更少。

这一臂值得单独报一行，因为它把"持久化到什么粒度"从设计直觉变成一个可比的量。

#### 7.9.2 精确版本 fencing 基线

当前 C2 的规则是单调 epoch、拒绝更旧。另一条在真实系统里常用的规则是乐观并发：**写入者必须持有当前版本号，版本不符则拒绝。** 它比 C2 更严——拒绝更旧的写入之外，还拒绝**版本未知**的写入者。

代价是每次写之前要先读一次当前版本。**在 7.1 的机会约束下这不是小代价**：它把"一次写占一次下行机会"变成"一次读加一次写占两次"。若机会成为瓶颈，这条基线的表现会直接反映机会约束的强度。

它同时是一条更保守的正确性基线。若它在本项目全部失效注入下都给出零覆盖，那么"零覆盖"本身就不再构成增量，增量只能来自机会消耗与恢复能力。**这个结果无论倒向哪边都有信息量**，因此值得独立于其他基线单列。

**三条在实现中发现的机制，值得进入正文。**

控制通道容量取决于数据 profile，而 profile 又取决于控制是否成功。这是自举的：节点切到加密 profile 之前只有常态的每小时一次上行，下发的配置命令只能等那一次机会。oracle 在 12 小时风险窗内仍有约 120 节点小时的配置错配，就是这个延迟的直接读数。

上行的分包必须随积压自适应。批量上限取成等于产生速率时，任一次上传失败都会造成队头阻塞且缓冲无界增长——这是回归测试抓出来的一处参数自相矛盾，不是实现细节。

**一处跨模块命名漂移被端到端运行抓出。** 需求侧写 `displacement`、节点侧写 `deformation`，评分器匹配不到任何样本，覆盖率恒为 0 且不报错。已加规范映射，并在公平性审计中断言该映射对两套词表都是满射。

**注入确实发生了，这一点先排除。** 各类在 72 小时内产生 1–6 次注入（请求未达 6 次 / 确认丢失 3 次 / 旧命令迟到 4 次 / 协调者重启 1 次 / 端侧重启 2 次 / 仅回传中断 1 次），事件列表非空、时刻落在运行内、节点归属正确。空结果不是坏掉的注入器造成的。

**因此故障排得稀是这套参数的性质，而这套参数是 A 层诊断值。** 把这个结论写成"本文 runtime 更鲁棒"需要靠调高故障强度制造差距，那正是本项目一直在避免的方向。诚实的读法是：**在这套诊断故障下，成熟的配置管理做法已经足够，本文的执行层没有可测的增量。**

**D8 的闸门因此落在"调整方向"那一支。** 闸门原文是三条出路：继续主稿（业务收益稳定且值得成本）、收缩主张（收益只在特定条件成立并报告该区间）、调整方向（成熟设备管理全面追平，评估评测与系统经验是否有独立论文价值，或结束该算法分支）。7.13、7.14、7.15 三条读数合起来指向第三支：无故障轨迹版本化配置已落在 oracle 上界 0.3 个百分点内；六类故障不改变排序；电量受限时反而把 oracle 的建模缺口暴露出来。

**这不是实验失败，是判据按设计生效。** D8 存在的意义就是让这件事在写作之前而不是审稿时暴露。可选的下一步有三条，都需要在决策记录里落定之后才能动手：把研究问题从"执行正确性"转到已经测出的边界本身（即"验证读当前状态看不到在途写入"这条机制性结论，它不依赖覆盖率优势）；把资产转为评测与系统经验（环境、故障注入器、审计链已建成）；或结束该算法分支。

**两处缺口，P2 冻结前必须补。**

**稳定身份在链路上并不存在。** 契约 §7 要求基线具备"稳定身份"，但 `AgentInterface.set_monitoring_profile` 每次调用都铸一个新身份（`node:profile:g{generation}`），因此"同一条逻辑命令的多次尝试携带同一身份"目前只存在于策略内部，没有落到报文上。策略侧已经维护并提供稳定逻辑身份（`vtc:{node}:{n}`），但运行时不回显它。这使报文级的配对抽样在重试层面缺一环，也意味着重试去重依赖远端按什么粒度判重这件事没有被钉住。补法有两条：运行时接受策略给出的身份并原样下发，或明确记录"身份由运行时铸造、策略的身份只用于本地账目"。这条要在 P2 之前定，因为它决定重试在链路上是否可配对。

**VTC 基线的退避参数是 A 层取值，却驱动它的收敛。** 900 s 基准、4 h 上限、6 h 命令 TTL 都是选出来的，不是标定的。它们直接决定 VTC 的错配时间（10864 min，接近本地规则的 11520），因此**这条基线的表观表现是参数选择的结果**。P2 之前应当冻结这几个值并做敏感性，否则"VTC 收敛慢"这个观察可能只是退避选得保守。

### 7.17 LLM 闭环与一处潜在缺陷

**LLM 那一项交付的是调用路径，不是模型证据。** `code/monitoring/llm_planner.py` 从 WorldView 渲染提示、解析并校验决策、交给运行器当作普通策略；决策不在动作集内、profile 不存在、缺参数一律拒绝并记录，不用回退静默替模型完成动作。调用账目含每次调用的原文、延迟、提示长度与后端名，标签携带后端因此结果表不会把模型运行与脚本运行混在一起。

本环境的端点是 `api.aicodemirror.com/.../codex/v1`，**返回 401、缺 `OPENAI_API_KEY`**，`make_real_backend()` 实测后给出具体缺失项而非静默降级。因此闭环目前用脚本后端跑通：

### 7.18 审计发现的两处结构性错误、四项业务指标与故障武装

**§7.13 与 §7.15 的"主命题已死"无效，两条理由都是实现错误而不是测量结果。** 在错误修好之前，现有读数既不能证明本文 runtime 有收益，也不能证明它没有。

**甲：业务层把网关与中心合成了一个实体。** `backhaul_gate` 只被 `backhaul_available()` 调用，后者只被 `center_send()` 调用，也就是只管下行。上行分支是 `rec.arrived` 成立后立刻 `rt.confirm(...)` 并写 `status[node_id]`，于是网关听到就等于中心可见，遥测不跨回传。契约 §6 明确要求"明确网络服务器位置、网关预缓存能力及回传时延"，架构 A 写的也是节点、网关、中心三个实体，所以这是违反契约而非简化取舍。

修法是 `opportunity.py` 增加 `GatewayItem`、`gateway_ingest`、`backhaul_forward` 与 `backhaul_delay_s`，运行器的上行只进网关缓冲，每 tick 由 `backhaul_forward` 前转，中心侧才更新 `status`、`confirm` 与接口的遥测记录。存储转发让回传中断**推迟**遥测而不是丢弃它，中断时长因此直接变成观测空窗。修好后 `backhaul_only` 第一次对指标有作用：

| 臂 | 无故障覆盖 | 仅回传中断 | 下行尝试（无故障 → 故障） |
|---|---:|---:|---:|
| 本地规则 | 32.8% | 32.1% | 0 → 0 |
| 版本化配置 | 59.1% | 59.1% | 387 → 335 |
| VTC 风格 | 57.4% | 54.2% | 140 → 133 |
| oracle | 62.3% | 60.9% | 156 → 156 |

覆盖率整体低于 §7.13 那一批（例如版本化配置 95.3% → 59.1%）是这次修正的直接后果，不是新的失效：观测路径现在有一条真实的、会down的跳跃，而按期有效覆盖率要求样本在**中心**截止前到达。

**乙：四条臂里没有本文 runtime。** `grep -rn "from operations import" code/monitoring/` 无命中，`operations.py` 那套执行语义从未被业务层引用。契约 §7 的第五条基线写的是"本文及消融"，实际跑的是本地规则、版本化配置、VTC 风格三条基线加一个策略上界。oracle 是策略不是运行时，而且它走同一个 `AgentInterface`，没有稳定身份、没有远端契约、没有调和，所以它是"某策略在无契约远端上的上界"。**在把 `operations.py` 接进来之前，任何关于执行层的结论都不成立。**

**丙：四项业务指标。** §7.6 列的四项里，配置错配时长本来就已是逐 tick 积分（`config_mismatch_s += TICK_S`），不是轮末采样。其余三项此前完全缺失，现已实现在 `scorer.business_metrics`：

- **关键观测空窗**：按需求 profile 的 `sample_s` 对时间积分得期望样本数，减去实际采样数。
- **误报成功**：中心结算为已生效、而结算时刻该节点实际并不在运行该值的次数。判定要读节点自己的 profile 历史，所以运行器同时记录 `profile_timeline`。
- **平台知晓 vs 实际生效时延**：`observed_at - applied_at`。为此 `AgentInterface` 拆出 `note_applied`（端侧真值，无条件记录）与 `note_observed`（中心知晓，取决于路径）；原先两者在同一次调用里写成同一时刻，知识时延被结构性地钉死为零。

新指标立刻分化，且分化的方式正是它们该有的方式：

两条读法。其一，确认丢失的代价**按臂不同**：重新验证的臂把知识时延压回分钟级，等待的臂要到 3 至 5 小时，这一栏是现有对照都不具备的。其二，陈旧覆盖让**四条臂各产生 4 次误报成功，oracle 也不例外**，因为 oracle 是策略而不是带单调 fencing 的远端；这是 §7.9.2 那条精确版本契约值得单列的直接证据，也是本文 C2 唯一能拿出的零值。

**丁：按动作的故障必须按动作武装。** 上一版里 `request_lost`、`ack_lost`、`stale_command` 按固定时钟排班，而钟点落在哪一分钟与部署当时在做什么无关。实测 `ack_lost` 的三个故障窗（t=54000/140400/226800，各覆盖 1 小时）内，被点名节点 n03/n11/n08 收到命令的次数**都是 0**，而它们全程各收到 6/7/8 次；事件表非空，被测动作从未被触及。这一类故障是**单次动作的属性**，不是时段属性，因此改为按标称时刻开窗、由该节点下一个真实动作消耗，`stale_command` 的延迟重新锚定到真实派发时刻并保留原有延迟。修改后 `ack_lost` 与 `stale_command` 才产生上表的两栏读数。**"故障事件非空"不等于"故障影响了待测动作"，这两件事此前被当成了一件。**

### 7.19 本文 runtime 入臂，与远端契约第一次成为可测的量

**`operations.py` 的语义第一次接进业务层**，以 `RuntimePolicy`（臂名 `ours`）实现，五条臂由 `policies.BUSINESS_ARMS` 统一登记。三个此前不存在的东西同时落地：

**稳定身份落到报文上。** §7.16 记的缺口有了物理位置：`AgentInterface.set_monitoring_profile` 只接 `profile`，策略手里的版本与逻辑身份在这一层被丢掉。现在 `profile_command` 可带 `version` 与 `logical`，两条投递路径——普通窗口与网络扣留后的释放——共用同一个远端判定函数。此前释放路径直接写 profile，绕过一切契约，于是**即使发送方把版本送上了链路，陈旧命令仍能覆盖更新的那条**，而这正是顺序类故障唯一要制造的危害。

**远端契约实现为 C1 去重加 C2 fencing。** 节点对同一个 `logical` 只生效一次；`version` 低于当前生效值的一律拒绝并回报中心，使中心停止重发而不是等超时。契约按报文字段生效，因此**发送方把版本送上链路才用得上它**：版本化配置臂此前发的是裸值，等于把远端能 fencing 的东西留在中心脑子里。这一条先按公平性修正，再比较。

**证据必须晚于写入才算证据。** 一个与期望相符的上报，只有在它产生于最后一次写入之后才能结清这次写入；产生在写入之前的只是一个更旧状态的读数。本文臂的规则是双向的：上报晚于写入且相符则结算，晚于写入而不符则"这次写入没落地"、过了驻留期重发；早于写入则两者都不成立，只能等。

结果如下（72 小时，单种子，无故障与陈旧命令两条轨迹）：

| 臂 | 无故障覆盖 | 无故障下行 | `stale_command` 覆盖 | 误报成功 | 陈旧覆盖 | 去重 | fenced |
|---|---:|---:|---:|---:|---:|---:|---:|
| 本地规则 | 32.8% | 0 | 32.8% | 0 | 0 | 0 | 0 |
| 版本化配置 | 59.1% | 387 | 58.4% | 0 | 0 | 41 | 0 |
| VTC 风格 | 57.4% | 215 | 53.5% | **4** | **4** | 0 | 0 |
| 本文 runtime | 57.2% | 293 | 51.4% | 0 | 0 | 44 | 0 |
| oracle | 62.3% | 165 | 60.5% | **4** | **4** | 0 | 0 |

**读法一：配置类负载上，本文臂与版本化配置臂测出的是同一个方法。** 两者都是零误报、零陈旧覆盖，都由 C1 去重挡住（41 对 44 次），`fenced` 都是零——**C2 在这条负载上一次都没有被用到**，因为同一条逻辑命令的重复投递先被去重接住了。这与 §7.6 早已写下的判断一致：设备影子按版本丢弃乱序旧更新，在配置类负载上与本文是同一条边界。本文 runtime 的增量不在这里，而在一句话动作与跨重启持久化；把这半张表当成本文的主要收益是把 §7.6 的边界重新说成弱点。

**读法二：没有远端契约的臂确实吃下全部四次陈旧覆盖。** VTC 与 oracle 各 4 次覆盖、4 次误报成功，**oracle 也不例外**——它是一个策略，不是带单调 fencing 的远端，所以它答不出这个问题。这两行是 §7.9.2 那条精确版本基线值得单列的直接依据。

**读法三：本文臂用更少的机会换到接近的覆盖。** 293 次下行对版本化配置的 387 次，覆盖 57.2% 对 59.1%；陈旧命令轨迹下 232 次对 375 次。这一点需要在多种子下确认，单种子不足以支撑。

**一处必须撤销的自证。** 本轮前半段我曾据"四条臂各 4 次误报成功"判断没有任何臂能防陈旧覆盖。那一读数是**指标缺陷**：释放路径当时不写 `profile_timeline`，判定"结算瞬间节点实际在跑什么"时读到的是不完整的历史。补上历史后那 4 次消失，真正的分化才作为上表出现。指标与被测对象同源时，指标的缺口会被读成被测对象的缺口。

### 7.20 §7.9 的两个对照臂与 §7.7.2 的授权重建

三个臂落地，`code/experiments/restart_experiment.py` 增两行、`method_comparison.py` 增一行。

**7.9.1 游标恢复臂 `journal_cursor`。** `Journal.up_to(cursor)` 给出日志在检查点处的视图；游标只在落盘时前进，落盘周期 `FLUSH_PERIOD_H = 4` 是方案自身的 A 层参数。游标只标记"已落盘"，**不标记"远端已确认"**——这一点按 §7.9.1 的要求分开，否则游标会退化成第二条不可靠的回执通道。恢复的语义差别在于：崩溃时落在游标之后的在途操作，恢复出的注册表里没有它们，因此协调者不知道它们存在，也就无从调和。

| 臂 | scheduled 恰好一次 | 调和读 | 写入 | adhoc 恰好一次 | 非请求 | 日志条目 |
|---|---:|---:|---:|---:|---:|---:|
| `journal`（全量重放） | 35.0% | 463 | 1423 | 35.0% | 0 | 3765 / 4717 |
| `journal_cursor`（游标重放） | **35.0%** | **0** | 1517 | **30.0%** | **133** | 275 / 370 |

读数与 §7.9.1 的预期逐条对上：`scheduled` 下恰好一次不变而调和读归零，代价是写入上升（放弃调和就得盲重发）；`adhoc` 下掉了 5 个百分点并出现 133 次非请求应用——那正是"少数在途操作从'尚未完成'变为'从未发生'"的可见形式，因为 `adhoc` 的身份不可从任务重算，游标之后的决策条目丢了就再也接不上。**持久化粒度因此从一个设计直觉变成一个可比的量。**

**7.9.2 精确版本 fencing 基线 `exact_version_cas`。** 远端由单调 fencing 换成乐观并发：写入者必须持有当前版本，版本不符者拒绝，版本未知者一并拒绝。`read_state()` 新增 `fence_version` 暴露远端会接受的版本；该臂每次写之前先读一次它，读不到就直接不发。30 天、单种子：

| 臂 | 恰好一次 | 写入 | CAS 读 | **CAS 读失败** | 空口 h | 归一代价 |
|---|---:|---:|---:|---:|---:|---:|
| `one_shot` | 28.4% | 1920 | — | — | 0.2 | 2254 |
| `verified_tool_calls` | 32.2% | 2023 | — | — | 0.5 | 4210 |
| **本文 `ours`** | **40.1%** | 4689 | — | — | 0.7 | 5728 |
| `exact_version_cas` | **27.6%** | 817 | 817 | **4506** | 0.7 | 1204 |

**更严的契约在机会受限下净亏，而且亏得不小。** 5323 次读尝试里 4506 次没有回音，写入者因此拿不到可以写入的版本，只能等下一次机会；结果恰好一次 27.6% **低于什么都不做的 `one_shot` 的 28.4%**，而空口与本文臂同为 0.7 h。§7.9.2 说"这个结果无论倒向哪边都有信息量"：它倒向的这一边说明，在 §7.1 的机会约束下，"每次写前先读一次版本"把一个机会预算变成两个，而读出失败率决定了它连基线都跑不过。它同时是一条更保守的正确性基线，零乱序、零陈旧覆盖，所以这一行不是负面结果，是**机会约束强度的直接测量**。

**7.7.2 授权重建臂 `journal_reauthorize`。** 从日志恢复出的操作处于**已知但不可派发**的状态：只有在到该实体的调和通道被重建之后才重新获得派发权。实现为"该实体在 `CHANNEL_MEMORY_H = 6` 小时内有过一次成功穿越"。

| 臂 | scheduled 恰好一次 | 写入 | 调和读 | 拒发 | adhoc 非请求 |
|---|---:|---:|---:|---:|---:|
| `journal` | 35.0% | 1423 | 463 | 0 | 0 |
| `journal_cursor` | 35.0% | 1517 | 0 | 0 | 133 |
| `journal_reauthorize` | **28.7%** | **960** | 463 | **463** | **0** |

**§7.7.2 的可测差别存在，但它的形状和原文猜的不完全一样。** 原文预期"两者的重复数预期都为零，差别应出现在调和读次数"——重复数确实都为零，调和读次数却相同（463 对 463），差别落在**写入数**（960 对 1423）与**恰好一次的代价**（28.7% 对 35.0%）上，以及在 `adhoc` 下消掉游标臂的 133 次非请求应用。也就是说，授权重建买到的是"不发无通道可回收的动作"这件事本身，代价是 6.3 个百分点的覆盖率与 463 次拒发。**那条规则不是免费的，它的收益要用越权副作用来记账，不能用覆盖率来记账。**

### 7.23 四接口与三个闭环接通、2×2 成形、CAS 基线公平化

**一、四接口此前只通了一个。** 业务层只调用了 `set_monitoring_profile`（1 处），`read_status` / `request_measurement` / `upload_records` 调用次数为零；运行器分发里有一句 `if "profile" not in payload: continue`，非 profile 的命令被**直接丢弃**。三个业务闭环里 W2 完全没有实现。

现在四个接口全部接通，节点侧语义逐条验证过：

| 接口 | 端侧语义 | 验证读数 |
|---|---|---|
| `read_status(node,max_age)` | 返回时间戳、启动标识、配置版本、电量估计、缓存水位、两个游标；由被动遥测免费应答 | `snapshot` 字段集已按契约补齐 |
| `set_monitoring_profile` | 版本化赋值，真正改变采样与上传调度 | 原有路径 |
| `request_measurement(node,request_id,deadline)` | 请求由**窗口内的新样本**应答，标签在采样发生那一刻打上 | 实测请求 `m1` 由窗口内 60000 s 的样本应答，产出 `n00:60000:rm1` |
| `upload_records(node,range,cursor,budget)` | 只送点名区间、按预算封顶、从点名游标起 | 实测送出 `[3300..4200]` 而旧缺口等待——新数据插到历史前面 |

三处必须记下的实现细节：**标签在采样时打**，因此旧缓存永远无法事后取得"我是新采集"的身份；**游标用样本时刻而非样本 ID**，ID 按字符串排序会把 `:10800` 排在 `:3600` 之前；**命令到达晚于自己的截止期一律拒绝**，实测拦下过一条窗口已关闭仍被执行到端侧的测量请求。

**二、三个闭环的运行读数。** 24 小时含风险窗（12–18 h）：W1 发出 48 条请求、**端侧应答 14 次**并产生 14 个带标签样本；W2 补传 19 条；W3 表现为 profile 回落。W1 的速率约束是"同一节点有未结请求就不再发，且请求等满自己的截止期"——中心分不清已应答与在途，凭猜测重问正是未知结果要禁止的动作。窗口按**上行节奏**而非采样间隔取：短于它所等待的节奏的窗口根本送不到。第一版没有这条约束时下行 2660 次、机会被吃光；有约束后 235 次。

### 7.24 陈旧覆盖的读数被撤销：它由过期命令被执行造出来

**加一条过期规则，掀翻了前几轮的一条主结果。**

命令有它自己的有效期（`PROFILE_COMMAND_VALIDITY_S = 6 h`），而 `stale_command` 的扣留时长默认取 **[2, 4] × 档位间隙 = 12–24 小时**。也就是说被网络扣住的命令，在释放时**早已过期**。前几轮没有强制过期，于是这些过期命令照旧在节点上被执行，产生了"VTC 与 oracle 各 4 次陈旧覆盖、版本化配置与本文各 0 次"这组读数，并被写进 §7.19 与 §7.21 当作 C2 的唯一数值优势。

补上过期规则后，同一轨迹变成：**4 条被持有、0 条被释放**——扣留的命令全部在有效期内被判过期并丢弃，`stale_reorders` 与 `stale_overwrites` 双双为零。**那条"版本化配置与本文都拿到零"的对比因此没有依据。**

**修法有两处，都不是调参。**

其一，扣留必须短于有效期，否则该故障描述的是一种部署不可能发生的顺序危险，`FaultSpec` 现在直接拒绝这种参数：

```
stale_command: delay_s=21600 is not shorter than the command validity 21600;
the held command would expire before it lands, so no ordering hazard is possible.
```

默认扣留改为 **0.50–0.95 × 有效期**（3–5.7 小时），并且只保留了原来的下界与上界两条断言中的有效期方向。

其二，**扣留还必须跨越一次需求变化**，否则它写回的是当前本来就生效的值——是一次协议层的乱序，不是领域损害。实测：扣留 4 小时而需求每 6 小时以上才变一次，两者几乎从不重叠，于是 4 次注入全部落在"写了同一个值"上。现在故障在派发时额外要求 `issued < 某次变化 ≤ issued + 扣留`，不满足就**保留武装、等下一次真实派发**，而不是把这一次注入花掉。这一条把两种事件分开了，正是 D15 要求的分开计数。

|---|---:|---:|---:|---:|---:|---:|
| 本地规则 | 0 | 0 | 0 | 0 | 0 | 32.8% |
| 版本化配置 | 0 | 0 | 0 | 0 | 0 | 59.1% |

**乱序发生了，覆盖没有发生。** `rule__naive` 的 2 次乱序是协议层的定序违规，它们没有把任何一个已经生效的值写回去。

**这一节的结论必须如实写：本文 C2 在陈旧覆盖这一栏上目前拿不出数值优势，因为它与被比较的臂在同一个零上，而那个零来自"这个 72 小时轨迹里没有一次注入真正造成了值倒退"。** 单种子、注入次数只有 1–2 次，统计功效极低；多种子重跑前，这一栏不得用于任何主张。前几轮据它写的"§7.19 读法一"与"§7.21 读法一"**作废**。

### 7.29 组合式 runtime 的优势是一个 bug：逻辑身份没有随需求周期变化

**§7.23、§六 的 2×2 表与 §7.27 的重启表都建立在同一个缺陷上，那些读数作废。**

**缺陷。** `Intent.logical_key` 对 profile 指令用 `{node}:profile:{value}` 作键，而 `ContractRuntime.settled` 按这个键去重。节点在风险窗之前报过一次 `normal`，这个键就被**永久结算**——需求在小时 18 回到 normal 之后，同一条指令被当成"已经完成"，再也不会下发。

**实测。** 72 小时里组合格发出 **31 条 `risk` 命令与 0 条 `normal` 命令**，96 个操作长期未结，节点 **78.3% 的时间停在密档上**（需求只要求 16.7%）。密档的上传间隔是 5 分钟而不是 1 小时，因此它凭空造出**两倍的上行机会**（29,815 次对 14,127 次），多出来的窗口又变成更多下行尝试。**它领先单体实现的那几个百分点，是这个人为的机会供给买来的，不是方法差异。**

**修法。** `Intent` 增加 `epoch`，在需求值发生**变化**时递增，键变成 `{node}:profile:{value}:e{epoch}`。同一个需求周期内重发仍是同一条指令，跨周期则是一条新指令。

**修完后同一批参数下的读数：**

| 臂 | 覆盖 | 上行 | 下行尝试 | risk 档时间占比 | profile 命令 |
|---|---:|---:|---:|---:|---|
| 本文（单体） | 54.0% | 14,127 | 918 | 16.5% | 49 risk + 56 normal |
| `rule__contract`（组合） | **54.0%** | 14,073 | 943 | 17.2% | 59 risk + 182 normal |
| 版本化配置 | **59.1%** | 15,297 | **387** | 19.8% | 46 risk + 71 normal |

**组合格从 57.0% 掉到 54.0%，与单体实现完全一致。** 两条本文实现现在给出同一个数，这本身是一个有用的确认——方法的两种写法不再互相矛盾。

**由此修正两处此前的表述。** §7.26 末尾那条"组合式比单体好近 9 个点、可能是实现问题"的说法**不成立**：那 9 个点是这个 bug，不是实现质量差异。§7.28 把差距归因于"单体节流缺陷"也**只对了一部分**——组合式当时并没有更好的节流，它只是被卡在密档上、拿到了更多机会。

**当前可信的结论回到一句：在稳态业务指标上，成熟设备管理基线以大约一半的机会开销拿到高 5.1 个百分点的覆盖。** 本文的实现修完节流后仍是 54.0%，与 59.1% 的差距是真实的方法差距，不是实现差距。

**同一个缺陷在 LLM planner 里也在。** `LLMPlanner._to_intent` 构造 `Intent` 时没有传 `epoch`，它因此恒为 0，每个节点整轮的 profile 指令共用同一个键——正是同一件事。**修完后 `llm__contract` 在 72 小时单种子上从 72.5% 掉到 54.2%。**

**三条本文实现现在收敛到同一个数（72 小时，单种子）：** 单体 54.0%、`rule__contract` 54.0%、`llm__contract` 54.2%。**这三条此前是 52.3% / 57.0% / 72.5%，差异全部来自实现缺陷与人为机会供给。收敛之后，"本文方法在稳态指标上是 54%"这一句才有意义。**

**待重跑的状态。** §六 的 2×2 表已用 `--tag 2x2v2`（只修了 rule planner）重跑一次，但那一次 `llm__*` 两格仍带缺陷，**必须再用 v3 重跑**。§7.27 的重启表同理，`--tag restart20v3` 已启动。**在 v3 读数写入之前，`llm__contract` 与 `llm__naive` 两格的所有读数一律不得引用**；`rule__contract` 那一列在 v2 之后可用。

**一次值得记下的过程。** 本轮为此重跑了三遍表格（v2 修 rule planner、v3 修 LLM planner），每次都发现上一遍漏了一个同样的错误。**这类"键在某处被悄悄复用"的缺陷不会报错，只会让读数变好**，因此只能靠在多个实现之间交叉比对来暴露——单体、组合式、LLM 三条路径互相作为对照，是这一轮唯一发现它的方式。

### 7.12 P1 前置项（不阻塞 P0，阻塞能耗与续航主张）

以下两项不属 P0 判据：72 小时参考负载在节点全程有电的前提下即可跑通，因此 P0 定义闭合不受影响。它们阻塞的是契约 §9 分析③"动作驱动能耗"以及任何续航、节能类主张。

**业务层的节点存活尚未由能量模型驱动。** 当前 `code/monitoring/runner.py` 用常数上行接收率 `uplink_p_arrive` 表示接入跳的成功，没有接 `energy.py` 的供电状态。契约 §6 要求各方法的电量分别演化并驱动可达性，这是 P0 剩下的最后一处结构性缺口。在补上之前，业务层的结果不能用于任何续航或节能主张。

**`alive` 会 latch，且这是补耦合的前置。** `energy.py` 的 `step()` 只在 `bat_wh <= 0` 时置 `False`、只在 `bat_wh > 0.05 × usable_wh` 时置 `True`，中间区间两个分支都不执行。因此节点一旦活着就保持活着，只有在恰好归零的那一刻才会翻转。文档串 "Returns whether the node is alive (powered)" 比代码强。补业务层耦合前需先修，否则"断电导致不可达"这条通路永远不会触发。

**另有两处待整理**：新节点以 `usable_wh` 初始化，而冷环境下的实际上界是 `capacity_Wh(T)`，首次 step 会静默丢掉差额；`disruption_env.py:271` 用能量状态直接覆盖节点的 `alive`，使任何其它失效类标记的死亡都会被电池恢复抹掉。
