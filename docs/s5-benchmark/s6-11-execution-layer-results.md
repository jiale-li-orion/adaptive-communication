# 执行层在 WirelessOpsBench 任务契约上的结果

复现：

```bash
export PYTHONPATH="$PWD/libs/pylibs"
python3 code/wirelessops_adapter.py --limit 120 --ticks 1200 --rounds 1,8,32,64
python3 code/wirelessops_adapter.py --limit 120 --ticks 1200 --rounds 1,8,32,64 --sink plain
python3 code/wirelessops_adapter.py --limit 120 --ticks 1200 --rounds 1,8,32,64 --sink plain --version
```

原始输出在 `results/wirelessops_execution_{idem,plain,plain_version}.txt`。120 个公开任务，Gilbert-Elliott 信道，每个 horizon 跑满 7,680 个操作周期。

## 一、实验设定

任务正确性不重新评分。公开包扣留了 scoring 谓词，重评等于替 benchmark 造答案。授权正确性由接入层按 `legal_transitions` 强制，全部运行中授权违规为 0，因此测得的差异全部来自执行层。

每个周期恰好意图一次逻辑写入。重复副作用因此精确计数为"落地的写入数减已驱动的周期数"，不从轨迹推断。

两个正交机制在 agent 侧。重试是否复用同一条逻辑写入的身份；验证是否向实体查询本次写入是否落地、查询是否限定在本次写入上。

| 策略 | 身份 | 验证 |
|---|---|---|
| `naive` | 每次尝试新身份 | 无 |
| `stable_key_only` | 周期内稳定 | 无 |
| `verified_wrapper` | 每次尝试新身份 | 非限定，即 arXiv `2608.02645` 的谓词 |
| `lifecycle` | 周期内稳定 | cycle 限定 |

远端另有一个开关，对应真实网络的维护窗口：sink 是否对同一身份的去重请求做合并，以及是否强制 epoch 单调。`--sink plain` 模拟重新下发一条配置命令的真实行为——它不是幂等的。

## 二、结果

每千周期计数，horizon 为 64，共 7,680 个周期。

| 远端 | naive | stable_key_only | verified_wrapper | lifecycle |
|---|---|---|---|---|
| 幂等 sink | 280.7 重复 / 8.1 零效果 | **0** / 8.1 | 132.4 / 73.2 | **0** / **4.3** |
| 非幂等 sink | 280.7 / 8.1 | **280.7** / 8.1 | 132.4 / 73.2 | 140.8 / **4.3** |
| 非幂等且强制 epoch | **0** / 6.8 | **0** / 6.8 | **0** / 66.4 | **0** / **5.3** |

四条结论。

**幂等键在没有配合的远端时价值为零。** `stable_key_only` 在幂等 sink 上重复为 0，换成非幂等 sink 后变成 280.7 每千周期，与 `naive` 逐位相同；同时 sink 的去重计数从 2,156 掉到 0。上一行里那份收益全部来自远端对键的配合，与 agent 的纪律无关。这正是把"用稳定幂等键"当作解法时会忽略的前提。

**epoch 强制让所有策略的重复归零，包括每次都用新身份的 `naive`。** 2,156 降到 0，agent 什么都不用改。重复这一侧的修复位置在远端，不在 agent。

**重复归零之后，唯一剩下的差异是冲突消解，而已发表的谓词在这里失效。** `verified_wrapper` 的零效果率在强制 epoch 后从 6.8 升到 66.4 每千周期，是不做任何验证的 9.8 倍。原因是其谓词问"此实体上是否曾应用过该动作"，会被更早周期的写入回答为是，于是包装器判定完成并停止，本周期该发生的写入从未发生。horizon 为 1 时该缺陷不可见：四个策略的零效果均为 0.0。

**cycle 限定的验证在三种远端配置下都是零效果最低的**（8.1 比 4.3、8.1 比 4.3、6.8 比 5.3）。它的优势不依赖远端的配合，因为它问的是"本次写入是否被处理"，而幂等键问的是"远端是否愿意合并"。

## 三、这与已有工作的关系

`verified_wrapper` 把重复从 280.7 降到 132.4，看起来是改进。在强制 epoch 的配置下它把重复降到 0 的代价是 510 个周期的写入从未落地。只统计任务结果与重复率的评测会把它排为更优解。

上游 benchmark 的七类条件全部刻画证据账本的可信度，其 episode 把工具调用视为必然送达，重复与零效果这两条轴都不在其故障表内；公开包也不含 baseline 分数，`2608.02645` 的 verified wrapper 在该 benchmark 上的表现无从对照。

## 四、效力威胁

CQI 是本项目提供的替代量。公开包不含 `ray_tracing` 实现与证据内容，该参数属假定层，须做敏感性扫描而非当作实测值报告。

接入层把任务的三类角色映射到真实地形节点上，节点取自 SRTM 覆盖网格，映射本身是设计选择。

epoch 的生成是接入层的行为，真实网络中它来自协调者的任期或配置管理系统的版本号。`--version` 只建模了单调性与拒绝语义，未建模 epoch 耗尽与协调者换届。

验证返回 `unknown` 时的最优策略未做搜索，当前只做有界重试。

全部数值为本文自己的 runtime 在公开开发集上的结果，不是该 benchmark 的官方分数。
