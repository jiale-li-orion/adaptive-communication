## 一、任务陈述（冻结文本）

> **灾前山区监测服务连续性。** 在供电不足、接入与回传间歇可用的条件下，系统应维持常态周期
> 监测；当外生事件（降雨阈值触发、上层监测要求）出现时完成事件驱动的加密观测与回传；在中断
> 期间保留可恢复状态；恢复后在有限通信机会与能量下，同时服务当前的新鲜数据与历史完整性。
> **方法只能通过真实设备支持的动作干预系统，不能改变任务的分母。**

展开成一句可检验的话：

> **中心必须在每一个稀缺的通信机会上决定：把它花在"弄清楚"（读状态、探活、核验缺口），还是
> 花在"做事"（改采样/上报周期、下单补传、切换备用路径）——而这两件事走的是同一条链路，
> 因此"节点已经静默"与"我的查询在回程丢了"在观测上不可区分。**

### 1.1 为什么这句话里每一部分都有依据

**风险等级不由 agent 判定。** 传感器异常、降雨阈值、上层平台下达的监测要求作为**外生事件**进入。
agent 不做滑坡预测——那是预测论文的工作。它做的是"业务要求已经出现之后，怎么让分布在山里的
设备真正完成监测"。（依据：`task-and-action-space.md:43` 契约已规定风险等级为固定回放；
`pre-disaster-paper-contract-v0.1.md:43` 明说"不训练滑坡预测器"）

**"持续稳定通信"转化为"监测服务连续性"。** 不承诺链路永不中断；通信技术提供物理路径，runtime
管理路径上的任务；永久无路径或无电仍需工程补盲、储能或维护。（依据：`pre-disaster-paper-contract-v0.1.md:12` 原文）

**观测通道就是控制通道。** 这是本项目的核心结构假设，也是**唯一还没有被任何一篇先行工作占据的
空白**：`agent-assumption-audit.md:44` 原文判为"这是最干净的一条"，`:58` 再次确认"其中 G5 尤其
干净"，由"网络侧 partition/disconnect 命中 0"（`:40`）等三重排除支撑；`prior-art-agent-runtime.md:716-717`
还给出互锁证据——"验证器自身也不可用"。（见 §八）

## 三、最重要的一刀：把人工风险窗换成 trace-driven task arrival

**当前实现对 task 的最终判决**（`C:§4`）：契约侧有五条把"决策"规定成了"输入"——
需求集外部生成（`pre-disaster-paper-contract-v0.1.md:47`）、关键测点集合任务给定（`:39`）、
风险等级固定回放（`task-and-action-space.md:43`）、触发加密观测的唯一依据是外部公告（`:82`）、
唯一的"必要时"没有判据（`:62`）。**更彻底的是：实现里连"观测值"这个量都不存在**
（`node_model.py:72-94` 的 `Sample` 没有读数）。**所以即使把所有实现偏差都补上，任务仍然是
"在两个窗口开启时把一次已知的状态写进 8 个节点"。根因在契约，不在实现。**

**冻结的替换方案：**

```
业务事件（外生、可复现、来自真实 trace）
  ├─ 常态：每 1 h 一次定时回传
  └─ 事件：降雨阈值触发 → 加密采集/回传突发
通信过程（按 seed 变化）
供电过程（按 seed 变化）
```

**业务事件序列固定**，通信与供电轨迹换 seed。这比"seed 0–19，每次都在第 12 小时进入 6 h risk
window"硬一个量级——**因为任务不是我们为论文编的，是别人已经部署九个月、论文里跑过的监测逻辑。**

同一原则适用于所有轴：**应用事件是 exogenous 的；方法只能决定怎么服务这些事件，不能改变任务
分母。** 当前 `task_generator` 其实已经做对了这一点（D18：需求集不随种子变化），**只是外生任务
本身造得太随意**。

## 五、规模与"关键节点"解耦

**16 节点可以继续作为仿真规模，但"8 个关键节点"不得成为业务真理。**

- Wang 的实地部署是 **5 台**：1 个 gateway / master rainfall node + 4 个 deformation subnodes
  （`B`；**待核**）。
- 冻结办法：**monitoring cell 的角色结构由现场论文给；5 / 10 / 16 / 32 nodes 是 scale axis。**
- 这样被问"为什么 16？"时回答"只是规模变量"，而不是"因为 16 比较方便"。

## 六、中通服痛点落在**扰动轴**，不进 Introduction 背景话

**扰动轴（冻结）：**

1. 供电开始不足（电池进入冬季充电门限以下）
2. 节点—网关局部不可达
3. gateway—center 回传中断
4. 两者同时发生
5. 恢复后 backlog 与当前 event traffic 同时存在
6. 有预部署 relay / backup WAN 时能否恢复服务

**必须同时说清的证据边界**（`B:§4`、`geohazard-china-context.md:427-589`）：

- **唯一的地灾直接关联只到设计层**：中通服咨询设计研究院中标**西藏自治区地质灾害风险预警系统
  建设项目初步设计**（2024-04-18，采购人 西藏自治区自然资源厅，单一来源，下浮率 4.00%，**无绝对
  金额**），范围含省-市-县三级预警系统设计、数据中心、业务系统、气象数据集成、硬件与野外调查
  装备。**无建设/运营阶段证据，无通信层属于其范围的证据。**
- **`地質災害` 在 CCS 四份报告里 0 命中**；年报未呈现任何地灾监测网络、监测平台或监测通信产品；
  命名的平台是安全生产 / 应急救援指挥 / 森林火灾 / 智慧水利。
- **公开的一切灾难内容是灾后应急抢修**：定日 6.8 级地震（到场设备是 30 kW + 240 kW 移动电源车
  + 2 台卫星电话）、怒江贡山福贡崩塌泥石流光缆中断、贵州三都山体滑坡全县通信瘫痪、重庆 5 区县
  铁塔基站停电。**240 kW 柴油发电车不是永久站点供电架构**——这个区分必须在技术报告里保持显式。
- **最强的佐证是电，不是无线电**：113 处阿克苏零碳光储基站（一手，年报 ESG）；日喀则西九县与
  阿里太阳能施工份额（一手，招标结果）；中国移动西藏 **>48% 基站为新能源供电**（二手，新华网）；
  2025-03 禾木暴雪 **17 个基站因线路受损告警**、雪埋光伏板停止发电（二手，澎湃）。
- **西藏的监测点位实际属于 中国移动西藏公司（林芝 536 点位）与中国铁塔**，不是中通服。
- **"中心多久下一次命令"在全部材料里没有任何数字。** 材料自己把它列进"下一次与中通服交流最值得
  获取"的清单（`S2/pre:196`），并明说"当前没有报价及运维频率"（`S2/pre:172`）。
- 项目内部演示假设"每小时 → 每五分钟"**禁止**当作真实频率使用（`S2/pre:99`）。

> **因此可以对老师/中通服说的，不是"你们需要一套地灾监测 runtime"，而是：公开证据显示中通服在
> 西藏做的是【离网供电工程 + 灾后抢修 + 地灾预警系统的设计层】，而**监测网本身的运维频率与故障
> 统计没有任何公开数字**。这恰好是我们要问的第一个问题。**

## 七、评分：分列报告，不造统一分数

**坚决不造"大一统分数"**——benchmark 最容易被 argue 的就是权重是作者自己调出来的。

**第一层（业务服务，主表）：**

| 指标 | 定义 |
|---|---|
| routine freshness | 常态下"本应每 1 h 得到一次 report"的实际年龄（AoI）与缺报比 |
| event freshness | 事件触发后"本应产生 N 份加密观测"的 trigger-to-first-fresh-data 时延、接收比例 |
| recovery completeness | 中断恢复后历史记录的最终完整性 |
| configuration mismatch duration | 错误配置在位的时长 |
| energy consumption | 各节点电量演化（必须**真的 binding**） |
| communication opportunities consumed | 消耗的机会数（分上行/下行） |

**第二层（执行语义机制指标）：** duplicate / stale / unknown / fenced 等，作为机制指标单列，
**不得参与第一层的加总**。

**不发明 deadline。** 当前 `DEADLINE_S = {"normal": 5400, "risk": 600}` 标为 A 层，
**repo 里没有任何来源能证明它们是地灾业务 SLA**。冻结做法：直接评价 source-backed service
（上面第一层），要画 deadline-success curve 时**令 deadline 相对 source cadence 扫描**
（1× / 2× / 3× cadence），并明确叫 sensitivity。

**实验哲学借用已有顶会顶刊**：外部过程 + 采样成本 + 传输成本 + energy harvesting + unreliable
channel，评价 distortion / AoI / freshness（TCOM 2025 semantic-aware sampling；TCOM 2021
energy causality + unreliable update + AoI；TII 2025 有限窗口内外生生成的 fresh data；
INFOCOM 2026 多实体共享资源下的 state synchronization 用 Version AoI 衡量）。**来源由 GPT 建议
提供、本轮未逐字核对 → 待核。**

## 八、与 G5 的关系：这是 novelty 的落点，必须写进 task

`D` 的结论：**最干净、最可能守得住的是 G5「agent 的观测通道与它的控制通道是同一条」**
（`agent-assumption-audit.md:44`「这是最干净的一条」，`:58` 再确认）。

**它要求 task 必须满足的形状：**

1. **没有任何带外探测接口**——关于远端实体存活的**全部**证据必须穿过承载控制命令的同一条间歇链路；
   "实体已静默"与"我的查询在回程丢了"在观测上不可区分。
2. 注入**认识上不可得**的故障类（不是"注入了就能看出来"的那种）。
3. 按实测 trace 驱动。
4. **判分落在终态副作用等价，而不是任务成功率**——因为 exact-match 会漏掉 23% 的灾难性失败
   （`prior-art-agent-runtime.md:525`）。
5. 显式报告 trace 预处理里 flapping 与 missed-outage 的权衡（`verified-evidence.md:213-220`）。

**这正好解释了当前 task 为什么测不出东西**：当前实现里 `read_status` 的主动查询在产品路径上
**不可达**（`C:§5`），状态靠遥测搭车免费得到——**等于把 G5 这个变量关掉了**。接通它，
"观测通道 ≡ 控制通道"才第一次真正承重。

**最大风险项**：α³-Bench（`agent-assumption-audit.md:64` 原文判为"Gap 1 的最大风险项"）。
**落笔前必须先读它。**

## 九、我对这份外部建议的六处修正与限定

**（A）接受的部分。** 主任务陈述、trace-driven task arrival、砍掉 10 min/90 min deadline、
风险等级降级为外生事件、动作空间从真实接口反推、规模与关键节点解耦、中通服痛点进扰动轴、
分列报告不造统一分数——**全部接受并已写入上文**。

**（B1）阻塞项：加密突发的形状两处记录不一致，冻结前必须核原文。**
- GPT 建议：「触发后 **3 次、5 min 间隔**加密采集/回传」，并给出真实事件时间
  00:17 / 00:49 / 01:04 / 01:47 / 08:16 / 08:31 / 09:45。
- repo 落盘（`system-model.md:88`）：「触发加密采集时 **5 min 一次、每次 3 包**」。
- **这两者是不同的 workload**：一个是"持续 5 min 节奏"，一个是"3 发点射"。canonical trace 的
  形状完全取决于它。**在核对 Wang 2022 原文之前，§二 的"canonical 事件 workload"一行不得冻结。**

**（B2）阻塞项：`0.2 mm` 的语义。** repo 记"雨量 **0.2 mm**"，GPT 记"阈值 0.2"。0.2 mm 作为
累计量偏小、作为雨强偏大，**需要核原文的量纲与窗口**。

**（B3）阻塞项：5 节点结构待核。** "1 gateway/master rainfall + 4 deformation subnodes" 有出处
但本轮未逐字核对。

**（C）最重要的一处限定：外围证据填的是"上行遥测"频率，不是"中心下发"频率。**
GPT 方案的最大贡献之一，是用 Wang 的 1 h + 事件突发**填上了 repo 里"多久下一次命令"的空白**。
但必须分清：**那是上行遥测节奏，不是中心下发命令的节奏。** 配置变更频率仍然没有证据。
**这直接影响任务能否承重**（见 §十）。

**（D）中通服的公开证据比"老师说"弱且方向不同**（§六）。不要把它写成"中通服需要地灾监测
runtime"；公开证据支持的是**离网供电工程 + 灾后抢修 + 设计层参与**。

**（E）`request_measurement` 与 `upload_records` 不得进承重柱**（§四）。前者证据弱于 `0042/0045`，
后者是抽象物。

**（F）G5 必须写进 task（§八），否则我们只是用 LoRa 重跑了一遍 TCOM/TII 的 AoI 任务，没有 novelty。**
这是 GPT 方案里唯一没有覆盖、而 `D` 判定为最关键的一环。

## 十、设计上最硬的一条要求：本地规则必须被证明不够用

契约 §5 自己写了这条竞争解释：

> **"本地规则已经足够"是一个必须被排除的替代解释**——否则无法区分 runtime 的收益与"我们只是
> 多发了几条命令"。（`task-and-action-space.md:99`）

**如果 canonical workload 只有"1 h 定时回传 + 本地降雨触发突发"，那么中心什么都不用做，
节点自己就跑完了。** 这是本方案最大的结构性风险。

**冻结的设计要求：任务必须包含本地规则在表达力上做不到的义务。** 三类候选：

1. **全局电量预算分配。** 哪个节点在冬季降到门限以下、要不要把它切到节能档、牺牲哪一部分
   监测来保住关键测点——**这需要全网状态，本地规则看不到**。
2. **跨节点比较与升级。** 某个节点的降雨触发是否要升级为邻域同时加密——本地规则只能看自己。
3. **backlog 与当前流量的优先级。** 恢复后先补历史还是先服务当前事件，取决于全网剩余机会预算
   （**此项证据较弱，见 §四**）。

**这三条都必须由中心下发才能生效**（`0042`/`0045` 是中心可远程设置的字段，**一手依据**），
**因此中心的命令是必需的，而它的频率由任务自身的事件结构决定，不需要外部 SLA 数字。**

> **这一条同时解决了 §九-C 的缺口**：我们不需要知道"中通服多久下一次命令"，因为承重的是
> **任务在最优点上要求中心下发的次数**，而那是可以从事件结构算出来的量，不是外部输入。
