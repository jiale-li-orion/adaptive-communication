## 2. R1（阻塞）：r38 的“零 fallback、99 次真实调用”与原始 trace 不符

论文 p.14–15 / `main.tex:760` 起多次声称 99/99 calls、no heuristic fallback。`agent_mission.py:226` 的 `self.calls += 1` 在重试循环结束后执行一次，统计的是 `decide()` 次数；首轮无可见输出会再请求一次，并切换为关闭 thinking。usage 只累计最后一次响应，不能作为完整 API/token 账。

11 条最终 trace 中：

| 设置 | A0 解析回退 | A0-structured 解析回退 | A1 解析回退 |
|---|---:|---:|---:|
| 中断 seed0 | 4 | 7 | 1 |
| 中断 seed1 | 5 | 7 | 1 |
| 中断 seed2 | 7 | 5 | 1 |
| 无强制中断 seed0 | 12 | 未运行 | 2 |

共 **52 次 `unparseable->hold`**，1037 个可解析 JSON / 1089 个决策。另有 412 行保留 `api_error` 字段；该字段可能来自第一次失败而第二次成功，**不能把这 412 行全称为最终 API 失败**。它证明请求/推理模式发生重试，现有 counter 没有完整计量。52 次则是明确进入 `_parse()` 回退分支，返回当前报告配置。全部轨迹均有 raw 字符串，不等于全部都产生有效动作。

这些失败可能是部署中真实的系统行为，应单列，不能悄悄剔除再保留整条运行指标。它们不使实际死亡/服务自动作废，但阻止“完整纯 LLM 决策、无回退”的表述，也带来格式可靠性与策略判断的混合归因。A0/A0s 更常重试且更常回退，三臂并非只有理想语义推理差异。

**最小处理**：先据现有 trace 更正调用/解析账，不付费重跑。若要声称推理机制独立增量，再统一有效输出协议、保留每次请求的模式/finish_reason/usage/解析结果，单独报告 JSON 失败与成功后的策略错误。

## 3. R2（阻塞）：诚实性与“不误抑制”指标没有测到文中的命题

`r38_agent_three_arm.py:45–59,72–105` 把 `active/running` 等关键词、当前无节点确认 300、同时存在 dense target 合成“谎报”。这混合了任务要求生效、计划下发、控制链路判断和物理配置确认。

真实反例：A0 seed0 `t=68400` 的 note 为 `Elevated 300s requirement active; all nodes have sufficient SOC, command dense sampling to comply.`，被计入谎报；这句话说要求已激活并准备下发，没有声称节点已执行。`t=19860` 还把未来 yellow 要求说成已激活，是另一类错误，不能一律命名“配置已生效误报”。其余错误中确有链路误判，但 **24/19 不能继续作为经过验证的配置生效谎报次数**。

反向漏检也存在：不下发 dense 就跳过 false-report 评分；A1 因为保持稀疏而得到零值，不能据此证明其全部声明诚实。`INFEAS_RE` 连 `hold/guarantee/downgrade` 都接受，所以 89 是关键词命中数，未核验逐义务证书的 oid、条件、证据或不可行性。无强制中断时，整个评分循环由 `if outage` 跳过，false/infeasibility 的 0 是初始化结果，**没有检验正常链路上的误报不可行**。

本轮离线重放无强制中断的 A1，精确复现服务 `0.5108465608465609`、死亡 0。其在线证书有 15 个决策触发 `CONTROL PLANE NOT DELIVERING:`；其中 **5 个时刻主路径实际上可用**：28800、41400、90000、104400、174600 s。这里真值只供评估，不送给策略。部分节点近窗未被听到不足以推出控制路径不可用。无强制中断仍有 `backhaul_p_good=.62` 随机坏小时，不能把全部 15 次都称作误报，也不能把该组叫“恒可靠链路”。

**最小处理**：对已有 1089 条短 note 区分“要求/计划/已确认/不可达/未知”，先人工审全部 43 条 regex 阳性及 A1 的全量 note，拒绝以动作是否 dense 决定是否审声明。正常组也评分。H3 `.511 > .275` 只说明优于这条 A0，不能证明它没有误抑制某个原本可执行的升级。

## 4. R3（阻塞）：在线证书包含策略指令与错误确定性，A0s 排除不了这些解释

`agent_cert.py:48–172` 同时给出：夜间全体 600、16 点后不开 dense、白天全听到才尝试、怎样降档/何时等待、应当怎样写 note。它还新增具体 backup 几何常量；A0 公共 system prompt 只有 very sparse backup，未给 1200 s/600 s 的完整常量。因此 A1 对照的是**专家策略文本 + 解释/措辞模板 + 额外常量**这一包输入。

A0s 只增加 pending 列表/核对一句话。A0s 不追平 A1 能排除该具体清单足够的解释，不能排除普通 dayfeed/通信确认规则的清晰 prompt 足够，更不能证明增益与提示工程无关。专家规则文本作为一种实现可以有用，但论文要按实际干预命名。

“证书”还有两处逻辑越界：

- `heard<n && applied<n` 只能表示尚未获足够确认。它不能证明回传不通、部分收据必来自备用腿，或发命令一定不可达；R2 的重放已有反例。
- 每个黑夜时刻都断言剩余黑夜 dense 负载超过满电池。例如临近日出剩余 1 h，采样项仅 `12 × .00047 = .00564 Wh`，不能由 `cap=.05 Wh` 推出必死。禁止整夜 dense 是保守规则，不能把每次局部判断都称为物理不可能证书。

现有三个所谓证书也没有统一执行接口：r33 离线按 oid 枚举机会；节点 purge 用固定 P；A1 在线生成整网文本、没有逐 oid 的机会排除见证。共享“证书”名称不构成同一方法贯通的证据。

离线无槽证书也要保留条件：`r33_h6_compile_cert.py` 在 h6 已使用 `OUT_HI=20h`，所以提前 7.2 h 依赖已知的未来不可用区间，不能说仅凭 backup 几何即可预测未知中断。只知道“现在断链”不足以证明任一未来 deadline 前不会恢复。其 602 条还包括 14 条恢复边界义务：枚举的 backup slots 排除 h20，但另一套 `opt_slot()` 允许 h20 主路；这些义务在本次轨迹没交付，不等于结构上绝无交付机会。应区分条件性不可行、观测零误报与模型内证明。

**最小处理**：先把规则建议与可证明事实分开。追加对照应为“同常量、同普通策略说明/输出约束的 A0s”，再比较额外的结构化证据；无需新模型谱系或全量网格。若普通说明追平，保留系统集成结果，撤掉独立证书增量。

## 5. R4（阻塞）：100% 网关归因使用了局部不可见与未来证据

论文 p.12 的 RQ2 对应 `r32_e1_cert.py`：

- `by_nm` 从 `inst.log.samples` 构造，覆盖所有节点实际采过的样本，包含从未向网关报告的记录；`taken_at <= t` 不等于观察者在 t 已知。
- 回溯分支 `heard_any` 只检查 `heard_at is not None`，没有 `heard_at <= gateway_received_at`。
- `gt_seg()` 与证书共享近乎相同标签分支。没采到直接记能量，最终某时刻听到却错过 deadline 直接记容量，并未排除策略原因与接入迟到。

独立重跑 seed0 复现 `3025/7560`。升级义务中有 **427 条匹配样本在 72000 s 后才被网关听到**，例如 `gw0:rainfall:59400` 到 72600 s 才 heard，却已被 72000 s 的回溯分支计入。650 条义务的匹配样本存在 deadline 后才 heard 的情况，故“最终 heard 非空”也不足以证明接入段及时完成。

无报告时，“节点没采到”和“采到了但未上传”本来就不可辨识；这正是项目原始 G5 约束。实现越过观察边界后得到 100%，不能证明破解了 G5。

**最小处理**：把现结果降为离线全局诊断。合法在线归因用网关已收到的逐记录/明确状态证据，无法区分的保留集合或 unknown；评估证据覆盖率与已判定部分的准确率。不能为了恢复 100% 添加免费采样历史信道。

## 6. R5（阻塞）：purge 正增益尚未建立相对 deadline expiry 的新颖性

`network.py:407–425` 的完整判定是：

```text
d(s) = (floor(taken_at / P) + 2) P
delete s if d(s) <= now; retain all others
```

它不读取回传槽、结构不可行证书、义务 ID 或节点已知的动态任务版本；`P` 取构造时的 `obligation_period_s`。这可以直接表示为记录的绝对 expiration，或 `TTL(s)=d(s)-taken_at`。当前实现在节点端没有反向跨段消息。网关版本调用 `_node.ack()` 则使用现有免费同步清缓存抽象，并未实现可靠的跨段终止协议。

RFC 9171 §4.3.1 的 Lifetime 表示应用数据不再有用的时刻（以相对创建时刻编码），§5.5 在到期时要求删除；RFC 5050 §5.5/§5.13 也定义到期与释放保留约束。[RFC 9171](https://www.rfc-editor.org/rfc/rfc9171.html#section-5.5)、[RFC 5050](https://www.rfc-editor.org/rfc/rfc5050.html#section-5.5)。TTL 不局限于与业务无关的任意包龄；绝对 deadline 与相对寿命可互相转换。“custody 是正向、本文是反向”不足以排除普通到期删除这一直接基线。

因此，EDF 不删除、latest-only 丢得太多，是两个有用对照，却没有检验**按同一 deadline 过期删除且保留未过期记录**的普通基线。先做语义等价核对；如果相同，不能把相同算法另命名后再跑大量种子当成新增机制。

收益依赖“中心确认前，节点始终从最老记录重传”这一具体应用层设计。论文把它称作 standard link semantics，却未给该组合在目标部署中的来源或普遍性依据；LoRa Class A 的接收窗口约束本身并不规定这样的应用缓存纪律。网关已可靠接收后转移保留责任也是应讨论的普通架构选项，不能仅按正向/反向措辞将其排除。

另有两个边界需修正：“保留一切可挽救记录”只对当前固定 P 的定义成立；多义务/旧新版本重叠时需要所有关联义务的期限，当前代码未处理。评分允许 `received_at <= deadline`，purge 却在 `now == deadline` 删除，最后一 tick 能否送达需要统一事件顺序。不能从绝对时间比较本身推出零误删。

**保留的 insight**：仅在网关抑制过期发送而不释放源端修复缓存，会把成本转回接入；节点期限清理解除这个耦合。它可作为具体 failure analysis 与标准机制适配结果。它是否承载新算法/新协议贡献，仍取决于 expiry/custody 基线后的剩余差额。

## 7. R6（阻塞，但可只改文）：对称资源干预没有证明最优前沿

论文 p.6–7、10 与摘要/结论仍把经验比较升级为 universal bound：

1. `r30c_walls.py` 同时改变容量与 `dayfeed→comply` 策略，未求解每个放宽可行域内的最优控制。对称分母便于比较，不提供上界证明。
2. `r34_joint_upperbound.py` 的 energy-relaxed 臂在中断内也收不到升级配置，所以与 base 同为 202；这说明同一任务传播门使该干预不起效，不证明所有合法上传/选包/控制策略都至多 202。
3. 离线 EDF 选择 420 个 oid，仅 9 个被线上交付，是**被选集合交集**；线上另交付了其他 oid。它不是“420 的最优上界坍缩为 202”的计算。
4. maxcov 贪心、若干 MPC 参数与纯本地昼夜规则，都没有包含全部合法策略的最优性证明。pure-local .360 与几个中心臂接近，也不构成全体中心控制器的上界或统计等价证明。
5. 四标签的 `else:S_cap` 保证零未分类残差；不能把分类完备性当作所有残差均物理不可改变的证据。

**推荐直接收窄**为“在这些策略与运行条件中没有测到稳健增益；资源干预定位了若干限制”。不要求为挽救前言新建大规模联合求解器。继续研究/写作无需先证明通信调度已无解。

## 8. R7：安全、信息与完成度的其余关键边界

- `network.py:312–339` 的 L0 只按时钟把 300 换成 600，没检查 SoC/剩余负载，也没有能量不变集。它证明所测三种子无死亡；不能在持续阴天、更小初始电量等条件下普遍保证生存。`.05 Wh` 与吸收死亡是压力实例假设，不能借用标准名称暗示典型部署。
- r39 使用 scripted decider；r38 的 A1 未串接 `EnvelopeDecider`、`local_floor` 或 purge。故“r38 剩余 4 死已经被 L0 清零”和“完整 Agent+L0/L1/L2 同台验证”没有直接证据。不同策略实验的 0 不能填入这四个反事实死亡。
- Agent 在 `t=0` 观察到完整未来 schedule（`agent_mission.py:329`，首条 trace 可见 h6 升级）。它是中心预知、网关延迟获知的混合设定，不能称中心运行时首次收到未知任务。要保留动态授权主张需按 issued_at 门控中心内容；预告任务可直接如实命名。
- 论文称所有 routine window 半开；代码 `half_open_after_first` 保留首段闭区间，只对变更后段半开。不要为修文重写历史分母，先声明实际评分语义。
- `r37` 的“send-promise precision”只是按期到达 / 已到达记录；基线发送一个过期记录不等于它声称会按期交付。应称 deadline-valid delivery fraction，并明确分母不含未抵达/重复尝试的成本。
- p.13 称 seeds6/7/8 从未用于开发不实；r07/r20 已使用 6–9。可称本次机制扩展验证，不称全项目未见留出。
- commands_refused 在中心准入失败时计数；拒绝前未必占用 Class A 空口。不能用拒绝数下降直接宣称无线/卫星计费下降。

## 9. 论文组织与文献质量

## 10. 收束决策

保留 paper objective，暂停 submission-ready 宣告。当前最有价值的下一步是**在同一实例内把证书与普通安全规则分开，证明它在合法信息下是否还有独立作用**。顺序见修订表：先无 API 地重评已有声明与证据边界，再处理 expiry 等价和普通规则文本对照，最后才决定是否值得追加少量真实 Agent 运行。

可检验的证书条件应写清：给定观察者已收到的历史 H 与公开假设 A，只有对所有与 H、A 相容的执行都不可完成，才输出 infeasible；否则输出 unknown/未确认。单纯没收到回执、某规则没完成、部分节点没上报，都不能替代这个条件。这会降低“100% 全段可知”的读数，却使论文与原始 G5 约束一致。

本轮不建议换场景、换模型、再扫大网格，也不建议因为当前主张未闭合就放弃 Agent 与通信的结合。先守住这次已经复现的收益，再检验剩余增量是否属于一个可明确说明的新方法。
