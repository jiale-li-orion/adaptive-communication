# 收敛评估：Execution-Grounded Obligation Runtime

日期：2026-09-19。基于 `e8ff1c4`、[doc51 独立审查](51-independent-review-paper-v06-2026-09-19.md)及用户提供的 GPT 收敛提案。**采纳一个 runtime 的组织方式；保留其机制假说；不据此宣布完整实现、独立新颖性或实验闭环。** 本轮只形成研究决策，不修改仿真、结果或 `main.pdf`。

## 1. 采纳的主线

用 **Execution-Grounded Obligation Runtime** 统一工作是合理的。任务的采集、接入、回传、中心确认存在执行依赖；配置与未确认缓存又会跨越控制失联持续生效。按 obligation 关联这些执行状态，能够把现有 failure analysis、期限清理、本地安全规则和 Agent 接口放在同一条论证中。

目前最有支撑的研究对象是：**间歇通信下，持续存在的执行状态应当保留多久、继续消耗什么资源，以及哪个位置有证据和能力终止其作用。** 已有两条路径体现了这一对象：

- 未确认记录继续占用节点修复批次，把回传侧的过期状态变成接入侧阻塞；节点期限清理改善交付。
- 已生效的密采配置持续消耗能量；依赖中心稍后降档会受回传和 Class A 机会限制，本地规则能在所测条件下阻止耗尽。

两者可以共用任务依据和证据语义，但操作不同：释放重传状态不会撤销已经生效的配置，停止配置也不会补回已经漏采的观测。论文应保留这种区别。

采用如下组织：问题与执行链 → 有限信息下的义务状态 → 状态释放与本地约束执行 → 机制对照 → Agent 接入验证。经验前沿放在问题刻画中；授权内重编译是接口用途；真实 LLM 是系统消费者。名称、组件数量和贡献分组无需另开实验决定。

## 2. 三处会改变技术结论的修正

### 2.1 Projector 表达可知边界，不承诺随时给出唯一失败段

`{feasible, S_energy, S_access, S_time, S_cap}` 混合了履约状态与原因，且漏掉 `unknown`。没有观测不等于没有采样，没有确认也不等于命令未生效。建议在概念上分开：

- **履约判断**：已确认完成、待定、给定假设下不可兑现；若提供 feasible，附上支持它的执行方案和适用假设。
- **依据**：观察者、实际接收时间、相关任务版本、假设与可辨识的阻塞段；证据不足时原因保留 unknown 或候选集合。

这不要求实现通用求解器。现有槽几何能够支持哪些条件性结论，就输出哪些；其余保留待定。`first blocking segment` 仅用于证据确实能区分顺序和原因的情形。

doc51 已指出 r32 的 2136/2136 使用全局及未来证据，不能支撑合法在线归因；r33 的 7.2 h 提前量依赖已知不可用区间。它们不能直接替新 runtime 背书。修复信息边界之后，报告判定覆盖率和已判定部分的可靠性即可，无须追求全段 100%。

**由此得到的设计 insight：无法确认整个任务能否完成，仍可能足以决定某项执行必须停止。** 例如，节点知道记录的有效期限已经过去，并不需要先诊断远端究竟为何失联，便可停止该记录的无价值重传。判断局部处置所需的证据可以少于完整根因诊断所需的证据。这是从现有现象推出的设计方向，尚不单独构成新颖性证明。

### 2.2 保留 lifecycle 机制，但不能用 certificate 名称越过 expiry 对照

当前 `network.py` 的节点 purge 只计算 `d(s)=(floor(taken_at/P)+2)P`；它不消费 projector 的逐义务证书，也没有实现新的反向释放消息。A1 的在线文本、r33 的离线枚举和节点 purge 尚未通过同一个义务接口贯通。因此，**certificate-driven state reclamation 可以作为拟议语义，不能写成现有系统已经证明的机制链。**

固定周期下，当前清理规则可直接表达为普通记录到期删除。RFC 9171 的 Lifetime 与 Bundle Expiration 已覆盖有用期限及到期删除：[§4.3.1](https://www.rfc-editor.org/rfc/rfc9171.html#section-4.3.1)、[§5.5](https://www.rfc-editor.org/rfc/rfc9171.html#section-5.5)。与 FIFO/latest-only 的正增益继续保留；该增益尚不能排除同期限 expiry 已经覆盖全部机制。

若采用 obligation 作为主对象，释放条件应对应**该执行状态所支持的、仍有效的全部已接受义务**。只证明一个 obligation 已过期，不自动证明记录对其他任务也无价值。仓库已有任务变更，先核对其真实关联与节点可知版本，不为制造新颖性另造任务。释放传输状态后，失约事实仍留在任务账本和评分分母中。

这里允许系统贡献建立在标准原语上。需要说明并验证标准原语怎样通过任务依据、证据和执行位置组合成有用系统；不要求 expiry、本地能量规则分别成为新算法。

### 2.3 Locality 是可执行条件，不能只剩距离或一条时延不等式

约束的执行位置同时取决于可得证据、授权/能力和剩余安全余量。可用下式表达设计条件：

\[
\operatorname{evidence\_available}(l,c)
\land \operatorname{authorized\_capable}(l,c)
\land D_{\rm observe+decide+act}(l,c)<M_c(t).
\]

其中 `M_c(t)` 是从当前时刻到违规前的剩余余量；延迟与余量都使用持续时间。同一套假设下的保守边界才可能支持保证，经验均值仅支持设计评估。位置还可能同时包含本地最低保护与中心任务协调，不能把“最低层”写成普遍最优位置。

R39 支持所测条件下将夜间规则放到节点的作用。当前本地门是时钟规则，尚未证明任意采能/初始电量下的安全不变量。L0/L1/L2 可以继续作为架构；不必为这一轮收敛补普遍安全定理。

## 3. 调整论文因果顺序

**执行层研究不依赖先证明调度已无优化空间。** 即使未来更好的调度提高服务，未确认缓存仍可能滞留，已生效配置仍可能在失联后持续耗电。它们是可以独立验证的执行问题。

因此，删去“强基线和全知策略已封死全部空间，所以只剩执行语义”的论证依赖。前沿实验按其实际求解范围报告，说明已测策略的效果与瓶颈即可。这样既保留已有工作，也避免任何新调度基线都能推翻整篇论文的动机。

建议使用以下主张作为**后续实现与验证目标**：

> 我们研究一种以监测义务为依据的执行 runtime：根据各位置实际可得的证据，管理跨段保留与重试状态，并在来得及干预的位置执行本地约束，降低间歇通信中无效持续执行造成的资源和服务损失。

Agent 负责使用接口规划任务，运行时负责其明确实现的执行约束。无需证明 LLM 不可替代，也不需要再扩一条 LLM 推理算法贡献。

## 4. 当前证据与下一步判别

| 部件 | 可以保留 | 下一步真正需要分辨的事 |
|---|---|---|
| 期限清理 | 指定缓存模型中，相对 FIFO/latest-only 的交付改善；doc51 已复现主点 | 同期限普通 expiry 是否逐决策等价；不等价时差异具体来自什么 |
| 本地安全门 | 所测配置下的部署位置效果 | 相同本地规则作为共同底座后，runtime 是否另有作用 |
| Projector | 有明确假设的结构判定；有限证据下的设计语义 | 合法观察下能判定什么、多少，哪些只能 unknown |
| Agent 接入 | 现有三臂作为实际输入包的系统表现 | 同常量、同普通规则和输出协议后，结构化执行依据有无独立增量 |

沿用 [doc51 的最小执行计划](../../s8-report/review-v0.6/experiment_todo.md)，不再开新网格。第一步用现有代码/轨迹完成 expiry 等价和局部证据核对；随后只有仍有独立作用时，才做同能力的普通组合对照：**同期限 expiry + 相同节点能量门 + 持久配置确认**。共享可观测信息、任务授权、资源与解析处理；先固定 planner 隔离执行机制，Agent 验证另行比较。

普通组合可以充分调优，不能故意缺少某条容易补齐的规则。若运行时仍改变行为，应落盘一条完整见证：合法证据 → 不同处置 → 真实释放/保护的资源 → 新增按期服务或减少损害，同时记录误释放与有益动作误拒。只减少诊断词或改变 note 不构成业务增量。若同能力普通组合与 runtime 等价，就承认该部分是标准机制的系统适配；无需用更多种子掩盖等价，也不据此关闭其他尚未判别的系统问题。

本轮决定：**采用 obligation runtime 的统一叙事；把上述三处修正纳入设计；保留正结果；暂停“完整新机制已闭环”的表述。** 不重命名代码、不补第四组件、不调用 LLM、不重跑实验。`main.pdf` 的证据修订仍按 doc51 待办执行，本记录不替代那些修订。
