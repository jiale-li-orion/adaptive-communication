## 2. 信息边界修复：非预知任务视图门控（doc38 §3）

### 2.1 问题

`joint_run` 旧实现把完整未来 `mission_schedule` 在初始化时展开成义务全集并直接 `adopt` 给现场 `JointControlPlane`；网关选包器因此在**没有任何任务消息接收事件**的情况下，就用上了 h6 之后才授权的 300 s 密义务截止期。doc38 的函数级见证：n00/displacement、taken_at=21600+600 的样本，仅替换预装任务表，最紧截止期就从 22800 变成 22650，全程无任务接收。

### 2.2 选定的信息模型

按 doc38 §3 的二选一，在线叙事明确选**"运行中新增授权"**：

- 任务表更新是一条独立的**网关本地通知**，只携带该段的 `(start, period, level)` 三个整数；
- 它与中心→网关的命令**共用同一条主回传**、同一个 `path_available(hour, 0)` 可达性，中心自段生效起持续重传，**首个主回传可用小时到达网关**；
- **不走北斗备用腿、不抢数据空口**，因此任务通知何时到达与 comply / dayfeed / ignore 等策略是否选择加密完全解耦；
- 记录四时间戳 `issued_at / center_received_at / gateway_received_at / node_applied_at`；达不到的环节不伪造完成时间。
- 预告 / 预装场景是另一条实验路径（此时普通网关也应持有全集），本轮不混用。

### 2.3 实现

`MissionViewGate`（mission_view.py）持有：

- `truth_routine`：与独立 scorer 同源的分段真值义务（变更后段半开，见 §3）；
- `belief_routine`：现场初始信念 = 首段节奏 sparse(600) 全程外推的**闭区间**义务；
- `initial_view` = 初始信念 + 全部非 routine（event）义务；
- `segments`（仅 k≥1 段，含 notified / gw_at）与 `segment_ops`（移除同区间旧信念、加入真值）；
- `poll(t_s, path_available_fn)`：对 `start ≤ t` 且主回传当前可达的段标记到达；中断窗内不发布。

`JointControlPlane.adopt(..., mission_gate=None)`：gate 存在时 `_obl_index` 用 `initial_view` 构建，否则用全集（默认 bit-identical）；`backhaul_forward` 每拍开头调 `_pump_mission(t_s)` 驱动发布，发布用 `self.path_available(h, 0)` 判定。`joint_run` 仅在 mission 多段（len≥2）时构造 gate，单段 / 固定任务 gate=None。

## 3. 采样语义版本化（doc38 §4）

- 旧语义保留为默认：`Obligation.matches` 闭区间 `[lo,hi]`，一份边界样本可同时满足相邻两个窗口——这是合法的"**窗口覆盖**"语义（"每个 300 s 窗口内有样本"）。
- 新增 `Obligation.match_half_open=False`；置真时用 `lo ≤ taken_at < hi`，配合分段义务表达"**每 P 秒一份独立新观测**"：一份边界样本只归属一个窗，于是更疏的采样无法在网格边界点凑出更密的频率。
- `piecewise_routine_obligations(..., half_open_after_first=False)`：**首段（变更前旧任务）闭区间，k≥1 段（新任务版本）半开**；单段 / 固定任务仍委托原闭区间构造。`joint_run` 对 mission 多段自动传 `half_open_after_first=True`，单段与全部固定任务 / R20 不变。
- 纠正了 piecewise 的注释：义务窗（评分分母）从**任务授权 / 生效时刻**段起点起算，**不随某方法命令实际送达的快慢后移**；现场未及时收到 / 采用新配置记执行失败或共同通信损失，不改变分母。执行器"何时可见"由 MissionViewGate 另行门控。
- 采样频率、上报（上传）频率、中心新鲜度是三个独立字段 / 指标，本文评分只处理采样的独立观测语义；是否把采样与上报解耦为两个可分别调节的动作，留待顺序 3 的机制设计，不在此预设。
- 旧 v1.1 / R20 评分**不追溯改写**；doc36 的"错开 150 s"处理在新任务版本中退场（半开主口径已干净），错位仅保留为相位敏感性。

## 5. 缺采归因与候选 C 的"可改变损失"假设（未定）

升级段 h6–h36 跨"白天—夜—白天"，叠加中断 h4–20 与 Class A 生效延迟，2119–2588 的缺采由三类性质不同的原因构成，**当前只做分解、不下"不可兑现"结论**：

1. **共同通信损失**：任务表与配置命令在中断后 h20 才到现场，升级段前约 14 h（h6–h20）现场在信息意义上仍按旧任务运行——这一段任何在线方法都无法据未送达的要求行动（doc38 §6：全中断来不及传任务首先是共同通信损失）。
2. **策略选择（dayfeed）**：命令 h20 生效时为深夜，dayfeed 只在标称白天（hod 6–18）加密，故 h20–h24 仍不密采；这是该启发式的选择，不是物理约束。
3. **能量约束**：comply 等整夜 300 s 密采致死 13 台，证明"h20 后整夜全密采"不可行；但"整夜全密采不可行"不等于"任何选择性加密都不可行"——在能量预算内对**最紧迫义务**选择性加密 / 补采是否能减少缺采而不致死，正是 doc33 候选 C（H1：按失约链路段修复正确控制层）与 doc38 联合 MPC 待检验的**可改变损失**，**r24 未给出判别**。

按 doc38 §6，"不可能兑现"需要可行域排除证书或限定模型证明；dayfeed / comply 没完成只构成"尚未兑现 / 当前不能保证"。假阴性需另交同初始条件、合法信息下的可行替代轨迹见证（顺序 3–4 处理）。
