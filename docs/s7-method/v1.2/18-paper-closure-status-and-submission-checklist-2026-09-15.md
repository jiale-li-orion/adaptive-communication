# Task v1.2 — 18 · 论文闭环状态报告与投稿前清单（阶段定稿）

日期：2026-09-15。承接 [17](17-ea-parameter-sensitivity-2026-09-15.md)。
本件回答一个问题：**"When Freshness Feedback Lies" 这篇论文现在闭环到什么程度、还差什么能投。**

## 1. 破局逻辑（为什么这条路成立，且不依赖"LLM 不可替代"）

最初的执念是"找一个只有 agent 能解、规则解不了的问题"，两次被证伪（v2gate 装包、C-send 发送侧）。
Astra doc07 把方向纠正为**联合通信执行层**，并接受"规则获益也是通信贡献"。本轮把它收敛成一个
**不依赖 LLM、但为 agent runtime 铺路**的完整命题：

> 在"接入段／回传段可用性分离 + Class A 控制延迟 + 弱采能"的灾前监测网里，**控制器看到的端到端
> 新鲜度会被它无法作用的回传段污染**；用这个被污染的 AoI/SoC 去闭环采样-上报，在松任务区失稳致死、
> 在紧任务区被合法静态配置前沿 Pareto 支配。正确的通信执行层是"按义务紧度选静态工作点 + 零拷贝
> 主备 failover"，反馈若要闭环必须锚定**网关本地可交付性**而非端到端年龄；工作点切换是任务级风险
> 状态驱动的慢编排（上层 agent/MPC 的合法职责），不是逐拍 AoI 闭环。

这是一个**反馈信号定位**的系统贡献：不是"闭环不好"，而是"在哪算、用什么量闭环"的边界理论，
并且明确划出上层 agent 的落点（C4）。
