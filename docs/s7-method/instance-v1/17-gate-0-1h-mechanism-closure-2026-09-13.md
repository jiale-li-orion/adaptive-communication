## 一、三个真实的实现缺陷（都已修，都影响过读数）

### 缺陷 A：`prune` 的时间单位不一致 → 过期列结构性死亡

`ControlPlane.prune(node_id, hour)` 把参数叫 `hour`、按小时索引比较，而
`DownlinkMessage.expires_at` **在全仓库范围内都是秒**（`t_s + 6*3600`、`now_s`、`10**9`）。
实例里 `expires_at = t_s + 21600`（例如 25200）与小时索引（0…12）比较 ⇒ **永不过期**：

- `downlink_expired` **恒为 0**——一条结构性死列（"看起来有值、永远不动"）；
- `intent_ledger` 里那些没送达的命令全部落在 `queued_left` 而不是 `expired`。

**修**：参数改名 `now_s`，统一按秒比较；`uplink` / `_deliver` 收到的小时索引由它们自己
`× 3600` 后再传（**签名不变，旧 monitoring 约定保留**）。

### 缺陷 B：过期只在投递路径里被检查 → `in_flight` 可以永久为真

`prune` 的文档写着"过期是时间的性质、不是窗口打开的性质"，但它**只在 `uplink` 与 `_deliver`
里被调用**。接入中断时 `tick` 在到达 `uplink` 之前就 `continue`，于是那条规则**一次也没执行**；
而 `CenterView.in_flight` 定义为"该节点队列非空" ⇒ **一次足够长的接入中断让 `in_flight` 永久为真**，
每条策略都在读电量之前 `continue` 掉该节点。`network.py` 里"留在队列里会让 `in_flight` 永远为真、
中心永不重发"这条注释**正是为此写的**——但它只处理了**扣留件**，没处理**送不到的命令**。

**修**：`Instance.tick` 开头对每个节点按时间清理一次，与投递路径无关。

**影响面（实测，`contcfg` 六格 × 四条臂）**：`downlink_expired` 从全 0 变成 2–27；
**业务列几乎不动**——缺采在全部 24 个格子里**逐位不变**（0.6/0.8/0.0/10.5/8.4 …），
交付变化 ≤ 1.9 条。⇒ 它是一个**真缺陷**，但**不是** `out3` 损害的成因。

### 缺陷 C：跳过原因在日志上同形

`plan()` 里四处 `continue` 全都表现为"中心没有生成意图"，含义完全不同。
**修**：新增 `CenterPolicy._skip(reason, node_id)` 与 `skip_report()`，
在五条策略的四处分支上分别记 `in_flight` / `dwell` / `no_soc` / `at_target` /
**`at_target_evidence_stale`**（后者专指"按一条过期证据维持了现状"，与 `at_target` 同形但含义相反）。
**纯诊断，不参与任何判断**。另新增 `CenterView.soc_age_s()`：证据年龄按**源时刻**算，不按接收时刻。

## 二、闸门问题：`out3` 为什么没有生成降档？——**两个候选解释都被排除**

| 候选解释 | 实测 | 判定 |
|---|---|---|
| "无证据不下发"（`soc is None`） | `out3` 下 `no_soc` 只占少数；**完全无读数的 `out0`** 才是 `no_soc` 压倒性（10141 / 总 10917） | **排除**。`soc_max_age_s=None` ⇒ 缓存读数**不会**因失联变成 `None` |
| `in_flight` 永久为真把中心静音 | 修好缺陷 A+B 之后中心**恢复下发**（h7、h8 都生成了意图），但**缺采一条没变** | **排除为成因**（缺陷本身是真的，见 §一） |
| **证据陈旧且仍然"健康"** | 中心最后一条读数来自 h3、值 **0.0185**（健康）。此后它在 h7/h8 生成的仍是**加密配置的重申**，不是降档 | **成立** |

**真正的机制**：策略把**3 小时前的 0.0185** 当成当前电量 ⇒ "健康 ⇒ 加密"这条规则被反复
应用到一条过期证据上 ⇒ **从不降档**。策略里**没有任何规则把"证据年龄"当作保守化的理由**：
`soc_age_s()` 是本轮才加的，而没有任何一条现有策略调用它。

⇒ 正确的表述是计划 §0 第 5 条要求的那一版：**安全性取决于仍在生效的负载、剩余资源、
以及能否及时改变它**。"谁写的"只是代理变量，**撤销**。

## 三、复现修复（计划 §0 第 4 条）

第一版 `trace_seed_timeline.py` 把 `contract=True` 写死去重放 `exec_layers=naive` 的结果，
并且**静默丢掉了 `backhaul_burst` / `uplink_burst`**——也就是说"重放"跑的是 **i.i.d. 链路**，
而登记结果是**南极突发链路**。三个业务数字偶然对上完全不足以发现这件事。

现在：

1. `exec_layer` **从该 `(arm, seed)` 在结果文件里的那一行读**，不猜；
2. `config` 里每个影响运行的键**必须**映射到 `one_seed` 形参，映射不到就**报错退出**
   （第一版就是这样漏掉 burst 参数的）；`charge_min_c` 的字符串→`None`/`float`、
   `--energy-scale` 的预先相乘、`backhaul_burst` 的拆分**逐条照抄 `main`**；
3. 比较**全部嵌套字段**（业务/能量/通信/执行/账本），排除 `_trace`，不一致**非零退出**；
4. 登记行**缺少**后来才加的字段（`intent_reason`、`skip_reasons`）算**新增**、不算不一致——
   `rerun_from_config.py` 已经踩过同一个坑。

**逐字段重放结果（四条不同条件的登记行）**：

| 条件 | 与登记行逐字段一致 | 开 trace 后逐字段相同 |
|---|---|---|
| `contcfg_b1.0_out3`（naive） | **✓** | **✓** |
| `frontpolar_c0.05`（南极突发链路） | **✓** | **✓** |
| `long48_polar_fifo`（48 h） | **✓** | **✓** |
| `frontfit_c0.008` | **✓** | **✓** |

## 四、闸门退出物：一条精确到秒的 seed 7 / `n02` 时间线

`python3 code/analysis/trace_seed_timeline.py --tag contcfg_b1.0_out3 --seed 7 --arm ea_nb --node n02`
（重放自检两条都通过之后才采信）：

| 时刻 | 事件 |
|---|---|
| 0 s | 出厂配置 `采样 3600 s / 上报 3600 s`，SoC 0.0195 |
| 60 s | 中心生成一对意图（`set_sampling_interval=600`、`set_report_period=900`），**它当时看到的电量 0.0195** |

## 五、保留 / 撤销清单

**保留**：
- `out0`（从不介入）⇒ 缺采 0、不可供电节点小时 0；`out3`（介入后失联）⇒ 缺采 10.5、
  不可供电 **14.22 节点小时**（**单位更正：`deficit_h` 是跨节点累计不可供电时间的种子均值，
  是节点小时，不是 Wh、也不是单节点持续时长**）。
- `bias1.0` 与 `bias3.0` 在 `out3` 下**逐位相同** ⇒ 这一档的损害**不由诊断偏置造成**。
- `aoi` 在同条件下缺采 0 ⇒ 仍是硬反证。

**撤销**：
- "没有生成降档是因为无证据不下发" —— **撤销**（§二）。
- "`in_flight` 永久为真解释了缺采" —— **不成立**（缺陷真实，但不是成因）。
- "安全性取决于谁写的" —— **撤销**，改为负载/剩余资源/能否及时改变。
- 第一版时间线（`contract=True` + 丢 burst 参数）—— **作废**，已由严格重放替代。

**统计口径更正**：`noout` 基线为 `ea_nb` **150.9/168 = 89.82%**、`local` **88.15%**、
`aoi` **91.73%**；此前报告里的 91.5% / 89.0% 不用。
