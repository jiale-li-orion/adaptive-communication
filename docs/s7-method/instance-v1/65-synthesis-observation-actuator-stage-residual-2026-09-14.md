# 综合：观察 → 动作 → 受影响环节 → 期限 → 剩余余量

日期：2026-09-14。本文把 repo 到目前**全部**实例层结果按一条判据重排，
并给出两种后续路线的边界。它**不引入新实验**；引用的每个数字都能在
`results/` 的已登记文件里找到，出处逐行标注。

---

## 0. 统一判据

$$\boxed{\ \text{useful intelligence}\ =\ \underbrace{\text{relevant observation}}_{①}\ \times\ \underbrace{\text{causally effective action}}_{②}\ \times\ \underbrace{\text{enough time}}_{③}\ \times\ \underbrace{\text{residual headroom}}_{④}\ }$$

四项里任何一项接近 0，planner 再"聪明"都不产生业务收益。**这不是格言，是本文 §1 那张表逐行算出来的。**

其中「② 因果有效的动作」需要一个**精确**的说法：

> 一个动作是**因果有效**的，当且仅当它**能改变当前承重环节的状态**。
> 「信息更细」与「状态更语义化」都**不**是充分条件——
> 一个更聪明的 observation 作用在**非承重环节**上，只会**把失败往后搬**。

## 2. 因果链：为什么 P1 的"改善"没有转化

doc 64 给出一条**精确**的结式（在 v1.1 的 store-and-forward 语义下，
**161,280 条义务级判定、不一致 0 项**）：

$$\text{delivered}_i=\mathbf 1[\,h_i^\*\le B(d_i)\,],\qquad B(d)=\max\{t\le d:\ \text{backhaul}(t)=\text{up}\}$$

据此，P1→P2 之间的因果链**是**：

```
候选放慢上报
  → 一部分义务的 h* 变早（P1 的 +6.45，阈值用的是 d）
  → 但更重要的是一部分义务的 h* 被推后
  → 被推后的那批越过 B(d)（而不是越过 d）
  → 交付净减（新增 0 条、丢失 58 条）
```

**两个中间量必须分开**：

* P1 的头条「准时到网关」用的是 `h* ≤ d`；
* 真正承重的是 `h* ≤ B(d)`，而 `d − B(d)` 的均值是 **1245 s / 3073 s / 1245 s**（P0/P1/P2），中位 0。
* 落在 `(B(d), d]` 这条**无效带**里的义务：`fixed300` 只有 0.1–0.9%，而候选有 1.4–2.5%
  ⇒ **候选的"准时"增量全部进了这条带**。

**这条链同时解释了 `pacing_backlog900_300` 为什么赢**，而且理由**不是**"它语义更聪明"：

```
回传受阻 → 网关 oldest_pending_age 增长 → 上报放慢 → 少花上行/能量
回传恢复并清空 → 受阻信号消失 → 上报回到 300 s → 新鲜样本很快进网关
```

即它在做 **下游拥塞 → 上游 offered load**，这本来就是 backpressure 的强项；
而 `oldest_pending_age` 是 `B(d)` 的**滞后代理**——它观测的正是承重的那一跳。

## 3. 一条**必须守住的**任务边界（否则会假装 v1.1 还有一块没试）

**当前 v1.1 的网关→中心这一跳没有有限容量的调度动作。**
读码核实（`opportunity.py:419`）：链路一旦 up，`backhaul_forward()` 就把**当前所有**
`gateway_pending` 一次性交出去——**没有容量预算、没有包选择、没有优先级调度**。

因此在这个 task 内，动作

> 「让网关更聪明地选择这次回传机会发哪些 pending item」

**根本不存在**。要研究 gateway packing / EDF / deadline-aware backhaul scheduling，
必须先给这一跳加**有限容量或发送预算**——那是 **Task v1.2 的能力变化**，
**不能**把它包装成"v1.1 里还有一块没试的地方"。

**所以我在 doc 61 §7 留下的那个"下一入口（缓存／打包纪律与回传窗口对齐）"要撤回**：
它在 v1.1 里**不是**一个可执行的 control surface。

**一个具体的、已参数化但未接线的口子**（供 v1.2 参考）：
`ControlPlane.backhaul_delay_s` 机制存在（`opportunity.py:429` 的 `t_s - heard_at_s >= delay_s`），
但**实例路径不传它**（`network.py:721`），本档也没配 ⇒ **它现在是静默空参数**。
接上它会让 `B` 依赖 `h*`（"太新的条目这一批带不走"），从而产生**真实的时序张力**；
**但它仍然不产生"机会之间做选择"的自由度**——那需要容量/预算。

## 4. 两个具体建议（按用户 2026-09-14 的判断）

**① `oblig_slack` 这一类不要重开成完整分支。** 两层理由都成立：
任务定义使剩余余量恒落在 `(period, 2·period]`，而 `command_delay ≤ period` ⇒ 候选**解析退化**
（doc 61 §3，已钉进第 [36] 组测试）。**这不是负结果，是没有 intervention contrast。**
反向的错误也要避免：**不能**为了让它激活去重新挑阈值——那就是看到支持集以后人工切一刀找 winner。

若要为审稿完整性补一条 baseline，**只补一条**、且必须是**非调参**的：
由物理量直接导出，例如

> latest-safe-action boundary：`now + report_period + command_effect_latency ≤ 该窗口的期限`

**不扫阈值、不试多档**。它赢了只能算**普通 deadline-aware baseline**，输了就关闭；**不重新成为主线**。

**② P0 不需要补 336 h。** 当前 P0 的价值是把"信息待遇"与"执行循环"拆开（doc 63）：
48 h 的 event 列**不承载信号**（0/20/0 全平），96 h 只作时间敏感性；
它**不承载**主论文的 multipath claim。继续跑 336 h 只是在一个 A 层合成扩展上加数字，
**不改变方向判断**。

## 5. 两条路线（第二阶段才选）

### 路线 A：把 causal story 写成**实证/benchmark 论文**（v1.1 已足够）

题目形态是 **"When does intelligent control matter in intermittent sensing?"**，
**不是**"我有一个新 Agent 算法"。已具备的材料：

1. **source-grounded benchmark**（ChirpBox / LoRa-on-Ice 拟合、真实突发度、Task v1.1 契约）；
2. **分层 failure accounting**：采集 ／ 节点→网关 ／ 网关→中心三级，
   `heard` 与 `heard_on_time` 的区分（doc 55/59）、`received_on_time ≡ delivered` 的对账；
3. **"首次到达 vs 最后一次机会"的结式**（doc 64）——一条**结构性**判据，且给出**无效带**的量；
4. **层次错位**：intent → 实际生效 → episode → service 之间可以脱节（doc 47/49 的降档计数与 O0 同值）；
5. **突发度压缩 policy headroom**（doc 41：27/42 档任务短于平均坏突发）；
6. **"新鲜信息不保证业务收益"**（doc 63：ACK 省尝试/能量，但净效应被执行方式与停发规则改写）；
7. **"改善非瓶颈环节会把失败往后搬"**（doc 59＋64）；
8. **控制位置只有在观察/动作/瓶颈对齐时才产生收益**（doc 47：O2 正、O1 无/略负、O0 近零；
   doc 61：网关整体积压管用、逐义务语义状态不管用）；
9. **大量貌似合理的方法被机制实验明确关闭**（doc 51/54/61：固定臂通吃 → 公平版翻转 →
   候选解析退化 → 副本族目标变量不存在）。

**它的诚实边界**：第三列（新机制／LLM 专属收益）**仍为空**；
所以它是一篇**实证系统论文**，不能声称 method contribution。
**也要守住**：「关闭」的都是**具名子假说**，不是"所有 agent 方法无用"。

### 路线 B：若**一定**要有 method contribution ⇒ 设计 **v1.2**，但先找到**真实存在的下游动作面**

判据不是"为了 agent 加 complexity"，而是 doc 64 已经用因果证据说出的那句：

> **目前剩余 failure 在 gateway→center，而 v1.1 在这一跳没有可控动作。**

所以要继续研究方法，**必须给这一跳一个真实的 actuator**。候选动作面（用户 2026-09-14 列出）
——有限容量回传 ／ 双 WAN path selection ／ 卫星配额 ／ 网关包优先级——
**我尚未核实其中任何一个是否有合作方／设备／论文来源**；这条"哪个有来源就选哪个"的判据
需要在 v1.2 立项时**逐条查证**，本文不预先声称任何一个可行。

一旦有了容量或预算，才真正出现值得做的调度问题：

$$\text{which obligation}\ \times\ \text{which path/opportunity}\ \times\ \text{when}$$

**并且**它天然落在 doc 58 §4 圈定的那条结构差异上：动作是**持续配置**还是**直接发送**、
状态如何处理**两跳到达与不可即时纠正**。
doc 64 §6 已给出该问题的形式：控制目标是 `B(d)`（**未来、不可观测**），
所以这是一个**部分可观测下的时序**问题，**不是**"按剩余余量排优先级"的问题——
这恰好是与成熟 deadline-aware scheduling 的区别所在。

## 6. 新颖性边界（不重复 doc 58 §4，只强化一点）

Zakeri 等 POMDP（arXiv 2311.06522）已同时处理部分可观测、采能、采样/传输成本与不可靠信道
⇒ **这些因素的罗列不构成贡献**。本文系列能提供的、**可能**有增量的是两条**结构**差异：

1. **动作是持续配置**（改的是节点此后的行为），不是直接采样/发送；
2. **两跳到达且不可即时纠正**，且 doc 64 表明承重阈值是 `B(d)`（未来的机会）而非 `d`。

**但**：路线 A 不声称机制增量；路线 B 的增量**尚未被验证**。
**未做全文对应前不声称缺口**；规则 planner 同样获益**支持通用通信方法、不证明 LLM 必要**。
