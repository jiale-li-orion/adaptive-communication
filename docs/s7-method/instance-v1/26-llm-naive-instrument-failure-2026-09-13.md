# 真实 LLM naive baseline：**仪器失效，本实验没能回答预注册问题**

日期：2026-09-13。协议 `llm_naive_v1`（`sha256=11a0ce44…`）。基线 `5db8509`。

## 发生了什么

全量跑（3 条件 × seed 0 × 13 h）在**第一个条件结束后崩溃**——崩点是我自己的打印语句：
`episodes = 0` 时 `amp_intents = None`，而我对 `None` 做了 `:.2f`。**崩溃把 `adm_noout` 的
动作分布、service、tokens 全丢在进程内存里。已修**（统一走 `_fmt()` 处理 `None`）。

崩溃前已打印的结果：**`adm_noout`：778 次 planner invocation、0 个 semantic episode、0 闭合。**

## 决定性判读：**不是接口坏，是模型每次都选 noop**

修好后做 30 次调用的受控探针（条件**不变**）：

| 量 | 值 |
|---|---|
| `actions` | `{'noop': 30}` |
| **未下达动作的原因分类** | **`{'action_noop': 30}`** |
| **原始输出采样** | 5 × `{"action":"noop"}` |
| 解析失败 | **0** |
| tokens | 27/次调用（327 in / 6 out） |

原因分类里**没有** `node_not_in_view` / `no_valAM` / 解析失败 ⇒ **我的接口没有把合法动作误判掉**。
**模型是真的每次都回答 `noop`。**

（`service`：`adm_noout` 160.0/168、`adm_out3` 45.0/168、**`polar_c0.05` 0.0/168 且 AoI 为 `None`**——
最后一条与 §7.95 的发现一致：**polar 在 seed 0 下链路根本没有交付**。）

## 为什么这**不能**用来判预注册判据

`episodes = 0` ⇒ `amplification = 0/0` **无定义**。更根本的是：

> **我给模型的状态里没有任何"现在有事情不对"的信号。**
> 节点已经在 `sampling=3600 / report=3600`，而 `obligation` 只是一句字符串
> （"one routine report per 3600 s per node"），**没有逐节点的"新鲜度 vs 义务"对照**。
> 一个理性的回答就是"没什么要做的"⇒ **永远 noop**。

所以"零动作"**既不是"LLM 克制"、也不是"没有 planning amplification"**，
而是 **prompt 没给出行动的理由**。按预注册判据 1 直接记"scripted 发现没有自然迁移"
**会是错误的**——那会把一个**仪器设计缺陷**读成一个**关于 Agent 的结论**。

**这正是要防的那类错误的反面**：不故意把 LLM 弄傻，但也**不能把它放进一个不需要动作的世界里，
再把"它没动作"当发现**。

## 已确认不是问题的部分

- `thinking` 关闭有效、JSON 严格、无解析失败（`bad = 0`）
- 接口的 node id 校验没有误杀（原因分类可证）
- 成本口径：**327 输入 / 6 输出 token 每次调用**，与预估一致
- 崩溃**只发生在打印阶段**，仿真与调用链路本身是好的

## 下一步需要决定的事（我不擅自改冻结协议）

按我自己定的规矩：**协议一旦冻结，改它必须新建 `protocol_id` 并重跑**，不能原地改。
所以把问题交出来：

**选项 A（推荐）**：新建 `llm_naive_v2`，在状态里补上**中心真的知道**的两样东西——
① 逐节点的**新鲜度 vs 义务**（它最后一次被听到距现在多久、义务周期多少）；
② 逐节点的**电量与证据年龄**。**不添加任何"该怎么办"的提示、不添加策略智慧**，
只是把"现在有没有事情不对"这个**中心本来就掌握**的事实呈现出来。
然后重跑 3 条件 × seed 0。

**选项 B**：接受"在当前 prompt 下 LLM 从不动作"，把它记成**baseline 的失败**而不是发现，
并据此说明**这个 benchmark 的 naive-LLM 基线需要一个明确的 objective 表达**——
但这更像是 benchmark 设计问题，不是 agent failure。

**选项 C**：先补 scripted 的**"有动作"对照**（`aoi`/`ea_nb`）在同一 seed 下的 action 数，
确认"中心确实有可做的事"，再决定 A 还是 B。**这个最便宜，也最能防止我们误判。**

## 成本

全量跑到崩 ≈ 778 次调用；探针 3 × 30 = 90 次。**合计约 868 次 ≈ ¥0.9 峰值价**，
远低于 8 元上限。**余额未被这件事威胁。**

## 附录：v2 修了"义务可判定"之后**仍然是 30/30 noop**——根因不是仪器，是**目标不对等**

按选项 A 新建 `code/protocols/llm_naive_v2.json`（`sha256=7c4c8c16…`，`derives_from` v1
并记下 v1 的 sha256）。**唯一改动**：状态里补上 `obligation_period_s` 与逐节点 `last_heard_age_s`
（中心**上次收到**该节点报文距今多久，用 `report_at` 而非 `taken_at`），并把"超期规则"原文写进状态。
**没有替它算 `overdue` 布尔量**（那才是加智慧）。其余一切逐字不变。

**结果：`actions={'noop':30}`、原因分类 `{'action_noop':30}`、原始输出 5×`{"action":"noop"}`。**
**与 v1 逐位相同。**

### 根因（这次找到了）：**默认配置已经满足义务，noop 是正确答案**

- 义务周期 `obligation_period_s = 3600`，而默认 `report_period = 3600` ⇒
  **节点本来就每小时报一次，`last_heard_age_s` 基本不超期** ⇒ **没有事情需要修**。
- 那 scripted 的 `aoi` 为什么在同一 seed 下动手 **245 次**？
  因为 **`aoi` 的目标不是"满足义务"，而是"把 AoI 压得更低"**；
  `ea_nb` 的目标是**省电**（低电时拉长周期）。**它们的动作来自义务之外的优化目标。**

⇒ **这不是仪器缺陷，是目标不对等**：

> 我给 LLM 的目标是**满足义务**；我拿来对比的 scripted 基线优化的是 **AoI / 能量**。
> 在这个世界里"满足义务"的正确行为就是**什么都不做**，所以 30/30（以及全量 778 次）的 `noop`
> **是模型做对了，不是它失败了**。

**⇒ 预注册判据 1/2 在这个设计下根本无法被检验**：`amplification = #intents/#episodes`
在"目标要求不动手"时必然是 `0/0`。**要测 planning amplification，必须先把 LLM 放进一个
"确实有持续工作可做"的目标里**——而这等于**由 prompt 决定它的策略**，是一个**研究设计决策**，
不该由我单方面拍。

### 已经排除干净的三件事

| 排除 | 证据 |
|---|---|
| 接口误杀合法动作 | 原因分类只有 `action_noop`，无 `node_not_in_view`/`no_value`/解析失败 |
| 思考未关闭 / JSON 不严 | `bad=0`、原始输出全是合法 JSON、`thinking` 参数已生效 |
| 环境没有可做的事 | scripted `aoi` 在同一 seed 下 **245 次动作 / 67 episodes**（§7.95）——**有事可做，只是目标不同** |

### 需要用户决定

要回答"LLM 会不会把 transport 失败当成新的 planning demand"，必须先给它一个**会产生持续工作**的目标，
并且**用同一个目标的 scripted 策略作对照**（否则又变成不可比）。三个可选项：

- **A′**：把目标改成**与 `aoi` 相同**（把 AoI 压到某个阈值以下）。对照 = `aoi`。
  代价：prompt 里出现了 AOI 阈值 ⇒ 阈值从哪来必须声明（可用已登记的 `aoi` 参数）。
- **B′**：把目标改成**与 `ea_nb` 相同**（在满足义务的前提下尽量省电/保活）。对照 = `ea_nb`。
- **C′**：不加优化目标，改成**施加外部压力**（例如把义务周期调紧、或让默认配置不满足义务），
  使"满足义务"本身就需要持续动作。**这一条最干净**——它不靠 prompt 注入策略，
  而是让任务本身变成"有事可做"；但**它改的是 task 设定，属于用户明令要慎动的范围**。

**我的建议是 C′**，因为它把"是否有持续工作"交给**任务**而不是**prompt**，
从而避免"由我写的 prompt 决定 LLM 的行为、再拿这个行为当发现"。
但按纪律，改 task 必须先经用户同意。

## 附录二：加上"超期计数"后跑过首次超期点——**结果与预期相反：不是过度规划，是行动不足**

**我上一轮的判断也错了一半**：我说"默认配置已满足义务 ⇒ noop 是正确答案"。
但 v2 的义务是 **`last_heard_age_s ≤ obligation_period_s`**，而链路有丢包，
**超期会真的发生**。为了不再靠猜，我在策略里加了**超期计数**（状态里
`last_heard_age_s > obligation_period_s` 或 `seen=False` 的节点数），并跑到 **150 epoch（2.5 h）**：

| 量 | 值 |
|---|---|
| **状态里有超期节点的 epoch 数** | **150 / 150** |
| **最多一次几个节点超期** | **14**（全节点） |
| **`actions`** | **`{'noop': 146, 'set_report_period': 4}`** |
| semantic episodes | **1**（closed 1） |
| 解析失败 | 0 |
| service / AoI | 163.0/168 ；3299 s |

**⇒ 在"状态明确显示义务未满足"的每一个 epoch 里，真实 LLM 有 146/150 次选择 `noop`。**

**方向和预注册假设相反**：

- 预注册判据 1/2 问的是"它会不会产生**过度**规划（amplification ≫ 1）"。
- **实测是行动不足**：`#intents / #episodes = 4 / 1 = 4.0`，但**episode 只有 1 个**，样本太小不能承重；
  唯一稳的陈述是 **150 个 epoch 里只下达了 4 次动作，而全部 14 个节点几乎一直处于超期状态**。

**这是一种与 planning amplification 不同的 agent failure**：不是"把 transport 失败当成新的 planning demand"，
而是 **"面对明确可知的未满足义务，不去动手"**——而且它在能动手时是能给出合法动作的（4 次都成功下发）。

**必须记下的局限（不夸大）**：我的超期判据把 **`seen=False`（从未听到）也算超期**，
所以 `150/150` 里可能有一部分来自"从未听到的节点"，而不是"听到过但老了"。
**要精确区分，需要把 `seen=True and age>period` 单独计数**——这是下一轮第一件事。
在分开之前，**不能说"每一个 epoch 都有真正老化的节点"**，只能说"状态里一直有未满足义务的节点，
且最多时是全部 14 个"。
