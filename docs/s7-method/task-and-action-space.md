## 2. 技术手段对应真实断点（作为 runtime 的执行资源池）

| 层次与断点 | 优先技术 | 对本文的含义 |
|---|---|---|
| 节点到网关边缘覆盖 | LoRa/LoRaWAN，测量后设置 SF/功率；改善天线点位；有可行两跳路径时部署固定中继或增加网关 | 选址、链路自适应与中继是**不同动作**。深遮挡未必能靠提高 SF 挽救（SF7→SF12 仅 +14 dB，遮挡超额损耗 71–107 dB）。**不应给 agent 一个无条件成功的"增强信号"按钮** |
| 网关到中心回传间歇中断 | 本地缓存、具备实际覆盖的蜂窝备用链路、北斗短报文等小数据备用回传 | E1/E4 支撑组合思路。**可配置备用路径 ≠ 独立供电、无限吞吐或总能接通** |
| 无市电、需长期自治 | 光伏与储能、低功耗 MCU、**按需给传感器/调制解调器上电**、本地触发与批量上报 | E2/E4 支撑。预算应区分节点与网关；计入采样、接收、重传、存储、**加热**与回传开销 |
| 省电休眠造成下行不可达 | 设备主动报告、约定接收窗口、队列化命令、**遥测携带配置版本与结果** | **休眠是正常协议行为，不能全部归类为故障**；**增加查询可能反而缩短续航** |
| 断连后的执行状态不明 | 幂等赋值、版本化期望状态、持久操作记录、设备侧回执、重连调和 | 与本文 runtime 最贴近，应测其额外收益**与额外代价** |

**标准机制**：[LoRa Alliance TS011 Relay](https://resources.lora-alliance.org/technical-specifications/ts011-1-0-0-relay) 已定义覆盖不足时的**双向帧中继**（[2024 修订 TS011 1.0.1](https://resources.lora-alliance.org/technical-specifications/ts011-1-0-1-relay) 进一步澄清协议行为）。**这是可实施的标准机制，不是任意多跳 mesh 的证明**；能否用于目标设备须核查节点、服务器与区域配置。

Class A 的下行依赖上行后的接收窗口（[Semtech 技术说明](https://learn.semtech.com/mod/book/view.php?chapterid=127&id=172)）→ 详见 `docs/s6-model/downlink-opportunity.md`。"云端随时下发、节点立即执行"的同步 RPC 模型不适合直接套用。**LoRa 点对点与 LoRaWAN 的 MAC 假设不能混用。**

**工程建议**：最小系统取"低功耗节点 — 固定网关 / 可选固定中继 — 蜂窝或小数据卫星回传"。UAV 留作有明确航时、供电、可飞条件与部署延迟的扩展实验；**暂不把 HAPS、无人机常驻和全制式互换放进最小系统**（否则容易把硬件增配收益与 runtime 收益混在一起）。

## 3. 需求表述与五条可检验命题

推荐的需求表述：

> 在灾害尚未发生的长期监测阶段，系统依据外部风险信息和现场观测，在**常态、加密观测与节能维持**模式之间切换；在接入、回传和供电**间歇可用**时，仍应使有效配置按时落地，并在有限能量与通信预算内保全**关键测点的数据新鲜度与历史记录**。

**该表述不要求 LLM 自主判定滑坡发生时刻。** 风险等级、采样下限与预警规则由领域规范/专家或固定回放给定；agent 处理设备能力、资源预算、工作流与异常执行。

五条可检验命题：

1. **缺报原因不唯一。** 休眠、没电、传感器故障、接入丢失、回传丢失可能表现相同。记录"未知"与证据年龄，**不能从一次超时直接判定原因**。
2. **风险阶段与能量预算冲突。** 加密观测产生更多采样与传输，节电可能让观测不够新；**这种耦合需用动作驱动的电量模型验证**。
3. **控制链路也会断。** 超时可能是请求没到，也可能是动作已执行但应答丢失；**查询同样受接收窗口与带宽约束**。
4. **重连带来过时工作。** 旧低频配置在新加密配置之后到达会降低风险时段观测频率；旧高频配置在解除风险后到达会多耗电。
5. **数据补齐不等于预警及时。** 次日补回昨天数据提高档案完整率，却无法弥补昨天关键时间窗口的缺测。

> 第 1、3、4 项的**具体发生频率仍是待测假设**；文献与接口证据不能替代执行故障日志。

## 4. 建议的动作空间（第一轮只实现前四项 + 设备状态回报）

| 动作 | 前置条件与执行对象 | 完成判据 | 实验价值及来源 |
|---|---|---|---|
| `read_status(node, max_age)` | 节点/网关可在实际接触窗口报告；缓存须带时间戳 | 得到带时间戳的电量、版本、缓存水位；**不够新则返回未知** | 有成本的观测，不能直接读模拟器真值；E6/E7 |
| `set_monitoring_profile(node, profile, generation, expires_at)` | 设备支持相应采样/上传参数；profile 满足预设监测下限 | 设备报告**匹配版本/配置摘要**，并观察到对应采样行为 | 主负载：幂等赋值、旧配置覆盖、过期指令；E2/E5/E6 |
| `upload_records(node, time_range, cursor, budget)` | 数据确实存在且剩余能量/链路预算允许 | 接收端确认**样本 ID 或连续游标**，并校验缺口 | 数据面恢复；重复样本去重，**过期历史与新数据分队列**；E7 |
| `request_measurement(node, request_id, deadline)` | 有可调用的按需采样功能；硬件与能量可用 | 返回**本次请求对应**的采集时间与结果，**不能拿旧值冒充** | 命令身份与鲜度；**持续传感器读缓存与触发新测量必须区分**；E7 |
| `set_backhaul_policy(gateway, policy, generation)` | 已安装备用终端且目标链路确有覆盖/额度 | 以版本回报及端到端探测确认切换效果 | 后续扩展；E1 支撑多 WAN、E4 支撑独立卫星实现，**不直接证明自动蜂窝—卫星切换** |
| `set_relay_config(relay, config, generation)` | 已部署且兼容协议的固定中继，维护能量与空口预算 | 中继配置确认并出现可验证的数据通路 | 后续扩展；TS011；**不能抽象成即时部署新物理设备** |
| `restart_device(node, request_id)` | 确有支持、恢复时间与持久化行为已测 | 新启动标识及服务恢复记录；**ACK 本身不充分** | 运维故障实验；E7。**不能默认任意重启都能物理 exactly-once** |

### 4.1 两条必须遵守的评分与设计纪律

**(a) 不同语义不能统一用"每命令执行恰好一次"打分。**
状态配置的评价对象是"**正确状态在正确时间生效**"。重复发送 `set(rate=5min)` 若不引发额外业务副作用，**不应算两次有害执行**，只计其通信与存储成本。独立采样请求按请求标识与实际采集记录评价；数据上传按样本标识评价。

**(b) 配置冲突域宜限定为一个 profile / 资源。**
若只使用**全实体单调 epoch**，晚到的**独立字段写**可能被误判为过时。可选完整配置快照，或明确的分资源版本规则。**物理采集/重启与日志更新并非天然原子，端侧崩溃窗口必须单独测。**

> (b) 直接影响 `README.md` §五 的 C2（单调 epoch fencing）设计：全实体 epoch 的粒度需要重新论证。

## 5. 一个完全灾前的最小案例

> 以下数值是**演示假设**，不是中通服 SLA 或通用地灾阈值。

- **常态**：按既定低频 profile 采集并缓存，网关周期汇总。
- **外部风险等级上升**：将指定关键节点切到加密 profile（例：每小时 → 每五分钟）；**本地触发规则继续独立工作**。
- 一个节点收到新 profile 但**确认报文丢失**；另一个仍休眠；网关中心回传间歇断开。
- runtime 保留未决状态，在**真实可接收窗口**重试/调和；恢复时优先处理最新有效 profile，**限制历史数据补传预算**。
- 注入**迟到的旧常态配置**，检查其是否错误覆盖加密模式；随后风险解除，恢复低功耗模式并验证结果。
- **在任意实际灾害发生之前结束评测**；观测真值及故障日志由独立记录器保留。

**比较重点**：风险窗口内有效测值是否充足、配置错配持续多久、设备是否在后续风险窗口之前耗尽电量、恢复开销是否值得。

**必须加入的竞争解释**：云端长断连时，节点或现场网关应依靠**事先下发的本地规则**维持最低监测服务。因此**"本地规则已经足够"是一个必须被排除的替代解释**——否则无法区分 runtime 的收益与"我们只是多发了几条命令"。
