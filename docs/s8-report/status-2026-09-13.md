## 二、这一轮做了什么（契约 §7 待办 + 11 项编号任务）

### (A) 四接口与三个业务闭环

**改前**：业务层只调用了 `set_monitoring_profile`（1 处），`read_status` / `request_measurement` / `upload_records` **调用次数为零**；运行器里一句 `if "profile" not in payload: continue` 把非 profile 命令直接丢弃；三个闭环里 W2 完全没实现。

**改后**：四个接口全部接通，节点侧语义逐条验证：

| 接口 | 端侧语义 | 验证读数 |
|---|---|---|
| `read_status(node,max_age)` | 时间戳、启动标识、配置版本、电量估计、缓存水位、两个游标 | 由被动遥测免费应答 |
| `request_measurement` | 请求由**窗口内的新样本**应答，标签在采样那一刻打上 | 请求 `m1` 由 60000 s 的样本应答，产出 `n00:60000:rm1` |
| `upload_records` | 只送点名区间、按预算封顶、从点名游标起 | 游标一跳，新数据插到旧缺口前面 |

另补两处**契约明文要求但此前没实现**的：
- **接收端按 ID 去重**——原先无条件 append，一条记录送两次收两次。实测 24 小时内单节点 **5,582 次重复投递**，`received` 列表比实际多十倍
- **缺口核验**——中心原先不能说自己缺了哪一段；现在 `archive_gap` 给出缺失区间两端

**W1/W2/W3 都跑起来了**。W2 此前零实现。

### (B) 强基线补齐

- **本地规则 + 缓存补传**：实测 2 小时回传中断下采样 4608、到达 4396、**档案完整率 95.4%**、无溢出丢弃；发送游标 82800 与确认游标 79200 确实不同

## 三、我撤销或改写的结论（这一节最需要你审）

这一轮最主要的产出不是新读数，而是**发现此前若干结论是错的**。

| 原结论 | 实际 | 根因 |
|---|---|---|
| "主命题已死" | 四条臂里**根本没有本文 runtime** | `operations.py` 从未被业务层引用 |
| "陈旧覆盖上无人能防" | 那是**过期命令被执行**造出的假读数 | 没有强制命令截止期 |
| "更严契约在机会受限下净亏" | 那是 **CAS 实现不公平** | 按 README 而非契约实现 |
| "oracle 不是上界" | **是上界** | 到达索引缺陷 |
| "组合式比单体好 9 个点" | 那是**逻辑身份缺陷** | 键没随需求周期变化 |
| "runtime 因子占绝对主导" | 两个因子量级接近 | 评分修正后 |
| "六类故障都有区分力" | **五类不改变覆盖率** | 故障排班落在无事发生的时刻 |
| "四条臂各 4 次误报成功" | 我的**指标读的是不完整历史** | 释放路径不写 profile 时间线 |

### 最要紧的一个缺陷（D36）

**评分口径里的每一次折叠都必须写明取的是哪一个。**

`arrived_index = {sample.sample_id: arrival for sample, arrival in arrived}` —— 一条记录出现多次时，**字典保留最后一次到达**。节点在确认丢失时反复重传，于是一条**按期到达过**的记录被判定为迟到。

**它不报错，只让所有读数都偏**，而且按"重传了多少"惩罚各臂——各臂重传量差三倍，因此它同时压缩臂间差异并颠倒排序。修完后覆盖率从 54% 变成 89–96%。

**这类 bug 只有在同时改变某条臂的重复次数时才暴露**，我为此重跑了三遍同样的表格，每遍发现上一遍漏了同一类错误。
