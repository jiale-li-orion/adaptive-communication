### 7.1 下行机会约束缺失

**现状**：`Link.request()` 只查询节点当前的信道状态（`node["good"]` 与 `node["alive"]`），下行成功率与节点是否上行无关。`disruption_env.py::call` 与 `mission_sim.py` 的命令路径同样是独立的逐轮伯努利。

**标准规定它们相关**：

- LoRaWAN Class A 的下行只能发生在一次上行之后的 RX1 / RX2 窗口内，节点回到休眠后没有接收窗口，因此**下行机会数 ≤ 上行次数**。
- 3GPP TS 23.682 V19.3.0 cl 4.5.4：PSM 终端 "is not immediately reachable for mobile terminating services"，只有在 connected mode 与随后的 Active Time（T3324）内可达。对野外设备下发只有三条路：等下一个 periodic TAU（T3412 最长可达数百天）、等它因自身上行醒来、或用网络侧缓存（MT NIDD / device trigger / reachability monitoring）在终端变可达的瞬间投递。
- OMA LwM2M 的 Queue Mode 正是为这一约束设计的：服务器排队，等设备再次可达时投递。

**实测后果**。机会率取「节点存活且信道良好」的比例，这是当前模型能给出的最宽松上界：

| 量 | 每节点每小时 |
|---|---:|
| 节点存活 | 0.681 |
| 存活且信道良好 = 机会上界 | **0.362** |
| 等预算对照 budget 3 实际需要 | 0.44（超 1.2 倍） |
| budget 8 实际需要 | 0.97（超 2.7 倍） |
| budget 20 实际需要 | 2.12（超 5.9 倍） |

若节点上报周期是 6 h 而非 1 h，机会上界降到 0.060，三档分别超 7.3、16.2、35.3 倍。

**结论**：等预算对照的三档全部超出机会上界，其中 budget 20 超近六倍。**"预算 20 下 Verified Tool Calls 追平、本文只剩 0.58 个百分点"这条核心负结果，测在一个 MAC 供不起的运行点上。** budget 3 与 budget 8 的超额倍数较小，但同样越界，不能直接引用。

**修复方式**：把控制面机会显式建模为「上行事件率 × 下行成功率」，节点的上行节奏给出机会窗口，协调者的下行请求受该上限约束。这不只是补一个上限：它引入一个此前不存在的资源轴——**每次机会推进了多少**。当前预算 20 下 Verified 花 133,227 次机会在询问，本文花 2,151 次在询问、其余用于写入，两者的机会总数几乎相同（147,505 对 146,266），区别在用途。

**待定参数**：一次上行给出几个下行机会。Class A 约 1，PSM 的 T3324 窗口内可承载多个。这个比值直接决定结果形状，需先定口径再跑。

### 7.1b 两处能量结论必须重述（P0.1 修正后新增）

P0.1 修正 `energy.py` 时暴露出两件事，都会改变现有表述。

**93.7% 与运行时用的模型不是同一个测量。** `code/physics/energy_model.py` 自包含，有自己的按天积分循环，不导入 `energy.py`。README 引用的 93.7% 出自它；而运行时（`disruption_env.py` 与 `method_comparison.py`）用的是 `energy.py`，修正前在同一站点同一电池同一负载下实测 **92.9%**，修正后 **96.4%**。两个数字此前被当作同一件事并列，需要分开表述：`energy_model.py` 的 93.7% 是其日模型的输出，`energy.py` 的 96.4% 是逐小时模型的输出。

**修正引入了一个无出处的假定，而结论对它敏感。** 加热要生效必须有昼夜温差，因此新增了 `DIURNAL_AMPLITUDE_C = 6.0`（最冷约 03:00、最暖约 15:00）。仓库内没有这个量的来源，它是 A 层假设。敏感性：0/3/6 K 均得 96.4%，9 K 得 92.4%，12 K 得 71.4%；温度基线偏移 +9 ℃ 时 100 W 的停电率降到 60.9%，+12 ℃ 时降到 50.8%。因此"充电门限而非能量禀赋是约束"这一结论在幅度 0–9 K 区间内稳定，超出该区间需重新论证。

**同站点上加热是决定性的杠杆。** 该站点年均温 −19.5 ℃，加上 ±6 K 昼夜项后最暖的夏季小时约 +3 ℃，仍低于 LiFePO4 的 +5 ℃ 门限，因此未加热节点全年发电为零，面板从 30 W 到 200 W 一律无效。同一个 100 W 节点加上 8 W 加热盒后可产 280,907 Wh/年，停电率降到 0。这条比"加大太阳能板无效"更可用，因为它同时给出了替代方案。

### 7.2 `energy.py` 的发电量计算（已修正）

```
gen = self.panel_w * dl * PEAK_FACTOR * SYSTEM_DERATE * temp_gain   # 已乘日照小时数 → 日电量
hourly_gen = self._generation_wh(...) / max(self._daylight_h(...), 1e-6)   # 又除回去 → 日照时段功率
self.bat_wh = min(self.bat_wh + hourly_gen - self.load_wh_per_tick, self.usable_wh)  # 但 24 h 每小时都加
```

注释写的是 "generation accrues only over daylight hours"，代码没有实现这件事。24 小时累加等于 `日电量 × 24/dl`：中纬度 `dl ≈ 12` 得 2.0 倍，西藏冬季 `dl ≈ 10` 得 2.4 倍。

**状态：已修正。** 日累计与手工核算逐位相同（doy 172、100 W、7 ℃：834.673805 Wh；旧规则 1435.050 Wh，1.7193 倍），29 项手工核算验证通过，加热改为真实功耗并计入账目，充电门限与容量曲线按化学体系绑定。`energy_model.py` 的 `simulate` 经核查按天正确积分，不受此缺陷影响。

**影响**：全部绝对交付率偏高；停电率与加热比例扫描的绝对值需重算。**配对比较不受影响**，因为 `EnvironmentTrace` 对全部 runtime 共用同一条轨迹，偏差在两侧同时存在。修完后发电减半，停电只会更频繁，因此"加大太阳能板对高海拔站点基本无效"这一结论方向不变。

同一文件另有两处待整理：`step()` 每小时计入发电而不区分昼夜位置；低温充电闸门 `CHARGE_GATE_C` 被当作所有 LiFePO4 的统一物理常数，应按具体器件绑定。

### 7.3 多实体集合未实例化

§一 声明的底层资源是"通感算一体化的多实体集合，包含 LoRa、NB-IoT、CPE、UAV、HAPS、卫星与微波"，§二 用三张表定义该集合。**实测核查：`disruption_env.py` 与 `mission_sim.py` 中上述实体关键词命中数为 0。** `Node` 数据类只有 14 个字段，是一个 LoRa 传感节点加可选中继与网关。§二 的三张表目前是装饰。

**比声明与实现不符更要紧的一点：核心结构假设目前还是一条公理。** 本项目的命题是"agent 的观测通道与它的控制通道是同一条，'实体已静默'与'我的查询在回程丢了'在观测上不可区分"。而真实部署里备用蜂窝链路、小数据卫星回传是常规手段，它们就是带外通道。审稿人只要问一句"部署里既然有备用链路，带外通道不就在那儿吗"，这条假设就守不住。

**修复方式**：把多实体集合真正实例化，让 agent 必须在 N 条候选链路之间自己发现哪条可用。此时歧义不再是假设——agent 分不清某条链路是断了、没电了、还是自己的查询在回程丢了。**§五 的三维观测语义（fresh / unknown / stale / unavailable）正好是描述这件事的词汇表。** 一旦补上，"带外通道"这个攻击面自动闭合，§二 的三张表也从装饰变成被测对象。

### 7.4 主实验没有 agent

§六 实验口径自述"主实验固定同一条决策轨迹，只替换执行 runtime"。`agent_react.py` 是 scaffold（`MockBackend` 与待接的 backend），其结果读数为随机占位。一篇研究 agent runtime 的论文主实验里没有 agent，是审稿人最容易动手的一处。

补接成本很低（两个 backend 已就绪），但**顺序上应当排在昂贵的实证工作之前**：若接上之后结论不保持，叙事要变，那时更贵的工作可能已经白做。最便宜的证伪实验应当排在最贵的工作前面。

### 7.5 必读文献缺口（已补齐三项，一项待订阅）

**α³-Bench（[arXiv 2601.03281](https://arxiv.org/abs/2601.03281)）——阻塞 Gap 1 的那一问有答案了，答案对我们有利。** 该基准的 6G 网络状态是 `n_t = (slice_t, lat_t, jit_t, loss_t, thr_t, edge_t)`，其中 `loss_t` 是"以百分比表示的丢包率"，**它是 agent 观测状态里的一个分量**，不是作用在工具调用执行上的注入故障。工具层做的是 MCP 工具调用与 A2A 协调，量的是"工具使用一致性"；丢包进入的是推理上下文与评分维度（Network Robustness，退化条件下该项下降 30–40%），而它的重试机制针对的是**生成**失败（schema 校验不过），不是网络失败。

**因此 Gap 1 可以落笔**：现有 agent 基准把网络退化建模成**agent 需要观测并据以得分的条件**，而不是**agent 必须消解的执行结果**。"实体已静默"与"我的查询在回程丢了"在观测上不可区分，这件事没有覆盖。这一条此前挂着不能写，现在能写了。

**Atomix（[arXiv 2602.14849](https://arxiv.org/abs/2602.14849)）A.2 是与本文最接近的既有工作，必须正面引用。** 原文：故障按伯努利概率逐 tool call 注入，在工具边界抛异常；Tx-Full 与 CR 中止事务并**用新 epoch 重试**；而 **No-Tx"建模丢失的响应：动作可能已经生效，但调用方看到的是错误，对应现实的超时或丢失的确认"**。这正是本文命题的那条歧义。

差别在消解方式：Atomix 走事务中止与回滚，重试换新 epoch；本文保持**同一个逻辑身份**不变，靠**单调 epoch 的远端 fencing** 让陈旧重发被拒绝而不是覆盖。§7.23 的公平 CAS 基线在同一张表里给出了这两条路线的可比读数。与之配套的反面论据是 *Rollback Is Not Undo*（INFOCOM 2026，DOI `10.1109/INFOCOM59046.2026.11571400`），**需机构订阅，尚未取得全文**，这是本节仍缺的一项。

**AgentChaos（[arXiv 2608.06790](https://arxiv.org/abs/2608.06790)）给出了本文一条实现规则的先例。** 它在 LLM API 层拦截并改写响应，定义 crash / omission / value 三类故障，作用于 content 与 tool call 字段；**并且逐条验证故障是否真的被触发，把未触发的任务过滤掉，以免低估故障影响**。这与 §7.18 第四节独立得到的结论是同一条：*故障事件非空不等于故障影响了待测动作*。本轮为此把按动作的故障改为按真实动作武装，此处有可引的先例。

**AgentDisruptBench（[HuggingFace `kavirubc/AgentDisruptBench`](https://huggingface.co/datasets/kavirubc/AgentDisruptBench)，MIT，100 任务 / 4 领域）的 20 类干扰分类法加强了 Gap 1，而不是削弱它。** 它的四类干扰是：

| 类别 | 类型 |
|---|---|
| Timing | `timeout`、`latency` |
| HTTP Status | `http_429`、`http_401`、`http_403`、`http_500`、`http_502`、`http_503` |
| Response Content | `malformed_json`、`truncated`、`null_response`、`missing_fields`、`type_mismatch`、`schema_drift`、`wrong_data` |
| Behavioral | `intermittent`、`flapping`、`quota_exhausted`、`auth_expiry`、`cascading` |

**二十类全部是"工具调用接口收到了什么坏响应"**，其主指标 `R(k, ε, λ)` 是在重复种子 k、任务措辞变体 ε、故障配置 λ 三个方向上的**通过率曲面**。它衡量的是 agent 对坏响应的**鲁棒性**，而不是**执行结果的不确定性**：没有一类对应"调用可能已经生效，但调用方看到的是失败"。这与 α³-Bench 的结论一致，Gap 1 在它身上同样成立。它的 20 类对照表可用于 §9 第⑥项的故障类型讨论——那是一张**工具调用接口**的分类法，与本文的**链路与生命周期**分类法（请求未达 / 确认丢失 / 旧命令迟到 / 协调者重启 / 端侧重启 / 仅回传中断）互为补充而非重复。

**剩余缺口只有一项。** *Rollback Is Not Undo*（INFOCOM 2026，DOI `10.1109/INFOCOM59046.2026.11571400`）需机构订阅，尚未取得全文。

**引用纪律。** 上述四项的取用只建立在**已读到的原文段落**上；未取得全文的条目（*Rollback Is Not Undo*、AgentDisruptBench）不得据传闻转述。α³-Bench 的结论来自其网络状态定义与指标描述，不是对其代码的复核。

### 7.6 待补的强基线与业务指标

**强基线。** 设备离线管理不是 agent 出现之后才有的问题，以下三条必须进入对照：

- **版本化 desired / reported 状态调和**（AWS Device Shadow 一类）。它按版本丢弃乱序旧更新，语义上就是本文的 C2，**在配置类负载上与本文是同一个方法的不同命名**。它诚实地界定了本文的适用范围：状态对能表达配置，表达不了一次性动作（触发采集、告警确认、补传）。§六 state-setting 一节三个契约配置给出逐位相同的 46.4%，正是这条边界在配置侧的测量值，应当按这个身份引用，而不是当作弱点。
- **队列化接触窗口交付**（LwM2M Queue Mode 思路）。若未运行真实协议栈，应称"语义实现"，不得命名为完整 LwM2M 复现。
- **本地规则 + 缓存补传**，用于回答 agent 编排本身是否必要。

**精确版本 fencing** 是第四条，但它与前三条的定位不同——它是一个**比本文更严的契约**（拒绝更旧的写入之外，还拒绝版本未知的写入者），代价是每次写之前先读一次版本。因此单列在 7.9.2，与游标恢复臂一起跑。

**业务指标。** 现有计数（重复、乱序、覆盖）需要换算成业务损害，其中四项可由已有状态导出，不需要新负载：

| 指标 | 算法 | 回答 |
|---|---|---|
| 配置错配时长 | 对配置时间线积分"实际 ≠ 期望"的小时数，取代当前的轮末采样 | 错误配置持续多久 |
| 关键观测空窗 | 由实际速率与期望速率算漏采量 | 风险时段漏掉多少观测 |
| 误报成功 | 协调者结算为已生效、而结算时该值并未生效或被随后覆盖的次数 | 平台告诉运维"已更新"而实际没有 |
| 平台知晓 vs 实际生效时延 | 由 §五 的 observation 维度直接给出 | 平台以为的与真实发生的差多少 |

第三项落在本文三维语义的 `observation` 维度上，是现有对照都不具备的一栏。它的机制是 7.7.1 的宣告顺序规则：把"宣告"排在"证据落盘"之后，误报成功在结构上就无法产生。

### 7.7 待补的方法表述（已完成）

以下五条是复查方法本身时发现的表述缺口。它们不改变任何数字，但改变方法在审稿人眼里的分量。**五条均已写入 §五 与 §六：** 7.7.1–7.7.3 作为三条新不变量补在"边界与不变量"之后，7.7.5 补在"远端契约的两个等级"，7.7.4 补在 §六 实验口径。以下保留原设计说明以备复查。

#### 7.7.1 宣告顺序：先落盘，再宣告

现有第一条不变量是"登记在派发之前"。它缺一条对偶：

> **在证据落盘之前，不得向平台或运维宣告某个效果已经生效。**

宣告是有外部后果的动作：它写进工单、可能触发人工排查、改变运维决策。若宣告发生在持久记录之前，进程在两者之间崩溃，就会留下一条对外的"已生效"陈述与一具空记录，而此后没有任何办法判断该陈述真假。顺序反过来时，崩溃的最坏结果是记录说已生效、但没有人被告知，这可以通过重放补上。

形式化为 `announce(op) ⇒ durable(evidence(op))`，与现有的 `dispatch(op) ⇒ durable(register(op))` 合起来给出完整规则：**一切对外可观察的动作都排在持久记录之后。**

这条同时是 7.6 表里"误报成功"指标的机制。那项指标测的是症状，这条规则是产生症状与否的原因。

#### 7.7.2 恢复恢复的是知识，不是权限

现有 `reconcile-before-dispatch` 已经蕴含这层意思，但没有说出来。准确表述是：从持久日志恢复出的操作处于**已知但不可派发**的状态；只有在重建到该实体的调和通道之后，它才重新获得派发权。

理由是持久日志保存的是"我做过什么"，它不保存"现在做还合不合适"。重启后协调者对下列事实一无所知：对端是否已经换过 epoch、本地记录的保留期窗口是否还有意义、上级任务是否在此期间被取消。把这些混进同一个状态里，恢复就会自动产生一次未经授权的动作。

由此可得一条可测差别：**恢复后立即重发，与恢复后先重建授权再重发。** 前一者是当前 journal arm 的行为。两者的重复数预期都为零（由 C1/C2 兜住），差别应出现在调和读次数，以及在节点断电、任务取消等场景下的越权副作用上。若该差别确实存在，它是一条独立于"记得 vs 不记得"的机制结论。

#### 7.7.3 准入控制：不派发无人能回收的工作

当前实现里，日志臂会对永久遮挡的节点无限调和（修正前 157,071 次调和读、42 h 空口），当时的处理是加保留期窗口。更根本的规则是：

> **若运行时无法指出一条到该实体的调和通道，就不派发这条操作。**

这条与 7.1 是同一件事的两面：下行机会是调和通道的物理前提，没有上行机会就没有下行窗口，也就没有调和通道。把 7.1 的资源上限与这里的准入判据合起来，永久遮挡点位（88.5%）产生的操作从"永远重试"变成"一开始就拒绝并上报"。

收益有两层。代价层面，它消掉一条随运行时长无界增长的调和负担。账目层面，它使平台的陈述变诚实——运维看到的是"该点位当前不可达、操作未执行"，而不是一条永远停留在在途状态的操作。后者正是本项目要解决的执行歧义的一个镜像：歧义的方向反了过来——从「无法确知效果是否发生」变成「明知无法执行却仍登记为在执行中」。

实现上，准入判据需要输入一个"到该实体是否存在调和通道"的判定。在 7.1 的机会模型下，这个判定可以显式定义为"该实体在保留期内是否存在过至少一次上行机会"。

#### 7.7.4 两种消费语义是系统固有的类别

作业输出存在两类语义：流式输出每次读取消费一段游标、每个字节只交付一次；终结输出是幂等的、可重复读取、不消费游标。这与本文的 `operation` 与 `state_setting` 两个 workload 切在同一条线上。

这一点应当写进 §六 实验口径：**两个 workload 的设立来自执行语义在真实系统里的两种固有形态，与实验是否方便无关。** 它同时解释了为什么 state-setting 上三种契约配置给出一致的 46.4%——幂等语义下执行层的区分能力天然退化，这不是本文方法的失败，是该语义的性质。

#### 7.7.5 身份的可猜测性与安全性无关

`fresh_id` 使用可预测的世代前缀构造身份。若被质疑身份可被伪造，回答是：**边界是授权，不是不可猜测性。** 远端按操作身份去重的同时校验该身份是否属于调用方；身份可猜与身份可冒用是两件事。这一条应与 §五 的远端契约一节合并说明，因为它决定了契约要求部署方提供的是"授权的身份空间"而非"随机不可猜的身份"。

### 7.8 持久日志的健壮性（已完成）

复查 `Journal` 与 `recover()` 时发现三处缺口。它们不影响任何现有数字，但如果日志要承担"跨进程生命周期保存执行连续性"这个角色，三处都必须补。**三条均已实现，回归测试 `code/experiments/test_journal_schema.py`（18 项）通过。**

#### 7.8.1 条目缺 schema 版本号

`Journal.record()` 写入的是 `{"kind": kind, **fields}`，`recover()` 对不认识的 `kind` **静默跳过**。这意味着一处载荷 schema 改动会静默地错放旧日志：不报错，只给出错误的恢复结果。

待补：每条持久变更携带 schema 版本，未知版本**显式失败**。宁可拒绝恢复并要求人工介入，也不要静默产出一个看似正常的状态。这是持久执行系统里的一条通则——**恢复失败必须是响亮的，因为它之后的所有判断都建立在它之上。**

#### 7.8.2 字段集未校验

恢复时应按 `kind` 做精确字段集校验，字段多于或少于预期即判为不可信。这条挡的是最常见的一类改动：写入端加了一个字段、读取端不知道它存在，于是新写旧读产生一个语义上错误的操作。精确校验把这类改动从静默错误变成启动失败。

#### 7.8.3 两类条目共用一条日志

决策存储与操作日志写在同一个 `Journal` 里，条目交织。两类条目的 schema 版本分别管理：`register` / `dispatched` / `observe` / `settle` 属注册表族，`decision` 属决策族，各自带版本号。决策条目的演化节奏与操作条目无关，共用一个版本号会迫使两者同步升级。

#### 7.8.4 实现后的行为

写入侧在追加时即校验 kind 与字段集，不合法的条目根本进不了日志。重放侧在校验整条日志之后才构造状态，任何一条不符即拒绝恢复。两者都抛 `JournalError`。

测试覆盖四类拒收：未知 kind、版本不符、多字段（写入侧新增而读取侧不认识）、缺字段。第四类是实践中最要紧的一类——写入侧加一个字段会产生一个看起来完全正常的操作，事后无从察觉。

### 7.9 待补的对照臂（需要跑）

#### 7.9.1 游标恢复臂 `journal_cursor`

当前日志臂的恢复方式是**全量重放加幂等去重**：不丢任何在途操作，代价是对每个未决操作重新调和一次（本轮 3,130 次调和读，空口 1.41 h 对无日志臂的 1.05 h）。

另一条路是**从最后一条持久确认的游标开始重放**，并接受"崩溃时刻在途的操作可能丢失"。代价有界，代价是可能漏。

这两条落在同一条轴上：**持久化的粒度**。预期游标恢复的调和读大幅下降、重复仍为零，而少数在途操作会从"尚未完成"变为"从未发生"，表现为零次率上升。

实现要点：**游标只标记"已提交给远端"，不标记"远端已确认"。** 这两个必须分开，否则游标会退化成第二条不可靠的回执通道，而它恰恰是为了不依赖回执才被引入的。游标状态本身也要持久，且它的丢失必须退化到安全方向——重放得更多，而不是更少。

这一臂值得单独报一行，因为它把"持久化到什么粒度"从设计直觉变成一个可比的量。

#### 7.9.2 精确版本 fencing 基线

当前 C2 的规则是单调 epoch、拒绝更旧。另一条在真实系统里常用的规则是乐观并发：**写入者必须持有当前版本号，版本不符则拒绝。** 它比 C2 更严——拒绝更旧的写入之外，还拒绝**版本未知**的写入者。

代价是每次写之前要先读一次当前版本。**在 7.1 的机会约束下这不是小代价**：它把"一次写占一次下行机会"变成"一次读加一次写占两次"。若机会成为瓶颈，这条基线的表现会直接反映机会约束的强度。

它同时是一条更保守的正确性基线。若它在本项目全部失效注入下都给出零覆盖，那么"零覆盖"本身就不再构成增量，增量只能来自机会消耗与恢复能力。**这个结果无论倒向哪边都有信息量**，因此值得独立于其他基线单列。

- **曾生效与当前生效分开。** 一个配置被应用、随后被合法的更新取代时，`applied_at` 保留而 `currently_active` 变为假——后来的成功不倒算先前的成功声明。

**三条在实现中发现的机制，值得进入正文。**

控制通道容量取决于数据 profile，而 profile 又取决于控制是否成功。这是自举的：节点切到加密 profile 之前只有常态的每小时一次上行，下发的配置命令只能等那一次机会。oracle 在 12 小时风险窗内仍有约 120 节点小时的配置错配，就是这个延迟的直接读数。

机会的成立条件是上行被网关收到，不是节点发了。Class A 节点发完会开 RX1/RX2，但网关只能使用它知道的窗口，而它知道的唯一途径是收到了那次上行。

上行的分包必须随积压自适应。批量上限取成等于产生速率时，任一次上传失败都会造成队头阻塞且缓冲无界增长——这是回归测试抓出来的一处参数自相矛盾，不是实现细节。

**一处跨模块命名漂移被端到端运行抓出。** 需求侧写 `displacement`、节点侧写 `deformation`，评分器匹配不到任何样本，覆盖率恒为 0 且不报错。已加规范映射，并在公平性审计中断言该映射对两套词表都是满射。

**版本化配置反超了 oracle。** 原因清楚：当前的 oracle 只知道"该切到加密 profile"，不知道**加密 profile 本身就是一笔能量成本**——每 5 分钟采样、每 5 分钟上传，比常态密 12 倍。在供电吃紧时把它切上去会加速死亡，因此真正最优的策略可能是**在电量不足时不切**。

这是建模缺口而非结论，但它指向一条此前没有的机制：**被要求的 profile 是能量负载的一部分，执行它未必改善监测服务**。契约 §9 的分析③（动作驱动能耗）正是为这件事准备的，而现在的实现还没有把"改配置"的能耗代价纳入策略的决策依据。在补上之前，受限组的表不进正文，oracle 那一行也不得称为上界。

### 7.15 七条诊断轨迹：六类故障不区分四条臂

> **本节的结论已撤销，理由与 §7.13 相同（见 §7.18 与 §7.19）。** "六类故障不区分四条臂"在本轮审计后出现了两个更具体的解释，都不是"故障真的不影响任何东西"。其一，`backhaul_only` 此前打在一个不承载观测路径的回传上，它无从影响任何臂；网关与中心分开之后，它立刻使 VTC 57.4%→54.2%、oracle 62.3%→60.9%。其二，`request_lost`、`ack_lost`、`stale_command` 按固定时钟排班，而钟点落在哪一分钟与部署当时在做什么无关——实测 `ack_lost` 的三个故障窗内被点名节点收到命令的次数**都是 0**，事件表非空而动作从未被触及。**"故障事件非空"不等于"故障影响了待测动作"。** 改写后的读数见 §7.18 与 §7.19。

P1 的完整对照。七条轨迹（无故障 + 契约 §5 的六类），四条臂，72 小时，单种子。读数：

| 故障类 | 本地规则 | 版本化配置 | VTC 风格 | oracle |
|---|---:|---:|---:|---:|
| 无故障 | 48.6% | 95.3% | 89.3% | 95.6% |
| 请求未达 | 48.6% | 94.7% | 89.3% | 93.5% |
| 效果发生但确认丢失 | 48.6% | 95.3% | 89.3% | 95.6% |
| 旧命令迟到 | 48.6% | 95.3% | 89.3% | 95.6% |
| 协调者重启 | 48.6% | 95.3% | 89.3% | 95.6% |
| 端侧重启 | 48.6% | 95.3% | 88.6% | 95.6% |
| 仅回传中断 | 48.6% | 95.3% | 89.3% | 95.6% |

**六类故障对四条臂几乎没有区分度。** 版本化配置在全部七条轨迹上停在 94.7–95.6%，跨故障类型的极差是 0.9 个百分点；oracle 在五条轨迹上与它相同，在另两条上更低。本地规则恒为 48.6%。

**三处集成错误已修，空结果因此更强。** 修正前协调者重启在它 10 分钟的停机窗口内每个 tick 都触发一次恢复钩子，而它只应发生一次；旧命令迟到按投递时刻判定，而该故障的定义是"某条在 T 时刻发出的命令延迟到 T' 到达"，`active()` 只在到达的那一分钟为真，按投递时刻判定命中的是巧合而非机制，已改为按发出时刻武装；端侧重启期间节点应停机（事件里带 `uplinks_suspended`），此前未实现。修正后故障按设计生效，四条臂的排序与极差没有变化——**故障确实开火而仍然不区分**，这比修正前更能支持结论。

**注入确实发生了，这一点先排除。** 各类在 72 小时内产生 1–6 次注入（请求未达 6 次 / 确认丢失 3 次 / 旧命令迟到 4 次 / 协调者重启 1 次 / 端侧重启 2 次 / 仅回传中断 1 次），事件列表非空、时刻落在运行内、节点归属正确。空结果不是坏掉的注入器造成的。

**因此故障排得稀是这套参数的性质，而这套参数是 A 层诊断值。** 把这个结论写成"本文 runtime 更鲁棒"需要靠调高故障强度制造差距，那正是本项目一直在避免的方向。诚实的读法是：**在这套诊断故障下，成熟的配置管理做法已经足够，本文的执行层没有可测的增量。**

**D8 的闸门因此落在"调整方向"那一支。** 闸门原文是三条出路：继续主稿（业务收益稳定且值得成本）、收缩主张（收益只在特定条件成立并报告该区间）、调整方向（成熟设备管理全面追平，评估评测与系统经验是否有独立论文价值，或结束该算法分支）。7.13、7.14、7.15 三条读数合起来指向第三支：无故障轨迹版本化配置已落在 oracle 上界 0.3 个百分点内；六类故障不改变排序；电量受限时反而把 oracle 的建模缺口暴露出来。

**这不是实验失败，是判据按设计生效。** D8 存在的意义就是让这件事在写作之前而不是审稿时暴露。可选的下一步有三条，都需要在决策记录里落定之后才能动手：把研究问题从"执行正确性"转到已经测出的边界本身（即"验证读当前状态看不到在途写入"这条机制性结论，它不依赖覆盖率优势）；把资产转为评测与系统经验（环境、故障注入器、审计链已建成）；或结束该算法分支。

**VTC 基线的退避参数是 A 层取值，却驱动它的收敛。** 900 s 基准、4 h 上限、6 h 命令 TTL 都是选出来的，不是标定的。它们直接决定 VTC 的错配时间（10864 min，接近本地规则的 11520），因此**这条基线的表观表现是参数选择的结果**。P2 之前应当冻结这几个值并做敏感性，否则"VTC 收敛慢"这个观察可能只是退避选得保守。

### 7.17 LLM 闭环与一处潜在缺陷

**§7.13 与 §7.15 的"主命题已死"无效，两条理由都是实现错误而不是测量结果。** 在错误修好之前，现有读数既不能证明本文 runtime 有收益，也不能证明它没有。

**甲：业务层把网关与中心合成了一个实体。** `backhaul_gate` 只被 `backhaul_available()` 调用，后者只被 `center_send()` 调用，也就是只管下行。上行分支是 `rec.arrived` 成立后立刻 `rt.confirm(...)` 并写 `status[node_id]`，于是网关听到就等于中心可见，遥测不跨回传。契约 §6 明确要求"明确网络服务器位置、网关预缓存能力及回传时延"，架构 A 写的也是节点、网关、中心三个实体，所以这是违反契约而非简化取舍。

修法是 `opportunity.py` 增加 `GatewayItem`、`gateway_ingest`、`backhaul_forward` 与 `backhaul_delay_s`，运行器的上行只进网关缓冲，每 tick 由 `backhaul_forward` 前转，中心侧才更新 `status`、`confirm` 与接口的遥测记录。存储转发让回传中断**推迟**遥测而不是丢弃它，中断时长因此直接变成观测空窗。修好后 `backhaul_only` 第一次对指标有作用：

| 臂 | 无故障覆盖 | 仅回传中断 | 下行尝试（无故障 → 故障） |

**乙：四条臂里没有本文 runtime。** `grep -rn "from operations import" code/monitoring/` 无命中，`operations.py` 那套执行语义从未被业务层引用。契约 §7 的第五条基线写的是"本文及消融"，实际跑的是本地规则、版本化配置、VTC 风格三条基线加一个策略上界。oracle 是策略不是运行时，而且它走同一个 `AgentInterface`，没有稳定身份、没有远端契约、没有调和，所以它是"某策略在无契约远端上的上界"。**在把 `operations.py` 接进来之前，任何关于执行层的结论都不成立。**

**丙：四项业务指标。** §7.6 列的四项里，配置错配时长本来就已是逐 tick 积分（`config_mismatch_s += TICK_S`），不是轮末采样。其余三项此前完全缺失，现已实现在 `scorer.business_metrics`：

- **关键观测空窗**：按需求 profile 的 `sample_s` 对时间积分得期望样本数，减去实际采样数。
- **误报成功**：中心结算为已生效、而结算时刻该节点实际并不在运行该值的次数。判定要读节点自己的 profile 历史，所以运行器同时记录 `profile_timeline`。

两条读法。其一，确认丢失的代价**按臂不同**：重新验证的臂把知识时延压回分钟级，等待的臂要到 3 至 5 小时，这一栏是现有对照都不具备的。其二，陈旧覆盖让**四条臂各产生 4 次误报成功，oracle 也不例外**，因为 oracle 是策略而不是带单调 fencing 的远端；这是 §7.9.2 那条精确版本契约值得单列的直接证据，也是本文 C2 唯一能拿出的零值。

**丁：按动作的故障必须按动作武装。** 上一版里 `request_lost`、`ack_lost`、`stale_command` 按固定时钟排班，而钟点落在哪一分钟与部署当时在做什么无关。实测 `ack_lost` 的三个故障窗（t=54000/140400/226800，各覆盖 1 小时）内，被点名节点 n03/n11/n08 收到命令的次数**都是 0**，而它们全程各收到 6/7/8 次；事件表非空，被测动作从未被触及。这一类故障是**单次动作的属性**，不是时段属性，因此改为按标称时刻开窗、由该节点下一个真实动作消耗，`stale_command` 的延迟重新锚定到真实派发时刻并保留原有延迟。修改后 `ack_lost` 与 `stale_command` 才产生上表的两栏读数。**"故障事件非空"不等于"故障影响了待测动作"，这两件事此前被当成了一件。**

### 7.19 本文 runtime 入臂，与远端契约第一次成为可测的量

**`operations.py` 的语义第一次接进业务层**，以 `RuntimePolicy`（臂名 `ours`）实现，五条臂由 `policies.BUSINESS_ARMS` 统一登记。三个此前不存在的东西同时落地：

**稳定身份落到报文上。** §7.16 记的缺口有了物理位置：`AgentInterface.set_monitoring_profile` 只接 `profile`，策略手里的版本与逻辑身份在这一层被丢掉。现在 `profile_command` 可带 `version` 与 `logical`，两条投递路径——普通窗口与网络扣留后的释放——共用同一个远端判定函数。此前释放路径直接写 profile，绕过一切契约，于是**即使发送方把版本送上了链路，陈旧命令仍能覆盖更新的那条**，而这正是顺序类故障唯一要制造的危害。

**远端契约实现为 C1 去重加 C2 fencing。** 节点对同一个 `logical` 只生效一次；`version` 低于当前生效值的一律拒绝并回报中心，使中心停止重发而不是等超时。契约按报文字段生效，因此**发送方把版本送上链路才用得上它**：版本化配置臂此前发的是裸值，等于把远端能 fencing 的东西留在中心脑子里。这一条先按公平性修正，再比较。

**证据必须晚于写入才算证据。** 一个与期望相符的上报，只有在它产生于最后一次写入之后才能结清这次写入；产生在写入之前的只是一个更旧状态的读数。本文臂的规则是双向的：上报晚于写入且相符则结算，晚于写入而不符则"这次写入没落地"、过了驻留期重发；早于写入则两者都不成立，只能等。

|---|---:|---:|---:|---:|---:|---:|---:|
| 本地规则 | 32.8% | 0 | 32.8% | 0 | 0 | 0 | 0 |
| 版本化配置 | 59.1% | 387 | 58.4% | 0 | 0 | 41 | 0 |
| VTC 风格 | 57.4% | 215 | 53.5% | **4** | **4** | 0 | 0 |
| 本文 runtime | 57.2% | 293 | 51.4% | 0 | 0 | 44 | 0 |
| oracle | 62.3% | 165 | 60.5% | **4** | **4** | 0 | 0 |

**读法一：配置类负载上，本文臂与版本化配置臂测出的是同一个方法。** 两者都是零误报、零陈旧覆盖，都由 C1 去重挡住（41 对 44 次），`fenced` 都是零——**C2 在这条负载上一次都没有被用到**，因为同一条逻辑命令的重复投递先被去重接住了。这与 §7.6 早已写下的判断一致：设备影子按版本丢弃乱序旧更新，在配置类负载上与本文是同一条边界。本文 runtime 的增量不在这里，而在一句话动作与跨重启持久化；把这半张表当成本文的主要收益是把 §7.6 的边界重新说成弱点。

**读法二：没有远端契约的臂确实吃下全部四次陈旧覆盖。** VTC 与 oracle 各 4 次覆盖、4 次误报成功，**oracle 也不例外**——它是一个策略，不是带单调 fencing 的远端，所以它答不出这个问题。这两行是 §7.9.2 那条精确版本基线值得单列的直接依据。

**一处必须撤销的自证。** 本轮前半段我曾据"四条臂各 4 次误报成功"判断没有任何臂能防陈旧覆盖。那一读数是**指标缺陷**：释放路径当时不写 `profile_timeline`，判定"结算瞬间节点实际在跑什么"时读到的是不完整的历史。补上历史后那 4 次消失，真正的分化才作为上表出现。指标与被测对象同源时，指标的缺口会被读成被测对象的缺口。

### 7.20 §7.9 的两个对照臂与 §7.7.2 的授权重建

### 7.23 四接口与三个闭环接通、2×2 成形、CAS 基线公平化

**一、四接口此前只通了一个。** 业务层只调用了 `set_monitoring_profile`（1 处），`read_status` / `request_measurement` / `upload_records` 调用次数为零；运行器分发里有一句 `if "profile" not in payload: continue`，非 profile 的命令被**直接丢弃**。三个业务闭环里 W2 完全没有实现。

现在四个接口全部接通，节点侧语义逐条验证过：

| 接口 | 端侧语义 | 验证读数 |
|---|---|---|
| `read_status(node,max_age)` | 返回时间戳、启动标识、配置版本、电量估计、缓存水位、两个游标；由被动遥测免费应答 | `snapshot` 字段集已按契约补齐 |
| `set_monitoring_profile` | 版本化赋值，真正改变采样与上传调度 | 原有路径 |
| `request_measurement(node,request_id,deadline)` | 请求由**窗口内的新样本**应答，标签在采样发生那一刻打上 | 实测请求 `m1` 由窗口内 60000 s 的样本应答，产出 `n00:60000:rm1` |
| `upload_records(node,range,cursor,budget)` | 只送点名区间、按预算封顶、从点名游标起 | 实测送出 `[3300..4200]` 而旧缺口等待——新数据插到历史前面 |

三处必须记下的实现细节：**标签在采样时打**，因此旧缓存永远无法事后取得"我是新采集"的身份；**游标用样本时刻而非样本 ID**，ID 按字符串排序会把 `:10800` 排在 `:3600` 之前；**命令到达晚于自己的截止期一律拒绝**，实测拦下过一条窗口已关闭仍被执行到端侧的测量请求。

**二、三个闭环的运行读数。** 24 小时含风险窗（12–18 h）：W1 发出 48 条请求、**端侧应答 14 次**并产生 14 个带标签样本；W2 补传 19 条；W3 表现为 profile 回落。W1 的速率约束是"同一节点有未结请求就不再发，且请求等满自己的截止期"——中心分不清已应答与在途，凭猜测重问正是未知结果要禁止的动作。窗口按**上行节奏**而非采样间隔取：短于它所等待的节奏的窗口根本送不到。第一版没有这条约束时下行 2660 次、机会被吃光；有约束后 235 次。

**三、CAS 基线按契约公平化，旧结论被推翻。** 契约 §7 对这条基线的要求是"**可缓存或从报告获得版本，不强制每次写前额外远程读**"，而 7.9.2 写的是"每次写之前要先读一次当前版本"。两处明文冲突，契约是冻结的权威。上一轮按 7.9.2 实现，据此写了"更严的契约在机会受限下净亏"。**该结论作废。**

| 臂 | 恰好一次 | 写入 | 版本读 | 读失败 | 回复 | 空口 h | 归一代价 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `one_shot` | 32.6% | 1920 | — | — | 405 | 0.2 | 2325 |
| `verified_tool_calls` | 35.6% | 2001 | — | — | 645 | 0.4 | 4161 |
| **本文 `ours`** | **42.4%** | 4549 | — | — | 769 | 0.6 | 5640 |

1455 次读失败全部来自首次读取在节点不可达时的重试；12 次成功意味着 12 个可达节点各读一次、此后**整轮不再读**，因为写入者自己的确认写入就是版本前进的来源。这正是"可缓存"该有的样子。

**公平实现下 CAS 与本文打平，而归一代价低 29%**（4019 对 5640），写入数也少 27%。公平的那条基线不再是净亏，它是一条比本文更便宜的同分方案。旧结论建立在一条被强制每次写前多读一次的实现上，那个代价是实验口径给的，不是契约给的。

**动数字的是 runtime 因子。** 同一个 planner 下 naive→contract 涨 18–21 个百分点；同一个 runtime 下规则与脚本后端只差 1.6–4.2 个点。观测空窗由 runtime 单独决定：naive 50%、contract 0%。这条分解正是 2×2 要给出的东西，也是上一轮那条混合臂给不出的。

**两处自己踩的结构性错误，记下来。** 其一，planner 记住"我上次问过了"就不再产出意图，下游 runtime 于是没有可重试的东西——决策必须按**节点自述**做，不能按自己的请求记录做。其二，`ContractRuntime` 重试预算耗尽后把逻辑动作**永久拉黑**，一次未送达的 profile 会在整轮里再不复发，节点带着错的调度跑完全程而所有计数器正常。预算该限的是连发次数，不是永久封禁。修完这两处，同一格子的覆盖从 27.4% 到 48.9%、下行从 2532 到 188。

**仍须跟上的一条。** 两个 contract 格子的覆盖率低于版本化配置臂（62.6%），原因是本文 runtime 的证据规则要求上报晚于最后一次尝试，而版本化臂按驻留期重发，收敛更快。这个代价是真实的，方向要按机会数配平后再判断。

### 7.24 陈旧覆盖的读数被撤销：它由过期命令被执行造出来

**加一条过期规则，掀翻了前几轮的一条主结果。**

命令有它自己的有效期（`PROFILE_COMMAND_VALIDITY_S = 6 h`），而 `stale_command` 的扣留时长默认取 **[2, 4] × 档位间隙 = 12–24 小时**。也就是说被网络扣住的命令，在释放时**早已过期**。前几轮没有强制过期，于是这些过期命令照旧在节点上被执行，产生了"VTC 与 oracle 各 4 次陈旧覆盖、版本化配置与本文各 0 次"这组读数，并被写进 §7.19 与 §7.21 当作 C2 的唯一数值优势。

补上过期规则后，同一轨迹变成：**4 条被持有、0 条被释放**——扣留的命令全部在有效期内被判过期并丢弃，`stale_reorders` 与 `stale_overwrites` 双双为零。**那条"版本化配置与本文都拿到零"的对比因此没有依据。**

**修法有两处，都不是调参。**

其一，扣留必须短于有效期，否则该故障描述的是一种部署不可能发生的顺序危险，`FaultSpec` 现在直接拒绝这种参数：

```
stale_command: delay_s=21600 is not shorter than the command validity 21600;
the held command would expire before it lands, so no ordering hazard is possible.
```

默认扣留改为 **0.50–0.95 × 有效期**（3–5.7 小时），并且只保留了原来的下界与上界两条断言中的有效期方向。

其二，**扣留还必须跨越一次需求变化**，否则它写回的是当前本来就生效的值——是一次协议层的乱序，不是领域损害。实测：扣留 4 小时而需求每 6 小时以上才变一次，两者几乎从不重叠，于是 4 次注入全部落在"写了同一个值"上。现在故障在派发时额外要求 `issued < 某次变化 ≤ issued + 扣留`，不满足就**保留武装、等下一次真实派发**，而不是把这一次注入花掉。这一条把两种事件分开了，正是 D15 要求的分开计数。

**修完之后的真实读数（72 小时，单种子）：**

| 臂 | 持有 | 释放 | 陈旧乱序 | 陈旧覆盖 | 误报成功 | 覆盖 |
|---|---:|---:|---:|---:|---:|---:|
| 本地规则 | 0 | 0 | 0 | 0 | 0 | 32.8% |
| 版本化配置 | 0 | 0 | 0 | 0 | 0 | 59.1% |
| VTC 风格 | 1 | 1 | **0** | 0 | 0 | 57.4% |
| 本文 | 1 | 0 | 0 | 0 | 0 | 52.3% |
| `rule__naive` | 2 | 2 | **2** | **0** | 0 | 32.8% |
| `rule__contract` | 0 | 0 | 0 | 0 | 0 | 56.5% |

**乱序发生了，覆盖没有发生。** `rule__naive` 的 2 次乱序是协议层的定序违规，它们没有把任何一个已经生效的值写回去。

**这一节的结论必须如实写：本文 C2 在陈旧覆盖这一栏上目前拿不出数值优势，因为它与被比较的臂在同一个零上，而那个零来自"这个 72 小时轨迹里没有一次注入真正造成了值倒退"。** 单种子、注入次数只有 1–2 次，统计功效极低；多种子重跑前，这一栏不得用于任何主张。前几轮据它写的"§7.19 读法一"与"§7.21 读法一"**作废**。

### 7.29 组合式 runtime 的优势是一个 bug：逻辑身份没有随需求周期变化

**§7.23、§六 的 2×2 表与 §7.27 的重启表都建立在同一个缺陷上，那些读数作废。**

**缺陷。** `Intent.logical_key` 对 profile 指令用 `{node}:profile:{value}` 作键，而 `ContractRuntime.settled` 按这个键去重。节点在风险窗之前报过一次 `normal`，这个键就被**永久结算**——需求在小时 18 回到 normal 之后，同一条指令被当成"已经完成"，再也不会下发。

**实测。** 72 小时里组合格发出 **31 条 `risk` 命令与 0 条 `normal` 命令**，96 个操作长期未结，节点 **78.3% 的时间停在密档上**（需求只要求 16.7%）。密档的上传间隔是 5 分钟而不是 1 小时，因此它凭空造出**两倍的上行机会**（29,815 次对 14,127 次），多出来的窗口又变成更多下行尝试。**它领先单体实现的那几个百分点，是这个人为的机会供给买来的，不是方法差异。**

**修法。** `Intent` 增加 `epoch`，在需求值发生**变化**时递增，键变成 `{node}:profile:{value}:e{epoch}`。同一个需求周期内重发仍是同一条指令，跨周期则是一条新指令。

**修完后同一批参数下的读数：**

| 臂 | 覆盖 | 上行 | 下行尝试 | risk 档时间占比 | profile 命令 |
|---|---:|---:|---:|---:|---|
| 本文（单体） | 54.0% | 14,127 | 918 | 16.5% | 49 risk + 56 normal |
| `rule__contract`（组合） | **54.0%** | 14,073 | 943 | 17.2% | 59 risk + 182 normal |
| 版本化配置 | **59.1%** | 15,297 | **387** | 19.8% | 46 risk + 71 normal |

**组合格从 57.0% 掉到 54.0%，与单体实现完全一致。** 两条本文实现现在给出同一个数，这本身是一个有用的确认——方法的两种写法不再互相矛盾。

**由此修正两处此前的表述。** §7.26 末尾那条"组合式比单体好近 9 个点、可能是实现问题"的说法**不成立**：那 9 个点是这个 bug，不是实现质量差异。§7.28 把差距归因于"单体节流缺陷"也**只对了一部分**——组合式当时并没有更好的节流，它只是被卡在密档上、拿到了更多机会。

**当前可信的结论回到一句：在稳态业务指标上，成熟设备管理基线以大约一半的机会开销拿到高 5.1 个百分点的覆盖。** 本文的实现修完节流后仍是 54.0%，与 59.1% 的差距是真实的方法差距，不是实现差距。

**同一个缺陷在 LLM planner 里也在。** `LLMPlanner._to_intent` 构造 `Intent` 时没有传 `epoch`，它因此恒为 0，每个节点整轮的 profile 指令共用同一个键——正是同一件事。**修完后 `llm__contract` 在 72 小时单种子上从 72.5% 掉到 54.2%。**

**三条本文实现现在收敛到同一个数（72 小时，单种子）：** 单体 54.0%、`rule__contract` 54.0%、`llm__contract` 54.2%。**这三条此前是 52.3% / 57.0% / 72.5%，差异全部来自实现缺陷与人为机会供给。收敛之后，"本文方法在稳态指标上是 54%"这一句才有意义。**

**待重跑的状态。** §六 的 2×2 表已用 `--tag 2x2v2`（只修了 rule planner）重跑一次，但那一次 `llm__*` 两格仍带缺陷，**必须再用 v3 重跑**。§7.27 的重启表同理，`--tag restart20v3` 已启动。**在 v3 读数写入之前，`llm__contract` 与 `llm__naive` 两格的所有读数一律不得引用**；`rule__contract` 那一列在 v2 之后可用。

**一次值得记下的过程。** 本轮为此重跑了三遍表格（v2 修 rule planner、v3 修 LLM planner），每次都发现上一遍漏了一个同样的错误。**这类"键在某处被悄悄复用"的缺陷不会报错，只会让读数变好**，因此只能靠在多个实现之间交叉比对来暴露——单体、组合式、LLM 三条路径互相作为对照，是这一轮唯一发现它的方式。

### 7.32 到达时刻索引取的是最后一次而不是第一次：全部覆盖读数被低估

**这是本项目至今影响最大的一个缺陷，§六 的两张主表与 §7.26、§7.27、§7.28、§7.30 的全部覆盖列都因此作废。**

**缺陷。** `scorer._index` 用字典推导构造到达索引：

```python
arrived_index = {sample.sample_id: arrival for sample, arrival in arrived}
```

一条 `sample_id` 在 `arrived` 里出现多次时，**字典保留最后一次到达**。而节点在中心确认丢失时会重传未确认记录——实测 24 小时内单个节点有五千余次重复投递。于是一条**按期到达过**的记录，只要之后被重传一次，就被判定为迟到。

**为什么它一直被隐藏。** 它按"重传了多少"惩罚各臂，而各臂的重传量差三倍（本文 918 次下行对 oracle 165 次），因此它不仅压低所有读数，还**压缩了臂间差异并改变排序**。§7.26 那句"oracle 不是上界"正是它造出来的：oracle 传得最少，受罚最轻，看起来追平了传得多的成熟基线。

**修法落在评分器而不是接收端。** 接收端按 ID 去重（上一轮补的）只保证 `received` 不多记，但"哪一次到达算数"是评分口径，必须由评分器自己说清。现在显式取**最早**到达。

**修正后同一批参数的读数（72 小时，单种子）：**

| 臂 | 修正前覆盖 | **修正后覆盖** | 档案完整率 | 下行尝试 |
|---|---:|---:|---:|---:|
| 本地规则 | 34.6% | **49.5%** | 98.4% | 0 |
| 版本化配置 | 59.1% | **92.8%** | 98.9% | 387 |
| VTC 风格 | 57.4% | **91.4%** | 99.5% | 215 |
| 本文（单体） | 54.0% | **84.9%** | 98.7% | 918 |
| oracle | 62.6% | **95.3%** | 99.0% | 165 |

**三条判断随之改写。**

**一、单种子表里 oracle 回到最高，但 20 种子表否掉了这句话。** 上表是单种子读数，oracle 95.3% 最高。**20 种子（`--tag business2`）否掉了它**：无故障轨迹上版本化配置 **96.34%** 已高于 oracle **95.12%**，两条组合格 94.41% / 94.92% 也逼近它。**oracle 应当被读作"一条没有执行层身份的参考策略"，不是上界**；§7.26 与 §六 里"版本化配置压过 oracle"的说法不应因为这次修正就被当成错误，它只是被换成了 20 种子的读数。

**二、臂间差异整体放大，排序基本不变但间距变了。** 修正前本文与版本化配置差 4.9 个百分点，修正后差 7.9；本地规则从 34.6% 升到 49.5%，说明它有相当一部分"未覆盖"其实是"到过、但被自己的重传判成了迟到"。**本地规则重传最少（不发下行、不触发额外重传），却仍被压低**——这条臂的读数在此前被读成"工程现状只有三分之一"，修正后接近一半。

**三、本文仍是四条非本地臂里最低的一条**，且下行尝试最多（918 对 165–387）。这个结论在修正前后一致，所以它比其余几条更可信。

**状态。** 业务层五臂表与 2×2 表已用修正后的评分器重跑（`--tag business2` 与 `--tag 2x2v3`）。**在替代读数写入之前，§六 两张表与 §7.26/§7.27/§7.28/§7.30 的覆盖列一律不得引用。**

**一条方法论上的教训，写进 D36。** 这个缺陷的方向是"让所有臂都变差、并且让传得多的变得更差"，因此它在任何单一臂的读数里都看不出来，只有在**同时改变一条臂的重传量**时才暴露——本轮是因为补接收端去重顺带改了 `received` 的结构才撞上的。**评分口径里的每一次"折叠"（用 dict 去重、用 set 取并、取最大或最小）都必须写明取的是哪一个，否则它会在无人注意时变成一个对所有臂都生效的偏置。**

### 7.33 恢复归因：给基线一台真的设备影子之后，"跨重启领先 14.1 个点"反转成落后

§7.30 的重启对照把两件不同的事当成了同一件事的两种写法。复核 `policies.py` 与 `runner.py`
之后确认，同一条轨迹上两条臂受到的待遇是：

| | 重启时发生什么 | 代码 |
|---|---|---|
| 版本化配置 | `on_restart` **清空** `desired` / `desired_version` / `issued_version` / `identities` / `reported` | `policies.py:189` |
| 本文 runtime | `on_restart` **只加计数**，全部状态留在对象里，`durable_storage = True` 只是把它标成"有持久化" | `policies.py:671` |

**版本计数器被清空是那 21.2 个点的直接来源。** 重启后 `identities` 归零，下一次写入的版本号
从 1 重新开始，而远端 `applied_version` 停在高水位——`runner.py:304` 的 fence 分支把这个写入
判为"比已生效的值更旧"并拒绝。**唯一被自己的契约反过来挡住一手的臂，正是那条把版本留在内存
里的臂**，而它之所以留在内存里，不是因为它选择不持久化，是因为它的持久化就是"进程没死"。

**公平化。** 新增三条臂，只改"记账放在哪里"，方法一行不动：

- `versioned_config_shadow`：按 AWS IoT Device Shadow 的文档语义，调和文档在平台上，重启后
  读回来（`desired` / `desired_version` / `identities` / `reported*` 存活），只丢进程内的
  未决簿记。
- `versioned_config_version_only`：只保住版本计数器与当前意图，不留"节点报了什么"。
- `vtc_style_durable`：同一套 verify-then-act，背后是持久存储。
- `ours_amnesiac`：本文 runtime，进程真的死了且**没有**日志（`durable_storage = False`）。
- `ours_reconstructed`：本文 runtime，进程真的死了但**日志真的在**，全部内存状态丢弃后只从
  journal 回放重建。

```bash
python3 code/experiments/monitoring_trajectories.py --days 3 --seeds 20 \
  --arms versioned_config,versioned_config_shadow,versioned_config_version_only,vtc_style,\
ours,ours_amnesiac,ours_reconstructed,oracle \

```

| 本文（单体，`ours`） | 94.53% | 94.53% | 0.00 | 2.73% | 628.9 | 0 |
| `ours_amnesiac` | 94.53% | **73.56%** | **−20.97** | 19.69% | 430.9 | 0 |
| `ours_reconstructed` | 94.53% | **94.53%** | **0.00** | 2.73% | 628.9 | 0 |
| oracle | 95.12% | 95.12% | 0.00 | 1.66% | 235.0 | 0 |

**三条结论。**

**一、公平化之后本文在重启轴上不再领先，而是落后。** 版本化配置拿到一台真的设备影子后完全
恢复（75.00 → 96.34，逐列与无故障读数相同），**比本文高 1.81 个点**（修正前是 7.27 点）。
§7.30 的"领先 14.1 个点"因此作废：它是"基线忘了自己的版本号"与"本文的进程没死"两个实现属性
之差，不是方法之差。

**二、本文自己的重启鲁棒性也是对象活着，不是持久化。** `ours_amnesiac` 与 `ours` 只差
"有没有日志"（并且因此 `durable_storage = False`），重启后掉 20.97 个点到 73.56%——**低于
公平的设备影子 22.8 个点**。本文 runtime 在 §7.30 里"纹丝不动"，靠的是同一个 Python 对象。
**这条结论在 §7.34 修正之后更强而不是更弱**：修好排序之后 `ours` 从 89.07% 升到 94.53%，而
`ours_amnesiac` 只从 71.40% 升到 73.56%，两者差距反而从 17.67 点扩大到 20.97 点。

**三、持久性是可实现的，而且只需要两个标量。** `ours_reconstructed` 在重启时把自己交回构造
函数（`self.__init__(**self._constructed_with)`，不是手写一串 `clear()`），然后只从 journal
回放重建每个节点的**最高契约版本**与**那条版本携带的稳定逻辑身份**，读数与 `ours` **逐种子、
逐列完全一致**（20 个种子的覆盖率与其他 10 个指标全部相同）。

**由此，"持久保存版本号就够了吗"有了两个独立答案，都是"够"。**

- `versioned_config_version_only` 与完整的 `versioned_config_shadow` 逐列相同（96.34% /
  372.6 / 47.5）——影子文档里除了计数器之外的字段，对恢复没有任何额外贡献。
- `ours_reconstructed` 只消费两个标量就恢复了全部 17.67 个点。

**所以本文对持久性的要求是"每节点两个整数"，不是"完整操作历史"。** 这个答案削弱而不是加强
本文的主张：任何一条愿意存一个计数器的实现都能拿到同一份恢复能力，成熟设备影子本来就存。


**一处顺带修好的不公平（D39）。** runner 把 `in_flight`（网络侧"命令还没送达"的簿记）直接
当成 `view.in_flight`（中心"我知道自己有命令在外"的信念）交给策略。协调者重启后命令确实还在
网关里，但一个没有持久化记录的中心不该知道这件事。原实现把这个信念送给了所有臂，等于把重启
本该拿掉的能力又还了回去。现在两者分开：`center_belief` 在无日志臂重启时清空，`in_flight`
继续承担送达簿记。

**D37。** 恢复对照的两条臂必须具有**同等**的持久化能力，判据是"状态是否在进程之外"而不是
"代码里有没有一个叫 durable 的字段"。任何一条臂的重启读数，必须在另一条臂有机会做同样的事
之后才可比较。

**D38。** 声明 `durable_storage = True` 的臂必须能在测试里从日志重建出恢复所需的状态，且日志
必须记录远端据以 fence 的字段。原来的 journal 只记接口参数（`profile` / `generation` / `path`），
**两个 fence 字段根本不进日志**，因此无论怎么回放都重建不出一个不被 fence 的发送方。schema 由
v1 升到 v2 并加 `contract_logical` / `contract_version`；校验是双向精确的，因此 v1 日志会被
明确拒绝而不是被猜着读。回归测试 `code/experiments/test_recovery.py` 覆盖：日志带契约字段、
日志经 JSON 往返后逐字节相同且重放结果不变、新对象能从日志重建高水位与逻辑身份、无日志臂两个
标量都归零（这条让前一条成为证据而不是同义反复）、`memory` 模式行为未变。

### 7.34 稳态差距归因：5.3 个点来自一个 tick 内的下发顺序，不是方法差异

§7.30 留下一处"仍未查清、已排除四个嫌疑"的分歧：单体 `RuntimePolicy` 比两条组合格低 5.3–5.8
个点，而且**在无故障轨迹上就已经差这么多**（89.07% 对 94.41% / 94.92%），重启只是让同一个差距
继续存在。它在稳态就被查明，与重启无关。

**主因。** `RuntimePolicy.plan` 在一次调用里先返回 W1 的 `request_measurement`、后返回 W3 的
`set_monitoring_profile`（`policies.py`）；控制面对每个上行机会**只投递节点队列的队首一条**
（`opportunity.py` 的 `_deliver` 取 `queue[0]`，Class A 的 `downlink_per_uplink = 1`）；而
`RuntimePolicy` 在节点有在途操作时**否决一切写入**（`skip/in_flight`），`ContractRuntime` 没有
这条。三者叠加：风险窗开启的那一刻节点还在常态档，上行节奏是每小时一次，**于是这唯一的一次
下行机会被排在队首的测量请求占掉，切档整体推迟整整一个常态档上行周期（3600 s）**。

**证据（trajectory `none`，72 h，20 种子；详见 `docs/s8-report/q3-steady-state-gap.md`）。**

| 检验 | 读数 |
|---|---|
| 损失的位置 | 14 条配置的**常态类命中数全部是 141.7–141.9 / 142（100%）**，差异全在风险窗需求（82.7%–91.9%） |
| 切档延迟 | `ours` 139.82 min 对 `rule__contract` 78.91 min，**差 60.91 min ≈ 常态档上行周期 3600 s** |
| 只重排、不改任何参数 | `ours` 89.07% → **94.53%**（下行 604.75 → 628.90） |
| 参数逐项放宽 | **没有一条能到 94%**：最大 +0.47（`retry_budget=99` 与 `dwell_s=0` 读数逐位相同），五个参数全放宽 +0.42 |
| 死参数 | `status_max_age_s`（1 h→24 h）与 `enable_backfill=True` 都是 **+0.00**；`wait/dwell` 分支稳态触发 **0 次** |
| 两臂发的测量请求 | **完全一样**（96.0 次/运行，逐种子无差异）——差别只在排在哪个位置 |
| 否决的规模 | `skip/in_flight` 7827.9 次/运行，其中 **85.3%** 发生在有 W1 请求未结时，3891.4 次的需求是 `risk` |
| 代价方向 | `ours` 关掉 W1 少花 **281.0** 次下行且 **+5.30 点**；而 W1 在组合臂里只值 **+0.13 点** |
| 不改代码的机制检验 | 把场景参数 `--downlink-per-uplink` 提到 2（非结论，用于检验队首阻塞），`ours` 89.07% → **94.87%**，两臂差距 5.34 → **0.57** 点 |

**修法。** `RuntimePolicy.plan` 在返回前按接口优先级稳定排序：**档位写入 → 测量请求 → 补传下单**。
理由是档位写入是唯一改变节点回访频率的命令——它既让窗口后半段可观测，又会产生那条测量请求
本来想要的样本；两者同时待发时，请求要的东西正是这次写入马上会造成的。

```python
priority = {OP_SET_PROFILE: 0, OP_REQUEST_MEASUREMENT: 1, OP_UPLOAD_RECORDS: 2}
out.sort(key=lambda item: priority.get(item[1].get("op"), 3))
```

**这一条是缺陷，不是调参。** 一个"先要样本、再换档位"的顺序，在"一个机会只投一条、且写入被
在途操作否决"的链路上，等于把换档推后一个周期；而 `RulePlanner.decide` 的顺序本来就是反的
（`compose.py`），所以两条实现此前读的是**不同的策略**，被并排放在 §7.30 的一张表里。**修正后
单体 94.53% 与组合格 94.41% / 94.92% 基本持平，那条"5.3–5.8 点的实现分歧"消失。**

**修正后需要重写的读数。** 主表、恢复表、消融表全部重跑（`business3` / `fairrestart4` /
`ablate20v3`）。**无故障轨迹上成熟基线领先本文的差距从 7.2 个点缩到 1.8 个点**（96.34% 对
94.53%），而本文的下行开销仍是它的 1.7 倍（628.9 对 372.6）。`2x2v3` 是组合臂，不受影响。

**没查清的部分（照录）。** 种子间残余摆动（`rule__contract − ours` 从 −5.12 到 +10.47）未分解；
"顺序 × 在途否决"没有做完整因子分解——单独去掉否决反而 −0.69 点且下行 +435.5，方向相反；
"去掉否决导致下行暴涨"的二次机制没查（怀疑走能量模型，未测）；W1 在组合臂里几乎零收益却吃掉
469.8 次机会，只给了"排序 + 否决"一条解释路径。**这几条都不影响上面的主因判定，但它们是下一步
该做的因子分解。**

**修复后 W1 的边际值是 +0.16 点（风险类 +0.21），代价 +305 次下行（1.94 倍）。** 这不足以确认
稳定收益，但**同样不足以据此删除它**，理由全部来自契约原文而非仿真：

**一、契约给它记了独立评分。** §4 把它列为闭环"风险上升后的加密观测——…设置 profile、
**必要时请求新采集**、处理未决结果"，独立后果是"有效配置是否及时生效；**风险窗中新测量是否

**二、它服务的义务是"样本必须是新采的"，而这一条是被强制执行的——但义务不等于这个动作。**
`request_measurement` 的约束一栏写着"**旧缓存不能冒充新采集**"；评分器 `scorer._covered_by` 要求
`window_start <= sample.taken_at <= window_end` 才算覆盖（`scorer.py:119-125`），另有一处专门
统计"拿窗口之前的样本冒充窗内样本"（`scorer.py:322`）。**需求分母确实承载了这条义务，不是 W1
无处施展。**

**但是要注意这两句话不是一回事**（D44）：

- 被证明的是："风险窗内的新测量按期到达"是一项业务义务。
- **没有被证明的是**："主动发出 W1"是满足它的唯一路径。

`_covered_by` **不检查这条样本是不是 W1 触发的，也不看请求 ID**。周期采样加及时上传能够满足同
一个需求，那是合法替代路径——而 §7.34 的排序修复做的正是让周期上传自己满足它。**所以本仓库此前
写的"W1 承担一项不可替代的义务"是过头话，已改：义务是真实的，这个动作只是当前实现里的一条
路径。**

**三、它只值 0.16 点的原因是采样从来不是瓶颈、上传才是。** 常态 profile 每 300 s 采一次，比任何
需求窗都密；而风险需求要求样本在窗开始后 **10 min** 内到达（`DEADLINE_S["risk"]`），常态 profile
的上传周期是 **3600 s**。W1 要做的是在"档位还没切过去"的那段时间里，用一次显式请求把新采的样本
挤进 10 分钟窗口。**§7.34 的排序修好之后档位写入排到队首，这个缺口在无故障工况下基本被写入自己
填掉了**——这就是 0.16 点的来源。**但"写入总能及时落地"是 `none` 轨迹的性质，不是故障轨迹的
性质**，而 `ours W1 off` 目前只在 `none` 上测过。

**四、要决定默认行为，需要的不是总体覆盖率，而是一组范围明确的对照。** 轨迹取
`request_lost` / `stale_command` / `backhaul_only` / `node_restart` 加低机会额度轴
（`sensitivity.py --opportunities 1,2,4`）；指标取**"风险窗中新测量按期到达率"**本身
（`steady_gap.py` 已输出 `risk_coverage`）与"窗开时该组无任何节点在 risk 档"的比例。判据：若在
写入被延迟或丢失的条件下关掉 W1 使该率下降，W1 保留为默认；若不下降，按 D32 的先例登记为"在这套
部署下冗余"——**但仍保留接口**，因为义务是契约赋予的，只是当前需求分布没把它逼出来。

**本轮不执行这组对照，也不改默认行为（D42）。** 排序修复已经让这个量从 −5.30 变成 +0.16，方向
都变了，说明它对实现细节很敏感。

### 7.37 任务合理性：当前参考负载里没有决策

在 §7.33–§7.36 把全部对照公平化之后，剩下一个更前置的问题：**这个任务本身是不是研究问题的
有效实例。** 逐项核查 `task_generator.py` 的实际输出（`build_deployment(0)`，72 h）之后，结论是
**不是**。完整核查见 `docs/s7-method/task-challenge-pivot-2026-09-13.md`。

**负载的精确结构：**

| 项 | 值 |
|---|---|
| 总需求 | 430 |
| 风险需求 | **288** = 144 个时刻（风险窗内每 5 min 一个）× 2 个关键节点；样本窗 **300 s**、宽限 **300 s** |
| 正常需求 | 142（样本窗 3600 s、宽限 5400 s） |
| 关键节点 | 8 / 16 |
| 风险窗 | 第 12–18 h、48–54 h，共 12 h |
| 机会供给（常态档） | 16 × 72 = **1152**；`ours` 实际下发 **664** |

**三条推论，每一条都让这个任务离监测更远一步。**

**一、风险需求不可能靠"按时采样"满足，所以采样频率不是变量。** 常态 profile 每 300 s 采一次，
样本一定在窗内；但常态档上传周期 **3600 s**，而宽限只有 **300 s**。**一条风险需求能否被满足，
等价于"该节点此刻是否处于 `risk` 档"。**

**二、`risk` 档是已知的时钟函数。** 中心拿到公告后持有整份日程（含窗口结束时刻）。W3 是它的逆
操作，W2 默认关闭（D32），W1 边际值 +0.16 点（§7.36）。**唯一承重的动作是把 `profile` 改过去、
再改回来。**

**三、于是整个任务是一句话：在两个窗口开启时，把一次已知的状态写进 8 个节点。**

**四、三条约束在主表里都不 binding。** 供电：4 个种子、72 h 结束 **0 个节点死亡**，
`blackout_ticks` 为空。机会：供给 1152 对下发 664，利用率约 58%，稀缺是突发的而不是结构的。
正确性：`stale_command` 扣留 21 条命令，**真正迟到释放 1 条**，危险交错 **1 次**（§十四的探针），
连同乱序/覆盖回退的效应量约 **0.125 次/运行**。

**五、尺度是 2 个事件 × 20 个种子。** 关于风险窗的每条结论，独立事件数是**每轮 2 次窗口开启**，
不是 288。这就是 §7.34 的排序修复能一次移动 5.5 个点的原因——它移动的就是那两个事件。

**为什么这比"参数没调好"更严重。** 需求是外生的（D18 明确写了需求集不随种子变化，也不随观测
变化），**中心看到什么都不影响它下一步要看什么**。一个不依赖观测的需求序列，无论参数调到多
极端，都只能测出投递能力，测不出监测决策。**所以任务给不出正结果，也给不出可发表的负结果**

## §7.38 执行层：身份缺字段维度污染了整条结论线（2026-09-13 补）

**先记缺陷，再记结论。** 契约层的 `logical` 曾写成 `f"{node_id}:period:{generation}"`——
**没有字段维度**。同一次决策的两个字段共享一个身份，于是第二个字段在远端与"第一个字段的重发"
不可区分，被当重复永久丢弃。两个后果都很隐蔽，而且正好污染本轮要下的结论：

- `atomic` 永远凑不齐一对，**等于一条配置都不下发**：它的三个业务数字与 `local` 逐位相同
  （149.5 / 18.5 / 2211 / 169.0），读起来像"正确但没用"的结论。
- `contract` 每次决策只落地一个字段（下发次序先间隔、后周期，上报周期**恒为默认值**），
  把跨代混配推得**比 `naive` 更长**，读起来像"契约反而有害"。

修法：`logical = f"{node_id}:{op}:{generation}"`。同时把"世代到齐"的定义从"两个字段"改成
"**这次决策意图写的字段集合**"（报文带 `fields`）——否则单字段策略 `AoiPolicy` 在原子层下会被
**整类丢弃**，那比缺陷更难发现，因为它让策略与执行层不可比。

与"原子层 0 个节点配置改变"。**作废**：旧读数的"上行 466.5 → 433.1（−7.2%）"那一版量的是这个

## §7.39 换掉 regret 的分母：真上界（2026-09-13 补）

**旧分母不能留。** ⑧/⑨ 的 regret 分母是**事后最优固定配置**（`best_fixed_posthoc`）：它随测试
条件变化（同一个策略在不同条件里对着不同分母算），而且**不是上界**——`ea_i600` 已经超过过旧的
"全知上界"（现更名 clairvoyant static selector）。旧上界 `dynamic_upper_bound` 也不行：两条松弛
叠起来**恒为 168/168**，用它算 regret 等于拿常数当分母，`local` 与 `dense600` 在它眼里一样。

**新真上界** `oracle.py:dynamic_oracle`：逐节点、逐小时的离线动态规划，状态是离散化的 `soc`，
每小时选一个档位（300/600/900/1800/3600）或"本小时不采样"，读**完整未来采能轨迹**。只松弛
可交付性；**不松弛**档位离散性与能量的小时耦合（含容量溢出截断）。

**造它的过程中踩了三个错，全部记档：**
1. **重复计数**：闭区间窗 `[h*3600, (h+1)*3600]` 用严格比较，第 h 小时的义务在第 h+1 小时又被记
   一次，12 条数成 23 条。改成"只在 `window[0]` 所在小时计一次"。
2. **把"电量耗尽"当成"轨迹不可行"**：`reward + (-inf) = -inf` 而 `-inf > -inf` 为假 → 档位留
   `None` → DP 强迫节点撑满整个时间窗。0.004 Wh 的节点能采 8 小时却被报成 0 条义务。加"本小时
   不采样"动作后修好——物理上耗尽就是停止采样。
3. **上界被真实策略突破**：纳入事件义务后，容量 0.05 下 `dense600` 交付 184 条、上界 171 条。
   实例在触发时刻做**触发锚定**的本地采样（1052 s 不在 300 s 网格上），上界动作集够不到。
   于是上界**只覆盖周期义务**——这也与既有纪律一致（事件列在全部臂上恒定 21.0/16.8，明令不得
   支撑结论），而且更紧得住：真实策略还要为事件采样花电，上界不给这笔电。
   **这一条是 `test_instance.py` [15] 抓到的**，不是自查出来的。

**结果**：真上界 168.0（名义 / 0.008）/ 146.2（0.004）；周期达标率 91.9% / 87.6% / 87.0%。
分解精确：`168 = 周期交付 + 缺采 + 缺送`。

**结论方向与预期相反**：headroom 是 8–13%（不是旧上界暗示的 0%），但**几乎全在链路交付侧**——

所以"本 task 不需要更强的 planner"这句话**方向成立、数值要改**：不是没有余量，而是余量不在

## §7.41 真实采能时间过程 `H_i(t)`、autonomy margin，与上界动作空间的一处缺陷（2026-09-13 补）

**一、`solar_harvest`（合成，A 层）与 `autonomy_margin`。** ② 到 ⑬ 都建立在"容量 × 标量采能"上，
这两者把能量问题压成**总量**问题，"什么时候有电"不进入模型。日照曲线把昼夜节律、短时云遮、
持续积雪引进来了。**合成曲线必须标明**：形状与参数是 A 层研究选择，结论只能读作"在这个形状下如何"。

**二、margin 的定义与三个已修错。** `margin = 1/λ_min`，`λ_min` 是使每个小时都还买得起该小时
采样能耗的最小采能缩放倍率。`1` 恰好够、`>1` 有富余、`<1` 不够、`=0` 不可能。错法记档：
1. **单调性方向搞反**：按"最大可行 λ"写，容量不受限时该值发散，每条都返回上界 8.0。有信息的是

2. **下界不可行被当成答案是 0**：初始电量为 0 时 `λ=0` 必然不可行，而正确答案完全可能是 1。

   四条曲线**逐位相同**。改成"日出固定 06:00、运行窗在钟面上滑动"才真的会动。
   **参数必须证明它会动**，与结果列同等适用。
以上三条都是测试 [17] 抓到的。手算可核：恒定采能 `h`、消耗 `c`、初始 0 时 `margin = h/c`，

能否撑住"，不刻画形状相对工作负载密度的关系。**引用 margin 必须同时给形状。**

**五、上界动作空间的一处缺陷（零 的收尾）。** 第一版 oracle 动作是一维、按"每采一条报一条"计能，
于是**高估密集采样能耗**。一维动作集是二维的真子集 → 旧值是真最优的**下界**，不是上界。
已改成 `(采样间隔, 上报周期)` 二元组。**实测影响为零**：四档绑定条件 20 种子均值逐位相同

而 `p = a` 时两式完全相等。**但"正确性"与"数值影响"是两件事**：只报前者夸大，只报后者留雷。
测试 [18] 用 `dense300`（采 300/报 900）钉住。

## §7.43 真实辐照下的 calibration cliff（含一个差点毁掉结论的抽样陷阱）

### 一、cliff 在真实天气里依然存在，而且更强

cap 0.004 Wh、峰值 0.02 Wh/h、闸门关（隔离时序形状），20 组真实窗口 × 10 种子：

| 窗口起点 | 真上界 | `local` / `ea_i600` / `ea_nb` 达标% | `dense600` | `dense1800` |
|---|---:|---:|---:|---:|
| 0 h | 168 | 82.7 | **19.5** | 32.1 |
| 1095 h | **140** | 85.4 | **30.5** | 56.3 |
| 2190 h | 168 | 88.2 | 91.1 | 91.1 |
| 3285 h | 168 | 55.1 | **19.5** | 31.8 |
| 4380 h | 168 | 86.7 | 55.6 | 76.4 |
| 5475 h | 168 | 82.7 | **25.5** | 85.6 |
| 6570 h | **112** | 82.7 | **29.3** | 47.8 |
| 7665 h | 168 | 87.1 | 70.2 | 83.9 |

`dense600` 的达标率在真实季节之间从 **19.5% 摆到 91.1%**，而三条反馈/基线臂稳在 55–88%。
**换到真实辐照之后，cliff 没有消失，离散度反而更大**——因为真实年周期里既有盛夏也有隆冬，
合成正弦只有一个振幅旋钮。

### 二、一个差点毁掉结论的抽样陷阱：**24 h 步长与昼夜周期相位锁定**

**这是本轮最有价值的方法学发现，必须记下来。**

第一次扫描我用"每 24 h 取一个窗口"（365 个样本），得到：**margin 全年最小 9.34、无一不可行**。
据此差点写下"真实辐照下能量并不紧张"。**它是错的**：

| 扫描方式 | 样本数 | 其中不可行 |
|---|---:|---:|
| 每 24 h 一个 | 365 | **0** |
| **全部 8760 个** | 8760 | **2775（31.7%）** |

原因是算术：**24 h 步长与昼夜周期严格同相**，365 个样本**全部落在同一个钟点上**，等于只探查了
一天之中的一个相位。而不可行与否恰恰取决于 12 h 窗口从哪个钟点开始。

**同一处的极端敏感**：起点 1080 h → margin **17.09**、1104 h → **23.58**、而 **1095 h → 0.000**。
平移 15 小时把结论从宽裕翻成不可能。

**因此的规则**：扫周期现象时，**抽样步长不得与现象的周期成整数倍关系**。本条的正确做法是
**相位分层**（每月一个窗口 × 四个钟点相位），而不是等间隔抽样。`irradiance_windows(hours, n)`
的默认等间隔实现在 n 使得步长为 24 的倍数时就会踩这个坑，已在文档里标出。

### 三、真实的能量利用率分布（全部 8760 个窗口，离线算，cap 0.004）

- 不可行（margin = 0）：**2775 个，31.7%**
- 可行：5985 个，margin min **0.09**、中位 **28.02**、max **78.89**

**读法限定**：这是**条件面**，不是概率。`cap 0.004` 与 `peak 0.02 Wh/h` 都是 A 层取值，
窗口是按 2023 年该点位的天气逐小时平移取的；**没有真实联合分布，就不能说"现实中有 31.7% 的时间
会这样"**。

## §7.44 相位分层扫描的分布性结论，与 no-op tax 的机制

### 一、48 个相位分层真实窗口（cap 0.004，10 种子）

| 臂 | 达标率 min | 中位 | max | **极差** |
|---|---:|---:|---:|---:|
| `local` | 55.1% | 82.7% | 88.2% | 33.0 |
| `ea_i600` | 53.9% | 82.7% | 88.2% | 34.2 |
| `ea_nb` | 55.1% | 82.7% | 88.2% | 33.0 |
| `dense1800` | 31.8% | 62.2% | 91.1% | 59.2 |
| `dense600` | **19.5%** | **29.8%** | 91.1% | **71.5** |

**固定策略的失败不再是一个数字，而是一个分布**：真实天气窗口之间摆动 **71.5 个百分点**，
而反馈/基线臂只摆动 33 点。48 个窗口里 15 个的 margin = 0（连基准工作负载都不可行）。

### 二、no-op tax 的机制：**只有一到两条采样的生存余量**

在一个真实窗口（起点 2926 h，cap 0.004）上做逐节点解剖，链条完整且可核算：

1. **该窗口开头有连续 7 个小时采能为零**（该点位真实的黑夜；采能从第 7 小时才开始爬升）。
2. 节点初始 4e-3 Wh，按每小时约 5e-4 Wh（采样 4.7e-4 + 空口约 3e-5）**只够约 8 小时**——
   **熬过这 7 小时黑夜的余量只有一到两条采样**。
3. `Node._take`：`if soc < sample_wh: alive = False; dead_at = t`——**付不起一条就永久判死，
   不跳过、不复活**。于是日出后第一个采样时刻（**t = 25260 s = 7.017 h**）就是生死线。
4. `ea_i600` 与 `local` 的**唯一差别是那 28 条命令**，而这 28 条设的值（3600/3600）
   **与设备出厂默认逐位相同**，是**值域空操作**。
5. 结果：**3/14 个节点恰好死在 t = 25260 s**；死亡是吸收态，它们丢掉整个白天的采能。
   10 种子均值：交付 135.9 → **109.6**、缺采 13.2 → **42.3**、死节点 0.8 → **7.2**。
6. `ea_nb`（`send_when_unknown=False`，**一条命令都不发**）与 `local` **逐位相同**。

**单条命令的代价可以手算**：一次接收窗口 `3.3 V × 11 mA × 2.0 s / 3600 = 2.0167e-5 Wh`
（`opportunity.RadioEnergy.add_rx`，`rx_window_ms = 2000`、`RX_MA = 11.0`），即**一次采样的 4.3%**。

**能量账本的一个反直觉事实（已核对）**：真值侧每节点 13 h 有 **0.0402 Wh** 采能，节点只吸收
**6.5e-3 Wh**（16%），其余因电池满而溢出——`consumed_wh == harvested_wh`、末态 `soc` 仍等于初值。
**瓶颈不是采能总量，是"电池只能缓冲约 1.3 小时的采能"。**

**一处没有查到最后的（如实记下）**：是哪三个节点（n01/n07/n11）被选中。已确认命令序列会整体
平移空口的随机流、从而改变逐节点空口开销，但没有追到最后一抽。**在那之前不把"空口能耗"
写成唯一的致因。**

### 三、这一节对主张的意义

**现象是实的、量级是大的、且来自本 task 本身**（不是人为造 fault）：`ea_nb` 与 `local` 逐位相同，
而 `ea_i600` 的 28 条值域空操作把交付砍掉 26.3 条。这给"action admission / no-op tax"提供了
一个**可核算的落点**：在多条命令都设成同一个值、且系统处于能耗刀刃上的时候，
**控制流量本身就是一种服务损害**。

**限定**：cap 0.004 与峰值 0.02 Wh/h 都是 A 层取值；"7 小时黑夜"是该窗口的真实形状，
不是全年典型值（见 §7.43 的相位分层分布）。
