# 灾前山区监测：通信与供电痛点、可执行动作及 runtime 论文决策

调研日期：2026-09-12；对齐本地 gap 的修订日期：2026-09-13。审阅本地提交：`9f330ed`。性质：定向文献调研、代码静态核查与研究建议；未运行新仿真、未开展现场实测。本文是已有研究的补充决策建议，尚未替换 README 的研究契约。

**判断：保留山区滑坡灾前监测场景，收窄到“间歇连接与有限能量下，监测模式变更及数据回传任务的可靠执行”。已有文献足以支撑场景和动作，但尚不足以证明现有 runtime 超越成熟设备管理机制。下一步优先补真实动作闭环和强基线，再决定论文主贡献。**

“持续稳定通信”宜转化为可考核的服务要求：关键风险窗口内数据足够新、关键测点没有过长观测空窗、配置能在期限内生效，断连后可恢复历史记录。永久无路径且无电时，软件无法保证实时回传；应把增加中继/回传与恢复任务执行分别计账。

## 0. 先继承本地 gap，本次只补现实任务链

已对齐 [s3 的七条 gap](../s3-novelty/prior-art-agent-runtime.md)、[核验与撞题记录](../s3-novelty/verified-evidence.md)、[母论文调研](../s3-novelty/prior-art-mother-papers.md)，以及较新的 [README](../../README.md)。`s3-novelty` 和 `s5-benchmark` 是被 Git 忽略的本地材料，普通 `rg --files` 不会列出；读取它们需使用 `--no-ignore`。初次检索漏掉这些材料，本修订已补读并据此调整结论。

已有结论包括：单个 runtime 机制没有新颖性；固定 planner 比较执行层；无线传输失效与工具 API 错误不同；任务进展与副作用正确性必须独立评价。本轮不把这些重新包装成新发现，也不重新启动寻找现成 agent-network benchmark 的已放弃路线，见 [s5 状态说明](../s5-benchmark/README.md)。

## 1. 最直接的证据及其边界

以下 E 编号区分事实来源；后文接口、指标和实验编排属于本报告建议，并非原作者已实现的 agent 系统。

| 证据 | 已核验内容 | 支撑什么；不能支撑什么 |
|---|---|---|
| E1：Kumar 等，*Wireless Networks* 26:2137–2152 (2020)，2019 年在线发表 | 山区滑坡预警 WSN 部署明确遇到非对称链路、天气引发动态变化、太阳能不足、切换和重连；采用中继及多 WAN 容错，摘要报告连接恢复少于一分钟 | 直接支撑灾前通信痛点，也证明恢复已有研究。此次核验出版社及作者机构摘要，未通读付费全文；该恢复时间不能直接当作西藏 LoRa 参数。[出版社](https://link.springer.com/article/10.1007/s11276-019-02059-7) |
| E2：Wang 等，*Frontiers in Earth Science* 10:899509 (2022) | 贵州尖山营 LoRa 节点经主节点、4G 回传，太阳能加 12 V/10 Ah 电池；常态与异常阶段采用不同采集/传输频次，现场运行约九个月 | 支撑低功耗与加密观测的业务切换。不是西藏实验，也没有给出可复用的长期链路 outage 分布。[全文](https://www.frontiersin.org/journals/earth-science/articles/10.3389/feart.2022.899509/full) |
| E3：Leinauer、Krautblatter，EGU25-11121 (2025) | Hochvogel 高山监测缺乏永久电源、存在积雪及无线边缘覆盖；超过五年运行，10–12 个传感器、10 分钟传输；裂缝计小时可用率 96.7–99.4%，激光测距仪为 56–65%，后者受雪埋影响 | 支撑多年维护困难及测项可用性差异。是会议摘要；端到端测值可用率不等于 LoRa 分组投递率。[作者摘要](https://meetingorganizer.copernicus.org/EGU25/EGU25-11121.html) |
| E4：平升电子西藏水文项目 | 三个无市电、无手机信号的水雨情站；北斗短报文、60 W 光伏与 38 Ah 蓄电池；定时给终端/传感器上电，完成采集上传后断电 | 高度匹配西藏供电与覆盖约束，但属于相邻水文场景和厂商自述，无独立可靠性验收数据。网页历史报文额度不代表当前北斗三号通用限制。[项目原文](https://www.data86.net/xzmdjybdtxdswjcxmalfx.html) |
| E5：司南导航楚雄项目，2024-07-18 发布，项目时间 2022-04 | 在 31 个滑坡隐患点安装 147 台设备，接收机支持根据运动/位置变化切换模式，并支持远程管理 | 支撑灾前多测点监测及模式控制的工程需求；多模能力清单不能证明每个点都安装了全部通信制式。[实施方案例](https://www.sinognss.com/about/news_information/2332.html) |
| E6：重庆市规划和自然资源局公开的群测群防智能化监测预警设备通信材料，PDF 印刷页 10–11 | 定义上报周期 `0042`、采样间隔 `0045`、通信模式 `00D0` 的设置/上报，带序列号及回复机制 | 证明远程配置是行业实际接口；其中模式编码是 NB-IoT/GPRS，不能直接扩展解读成卫星切换。序列号也不自动等于持久幂等保证。[官方 PDF](https://ghzrzyj.cq.gov.cn/zwxx_186/tzgg/202005/P020200527440877815913.pdf) |

## 2. 技术手段如何对应真实断点

| 层次与断点 | 优先考虑的技术 | 对本项目的含义 |
|---|---|---|
| 节点到网关边缘覆盖 | LoRa/LoRaWAN，测量后设置 SF/功率；改善天线点位；有可行两跳路径时部署固定中继或增加网关 | 选址、链路自适应与中继是不同动作。深遮挡未必能靠提高 SF 挽救；不应给 agent 一个无条件成功的“增强信号”按钮 |
| 网关到中心回传间歇中断 | 本地缓存、具备实际覆盖的蜂窝备用链路、北斗短报文等小数据备用回传 | E1/E4 支撑组合思路。可配置备用路径，不意味着独立供电、无限吞吐或总能接通 |
| 无市电、需长期自治 | 光伏与储能、低功耗 MCU、按需给传感器/调制解调器上电、本地触发和批量上报 | E2/E4 支撑。预算应区分节点与网关；计入采样、接收、重传、存储、加热和回传开销 |
| 省电休眠造成下行不可达 | 设备主动报告、约定接收窗口、队列化命令、遥测携带配置版本与结果 | 休眠是正常协议行为，不能全部归类为故障；增加查询可能反而缩短续航 |
| 断连后的执行状态不明 | 幂等赋值、版本化期望状态、持久操作记录、设备侧回执、重连调和 | 与本项目 runtime 最贴近，应测其额外收益和额外代价 |

LoRa Alliance 的 [TS011 Relay](https://resources.lora-alliance.org/technical-specifications/ts011-1-0-0-relay) 已定义覆盖不足时的双向帧中继；[2024 修订](https://resources.lora-alliance.org/technical-specifications/ts011-1-0-1-relay) 进一步澄清协议行为。这是可实施的标准机制，不是任意多跳 mesh 的证明。是否能用于目标设备，应核查节点、服务器及区域配置。

LoRaWAN Class A 的下行接收依赖上行后的接收窗口，见 [Semtech 技术说明](https://learn.semtech.com/mod/book/view.php?chapterid=127&id=172)。因此“云端随时下发、节点立即执行”的同步 RPC 模型不适合直接套用低功耗 Class A。LoRa 点对点与 LoRaWAN 的 MAC 假设也不能混用。

工程建议：先以“低功耗节点—固定网关/可选固定中继—蜂窝或小数据卫星回传”为主架构。UAV 可留作有明确航时、供电、可飞条件及部署延迟的扩展实验；暂不把 HAPS、无人机常驻和全制式互换放进最小系统。

## 3. 痛点到任务的抽象

推荐需求表述：

> 在灾害尚未发生的长期监测阶段，系统依据外部风险信息和现场观测，在常态、加密观测与节能维持模式之间切换；在接入、回传和供电间歇可用时，仍应使有效配置按时落地，并在有限能量与通信预算内保全关键测点的数据新鲜度与历史记录。

该表述不要求 LLM 自主判定滑坡发生时刻。风险等级、采样下限和预警规则由领域规范/专家或固定回放给定；agent 处理设备能力、资源预算、工作流与异常执行。

具体痛点可以拆为五个可检验命题：

1. **缺报原因不唯一。** 休眠、没电、传感器故障、接入丢失和回传丢失可能表现相同。记录“未知”和证据年龄，不能从一次超时直接判定原因。
2. **风险阶段与能量预算冲突。** 加密观测产生更多采样与传输，节电可能让观测不够新；这种耦合需要用动作驱动的电量模型验证。
3. **控制链路也会断。** 超时可能是请求没到，也可能是动作已执行但应答丢失；查询同样受接收窗口与带宽约束。
4. **重连带来过时工作。** 旧的低频配置在新的加密配置后到达，可能降低风险时段观测频率；旧高频配置在解除风险后到达，可能多耗电。
5. **数据补齐不等于预警及时。** 次日补回昨天数据提高档案完整率，却无法弥补昨天关键时间窗口的缺测。

第 1、3、4 项的具体发生频率仍是待测假设；文献和接口证据不能替代执行故障日志。

## 4. 建议的 agent 动作空间

接口名是本项目建议。E 编号支持底层需求/能力，不表示原系统有同名 API。第一轮只实现前四项与设备状态回报。

| 动作 | 前置条件与执行对象 | 完成判据 | 实验价值及来源 |
|---|---|---|---|
| `read_status(node, max_age)` | 节点/网关可在实际接触窗口报告；缓存须带时间戳 | 得到带时间戳的电量、版本、缓存水位；不够新则返回未知 | 有成本的观测，不能直接读模拟器真值；E6/E7 |
| `set_monitoring_profile(node, profile, generation, expires_at)` | 设备支持相应采样/上传参数；profile 满足预设监测下限 | 设备报告匹配版本/配置摘要，并观察到对应采样行为 | 主负载：幂等赋值、旧配置覆盖、过期指令；E2/E5/E6 |
| `upload_records(node, time_range, cursor, budget)` | 数据确实存在且剩余能量/链路预算允许 | 接收端确认样本 ID 或连续游标，并校验缺口 | 数据面恢复；重复样本去重，过期历史与新数据分队列；E7 |
| `request_measurement(node, request_id, deadline)` | 有可调用的按需采样功能；硬件与能量可用 | 返回本次请求对应的采集时间和结果，不能拿旧值冒充 | 命令身份与鲜度；持续传感器读缓存和触发新测量必须区分；E7 |
| `set_backhaul_policy(gateway, policy, generation)` | 已安装备用终端且目标链路确有覆盖/额度 | 以版本回报及端到端探测确认切换效果 | 后续扩展；E1 支撑多 WAN，E4 支撑独立卫星实现，不直接证明自动蜂窝—卫星切换 |
| `set_relay_config(relay, config, generation)` | 已部署且兼容协议的固定中继，维护能量及空口预算 | 中继配置确认并出现可验证的数据通路 | 后续扩展；TS011；不能抽象成即时部署新物理设备 |
| `restart_device(node, request_id)` | 确有支持、恢复时间与持久化行为已测 | 新启动标识及服务恢复记录；ACK 本身不充分 | 仅作为运维故障实验；E7。不能默认任意重启都能物理 exactly-once |

状态配置的评价对象是“正确状态在正确时间生效”。重复发送 `set(rate=5min)` 若不引发额外业务副作用，不应当作两次有害执行；计其通信与存储成本即可。独立采样请求则以请求标识及实际采集记录评价。数据上传按样本标识评价。不同语义不能统一用“每命令执行恰好一次”打分。

配置冲突域宜限定为一个 profile/资源。若只使用全实体单调 epoch，晚到的独立字段写可能被误判为过时；可选完整配置快照或明确的分资源版本规则。物理采集/重启与日志更新并非天然原子，端侧崩溃窗口必须单独测。

## 5. 一个完全灾前的最小案例

以下数值是演示假设，不是中通服 SLA 或通用地灾阈值。

- 常态：按既定低频 profile 采集并缓存，网关周期汇总。
- 外部风险等级上升：将指定关键节点切到加密 profile，例如从每小时到每五分钟；本地触发规则继续独立工作。
- 一个节点收到新 profile，但确认报文丢失；另一个仍休眠；网关中心回传间歇断开。
- runtime 保留未决状态，在真实可接收窗口重试/调和；恢复时优先处理最新有效 profile，限制历史数据补传预算。
- 注入迟到的旧常态配置，检查其是否错误覆盖加密模式；随后风险解除，恢复低功耗模式并验证结果。
- 在任意实际灾害发生之前结束评测；观测真值及故障日志由独立记录器保留。

比较重点：风险窗口内有效测值是否充足，配置错配持续多久，设备是否在后续风险窗口之前耗尽电量，以及恢复开销是否值得。

云端长断连时，节点或现场网关应依靠事先下发的本地规则维持最低监测服务；不能把所有灾前加密动作都建立在云端在线的假设上。这也意味着必须加入“本地规则已经足够”的竞争解释。

## 7. 必须正视的已有机制与强基线

设备离线管理并不是 agent 出现后才有的问题。

- [AWS Device Shadow](https://docs.aws.amazon.com/iot/latest/developerguide/iot-device-shadows.html) 已区分 desired/reported 状态，并给出按版本丢弃乱序旧更新的方式。配置负载应加入这种语义的实现，不能只比较 one-shot 和盲重试。
- [OMA LwM2M 1.2.2 Transport](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Transport-V1_2_2-20240613-A.html) 包含 Queue Mode，支持设备休眠、再次可达后再交付请求。它是“接触窗口下发”的重要先例。
- [CoAP RFC 7252](https://www.rfc-editor.org/rfc/rfc7252.html) 已有消息去重及幂等 PUT 语义。有限缓存/重启边界应按实际协议分析，不能把现有协议写成完全不处理重复。
- E1 的山区 WSN 部署已经研究容错回传与重连。不要从“通信文献不写 agent”推导为“通信文献未处理失效”。

建议基线结构：

1. 固定本地监测规则＋缓存补传＋静态回传，回答 agent 编排是否必要。
2. 同 planner＋持久队列＋重试退避＋设备端幂等键，回答稳定身份之外的收益。
3. 同 planner＋版本化 desired/reported 配置调和，作为配置负载的强基线。
4. 队列化接触窗口交付，可采用 LwM2M Queue Mode 思路；若未运行真实协议栈，应称“语义实现”，不得命名为完整 LwM2M 复现。
5. 现有 verified-tool-calls 与本 runtime，在相同端侧能力、消息与能量预算下比较。

端侧 receipts、fencing、持久化应分别做等能力比较和消融。若只有 ours 使用配合的远端协议，结论必须是“客户端＋远端协议的整体收益”，不能归因于 agent 更强。ADR/中继/链路切换可以固定为共同基础设施；系统级另做因子实验，避免把多装硬件的收益算给 runtime。

## 8. 后续评测契约

**实验 A：固定动作的运行时机制。** 同设备、同信道、同 profile 请求序列，只替换执行层。分开注入请求丢失、确认丢失、单向链路、休眠、过期投递、网关重启、设备重启及持久化丢失。保留永远不可达的负面案例。

**实验 B：灾前任务闭环。** 风险阶段回放→有效 profile→实际采样→缓存与传输→耗电→后续可达性。共享的是外部扰动，不是各策略的电池结局。以原 hourly 模型跑长时间背景、以事件驱动模型表达秒/分钟窗口；小时粒度不能证明五分钟交付时限。

**实验 C：最小硬件闭环。** 建议先用 2–4 个可控节点、一个网关、可控回传和电流记录装置；用链路丢包/延迟与供电中断重复 A 的关键案例。设备配置日志、采样时间、网关接收与中心接收四者必须可对齐。台架注入支持机制可行性，不等于西藏长期性能；随后才进行实际安全监测点试验。规模与时长为本报告建议。

建议主指标：

| 指标 | 定义与避免的混淆 |
|---|---|
| 风险窗口及时数据覆盖率 | 按风险时段、测点和必要测项，统计数据到达时年龄是否低于规定期限；阈值由场景契约给定 |
| 关键观测空窗 | 数据年龄越限持续时长及分位数；区分单传感器与多个关键测点同时缺测 |
| 配置错配时长 | 对有效期内“实际 profile ≠ 期望 profile”积分；比轮次末一致率更能揭示迟到覆盖 |
| 模式切换期限满足率 | 在有效期限内配置被执行且取得足够执行证据；分别报实际生效与平台知晓的时延 |
| 每个及时有效记录的能量/通信代价 | 包括采样、接收、查询、重传、持久化、网关及备用回传，不只计 Tx |
| 历史完整率 | 按样本 ID/采集时间统计补齐，独立于实时合格率 |
| 语义失败及未知率 | 陈旧覆盖、过期执行、实际副作用重复、误报成功、结果长期未知分别报告 |

两个分母同时报告：全部任务需求，以及物理上有至少一次可用机会的任务需求。前者体现工程缺口，后者隔离运行时执行能力。共享种子做配对区间；增加不同行为负载、outage 分布和节点持久化条件，检验收益是否只出现在人为偏置的用例。

成本用明确台账拆成节点、中继、网关、光储、回传资费、现场安装和运维次数。当前没有报价及运维频率，不预填“降低成本 x%”。

## 9. 论文路线决策

| 路线 | 价值与主要风险 | 决策 |
|---|---|---|
| A：低功耗山区覆盖/通信方案 | 最直接回应产业需求，但仅组合成熟技术难形成新贡献，需新硬件、组网或联合优化及外场证据 | 作为工程背景和共同底座，暂不转为主线 |
| B：灾前监测任务的中断容忍执行 runtime | 与现有代码最贴近；需求与动作可溯源。风险是与影子状态、队列、幂等/版本机制重合 | 推荐下一轮验证，先补强基线和业务闭环 |
| C：能量与数据新鲜度约束下的主动查询/重试/调和调度 | 通信研究问题更集中：把有限下行、能量与动作截止期纳入优化 | 若 B 的正确性收益被成熟方案覆盖，再探索该分支；此时不是立即立项承诺 |

可用工作题目：**“面向灾前山区监测的间歇连接感知任务执行运行时”**；英文工作题目 *Interruption-Tolerant Execution of Monitoring Tasks in Energy-Constrained Mountain Networks*。

要主张的候选增量是：在受限接触窗口内，对有有效期、不同执行语义的监测动作维持可核验执行，并量化其对关键数据可用性和能耗的影响。是否构成方法创新，取决于与上述强基线比较，而不是由场景真实性自动推出。

建议推进顺序：

1. 固定四个核心 API、端侧能力和数据/配置评价契约；用 E2/E6/E7 对齐，准备给中通服核实。
2. 接通 profile→采样→电量→数据交付的闭环，修正能量与时隙模型的已识别问题。
3. 加入版本化设备影子、持久幂等队列和本地规则基线，先跑小规模配对实验。
4. 若强基线下仍有业务收益，再做硬件闭环、扩大仿真并接入 LLM 补充评测。
5. 若增益只来自额外端侧能力、额外中继，或只消除了无害的重复赋值，缩减相应论文主张；保留工程价值，重新选择 C 或其他有证据的研究增量。

**当前判定：场景与动作抽象可以继续；不建议直接进入论文定稿。** 通信系统路线应让收益体现为关键数据、接触窗口与能耗约束下的性能；若最终只有通用持久执行机制，宜按系统问题重新定位，不能仅靠加入山区 DEM 来建立通信创新。

下一次与中通服交流最值得获取的是：真实 RTU/网关型号与接口、常态/汛期采样和上传周期、命令回复与重启行为、带发送端分母的报文轨迹、供电电流/电压/光照记录、以及一次缺报导致人工排查的完整工单。优先区分“只能上报”与“可远程配置”的现网设备；这决定 runtime 能否真实落地。
