# 评测契约：强基线、业务损害指标与实验编排

> 来源：`docs/s2-scenario/pre-disaster-runtime-decision-2026-09-12.md`（Astra，2026-09-12）的 §6–§8，2026-09-13 转写入本文档。
> 本文件取代"只报执行计数"的旧口径。配套：`docs/s7-method/task-and-action-space.md`、`docs/s6-model/downlink-opportunity.md`。

## 1. 必须正视的强基线

**设备离线管理不是 agent 出现后才有的问题。** 现有工业机制已覆盖本文一部分地盘：

| 机制 | 已有能力 | 对本文的含义 |
|---|---|---|
| **[AWS Device Shadow](https://docs.aws.amazon.com/iot/latest/developerguide/iot-device-shadows.html)** | 区分 desired / reported 状态，并**按版本丢弃乱序的旧更新** | 配置负载应加入这种语义的实现，**不能只比较 one-shot 与盲重试** |
| **[OMA LwM2M Queue Mode](https://www.openmobilealliance.org/release/LightweightM2M/V1_2_2-20240613-A/HTML-Version/OMA-TS-LightweightM2M_Transport-V1_2_2-20240613-A.html)** | 支持设备休眠、**再次可达后再交付请求** | 这是"接触窗口下发"的重要先例；也直接对应 `docs/s6-model/downlink-opportunity.md` 的机会约束 |
| **[CoAP RFC 7252](https://www.rfc-editor.org/rfc/rfc7252.html)** | 已有**消息去重**与**幂等 PUT** 语义 | 有限缓存/重启边界应按实际协议分析，**不能把现有协议写成完全不处理重复** |
| **E1（Kumar 等）** | 山区 WSN 已验证容错回传与重连 | **不要从"通信文献不写 agent"推导为"通信文献未处理失效"** |

## 2. 建议的基线结构（五项）

1. **固定本地监测规则 + 缓存补传 + 静态回传** → 回答 **agent 编排是否必要**。
2. **同 planner + 持久队列 + 重试退避 + 设备端幂等键** → 回答**稳定身份之外的**收益。
3. **同 planner + 版本化 desired/reported 配置调和** → 配置负载的**强基线**。
4. **队列化接触窗口交付**（可采用 LwM2M Queue Mode 思路）→ 若未运行真实协议栈，须称"**语义实现**"，**不得命名为完整 LwM2M 复现**。
5. **现有 verified-tool-calls 与本文 runtime**，在**相同端侧能力、消息与能量预算**下比较。

> **端侧 receipts、fencing、持久化应分别做等能力比较与消融。** 若只有 ours 使用配合的远端协议，结论必须是"**客户端 + 远端协议的整体收益**"，不能归因于 "agent 更强"。ADR / 中继 / 链路切换可以固定为**共同基础设施**；系统级另做因子实验，**避免把多装硬件的收益算给 runtime**。

## 3. 实验编排（A / B / C）

**实验 A：固定动作的运行时机制。**
同设备、同信道、同 profile 请求序列，只替换执行层。**分开注入**请求丢失、确认丢失、单向链路、休眠、过期投递、网关重启、设备重启及持久化丢失。**保留永远不可达的负面案例。**

**实验 B：灾前任务闭环。**
风险阶段回放 → 有效 profile → 实际采样 → 缓存与传输 → 耗电 → 后续可达性。**共享的是外部扰动，不是各策略的电池结局。**
以原 hourly 模型跑长时间背景，**以事件驱动模型表达秒/分钟窗口**：

> ⚠️ **小时粒度不能证明五分钟交付时限。** 广东地方标准要求"现场数据采集至传输监控终端 ≤5 min"，而本文当前仿真是小时步长——**按标准口径目前无可主张的能力**。

**实验 C：最小硬件闭环。**
建议先用 **2–4 个可控节点 + 一个网关 + 可控回传 + 电流记录装置**；用链路丢包/延迟与供电中断重复 A 的关键案例。**设备配置日志、采样时间、网关接收与中心接收四者必须可对齐。**
**台架注入支持机制可行性，不等于西藏长期性能**；随后才进行实际安全监测点试验。

## 4. 主指标（取代纯执行计数）

| 指标 | 定义与要避免的混淆 |
|---|---|
| **风险窗口及时数据覆盖率** | 按风险时段、测点与必要测项，统计**数据到达时年龄是否低于规定期限**；阈值由场景契约给定 |
| **关键观测空窗** | 数据年龄越限的**持续时长及分位数**；区分单传感器与多个关键测点**同时**缺测 |
| **配置错配时长** | 对有效期内"实际 profile ≠ 期望 profile"**积分**；比"轮次末一致率"更能揭示迟到覆盖 |
| **模式切换期限满足率** | 在有效期限内配置被执行且取得足够执行证据；**分别报"实际生效"与"平台知晓"的时延** |
| **每个及时有效记录的能量/通信代价** | 包括采样、接收、查询、重传、持久化、网关及备用回传，**不只计 Tx** |
| **历史完整率** | 按样本 ID / 采集时间统计补齐，**独立于实时合格率** |
| **语义失败及未知率** | 陈旧覆盖、过期执行、实际副作用重复、误报成功、结果长期未知**分别报告** |

### 4.1 两个分母必须同时报告

- 分母 1：**全部任务需求** → 体现工程缺口
- 分母 2：**物理上至少有一次可用机会的任务需求** → 隔离 runtime 的执行能力

> 这一条直接修掉 `README.md` 自己承认的问题："到报率的分母包含永久遮挡节点，因此 47.8% 反映的是物理边界而非策略上限。"

### 4.2 统计与成本口径

共享种子做**配对区间**；增加不同行为负载、outage 分布与节点持久化条件，**检验收益是否只出现在人为偏置的用例**。

成本用明确台账拆成：节点、中继、网关、光储、回传资费、现场安装、运维次数。**当前没有报价与运维频率，不预填"降低成本 x%"。**

## 6. 继续投入的判据（可证伪）

**在强基线下，runtime 仍改善了有业务意义的执行正确性或数据可用性，且额外通信、能量成本合理** → 继续。

**若收益只来自以下任一项，则收缩对应主张：**

1. 多装中继 / 额外硬件；
2. 端侧独享的持久化能力（而对照没有同等能力）；
3. 只消除了**无害的重复赋值**。

**agent 的必要性应单独检验**：本地规则能够完成的即时保护**继续留在节点**；agent 的候选价值是**跨设备、跨资源的任务编排与恢复**。这样也更容易证明 runtime 的收益不依赖"换一个更聪明的 LLM"。
